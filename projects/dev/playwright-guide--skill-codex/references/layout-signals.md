# Layout Signals

Использовать, когда задача про смысловые части интерфейса: крупные и мелкие блоки, расстояние между секциями, порядок, визуальный вес.

Это не pixel-diff инструкция. Это набор сигналов, которые нужно собирать через официальный Playwright path.

## Главный Принцип

Не мерить смысл страницы по одним пикселям и не мерить его по одному DOM.

Сильный проход строится так:

1. semantic structure
2. rendered geometry
3. block grouping
4. visual weight
5. only then verdict

## Полезные Сигналы

### 1. Semantic anchors

Сначала искать крупные смысловые зоны:

- `main`
- `nav`
- `header`
- `footer`
- `aside`
- `section`
- `article`
- `form`
- headings

Если страница не даёт нормальных anchors, это уже полезный сигнал, а не только неудобство.

### 2. Rendered geometry

Для каждого кандидата на block-level смысл:

- `x`, `y`, `width`, `height`
- доля viewport
- доля видимости
- relative order on screen

Считать по rendered boxes, а не только по source order.

### 3. Block grouping

Элементы стоит склеивать в один смысловой блок, если одновременно держатся несколько сигналов:

- общий контейнер
- маленький gap
- общая ось выравнивания
- похожая типографика
- одна heading-to-body связь
- повторяемый паттерн sibling items

### 4. Visual weight

Вес блока не равен одной площади.

Смотреть вместе:

- площадь
- размер и вес текста
- контрастность и заметность
- image presence
- число interactive elements
- позицию в экране
- шум вокруг

Маленький CTA может быть важнее среднего текстового блока.

## Практические Проверки

### Gap analysis

Мерить не просто `px`, а отношение:

- межсекционный gap
- внутрисекционный gap

Если gap между двумя supposedly major blocks почти такой же, как внутри одного блока, секции визуально слипаются.

### Block sizing

Большой смысловой блок лучше определять не по одному `height`, а по комбинации:

- area ratio
- наличие heading или landmark
- dominance against neighboring blocks

### Order check

Сравнивать:

- visual order
- DOM order
- accessibility order

Если визуально главное идёт в одном порядке, а читается в другом, это отдельная проблема, не мелкая оговорка.

### Visual-weight check

Спрашивать не "что больше", а:

- что первым притягивает взгляд;
- есть ли явный главный блок;
- не получили ли слишком много равного веса второстепенные части;
- не затёрт ли важный action.

## Базовые Эвристики

### Above-the-fold clarity

В первом экране обычно полезно увидеть:

- 1 явный главный блок
- 1-2 вторичных направления

Если всё одинаково кричит, иерархия слабая.

### Repetition handling

Список из карточек не стоит на раннем шаге считать десятью независимыми "смыслами".

Сначала это collection.
Потом уже можно анализировать отдельные cards как внутренний уровень.

### Sticky noise

Sticky header, floating chat, cookie banner и другие service layers легко ломают картину.

Их надо учитывать отдельно от основного content flow.

## Что Не Делать

- не объявлять visual hierarchy только по area
- не делать вывод о reading order только по screenshot
- не смешивать service chrome с основным content weight
- не строить вердикт раньше evidence
- не использовать один жёсткий threshold для всех страниц
