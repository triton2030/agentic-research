Как работают мои skills

Skill в твоей системе - это не “талант модели”, а маленький рабочий контракт: когда включаться, какую локальную правду читать, какой owner имеет право решить вопрос и каким evidence закрывать работу.

Путь одного запроса

Когда ты пишешь задачу, skills не складываются в один большой autopilot. Они дают короткую маршрутизацию: кто владеет решением, что надо прочитать, и где остановиться.

1

Запрос попадает в trigger layer

Название skill, path на SKILL.md или описание задачи включает routing. Если ты явно называешь $html, выигрывает обычный HTML-output, а не diagram-output.

2

Codex читает живой контракт

У каждого skill есть локальный SKILL.md. Его надо прочитать перед действием. Если там есть references или scripts, они сильнее общего знания модели.

3

Owner решает право слоя

Сложная часть - не “какой файл править”, а “какой слой имеет право владеть этим правилом”. Здесь ключевой router: 1folder-contract.

4

Work skill делает ограниченную работу

1md-navigator ищет, 1md-reader читает выбранное, 1md-graph проверяет последствия, 1skill-architect держит skill package, html собирает объясняющий output.

5

Closeout требует evidence

Финал должен назвать наблюдаемое изменение: файл, commit, проверку, clean status, browser check, validator, снятый риск или точный следующий owner.

Четыре слоя skills

Это не иерархия важности. Это разные права: одни skills выбирают путь, другие читают корпус, третьи создают output, четвёртые проверяют или критикуют.

Owner routing

Этот слой отвечает за право решения. Он нужен, когда локальный фикс может создать второй source of truth, положить правило не туда или спутать owner.

1folder-contract 1strategy 1instruction-layer 1strategy-docs 1ia-audit
1folder-contract Судит право слоя и отдаёт handoff: text, skill, graph/runtime, validator, checkpoint.
1strategy Работает до исполнения, когда есть реальная развилка подхода, цена или риск.
1instruction-layer Владеет wording/placement инструкционной прозы, но не runtime-механизмом.
1strategy-docs Держит GOAL, README и roadmap shape, не превращая их в rulebook.

Work engines

Этот слой делает работу в выбранном owner-е. Он должен быть узким: найти, прочитать, проверить graph, обновить skill, собрать repo map, сделать CLI-confirmation.

1md-navigator 1md-reader 1md-graph 1skill-architect 1cli-tools 1repo-map
Markdown trio Search-first, bounded reading, then graph safety. Ни один из трёх сам по себе не даёт semantic verdict.
1skill-architect Владеет skill contract: trigger, body, references, scripts, assets, validation.
1cli-tools Нужен, когда догадка должна стать CLI-evidence: links, rename, symbols, diagnostics, dependency drift.
1repo-map Быстрая структурная ориентация по незнакомому codebase, не Markdown search.

Output surfaces

Этот слой делает видимый артефакт. Важно: output не становится canonical truth. HTML-страница помогает увидеть систему, но не заменяет SKILL.md.

html html-plan html-diagram 1obsidian 1mermaid pdf
html Универсальный self-contained report/explainer/prototype/deck. Много текста, структура и интерактивность допустимы.
html-diagram Когда главный результат - визуальная архитектура, SVG-сцена и быстрый spatial understanding.
html-plan Когда нужен прагматичный план, близкий к исходному тексту, без раздувания.
1obsidian / 1mermaid Работают для Obsidian UX и Mermaid-safe схем, не для любого HTML-output.

Verification and critics

Этот слой не должен превращаться в ритуал. Он включается, когда нужна независимая проверка, browser evidence, memory freshness или очень строгий review.

1fresh-eyes playwright screenshot-design claude-mcp gemini-mcp supermemory-*
1fresh-eyes Не ordinary closeout, а critic loop, когда правка задела несколько профессий или нужен внешний взгляд.
playwright Живой browser check: console, layout, clicks, screenshots, local file or localhost.
memory route Ускоряет старт, но drift-prone claims проверяются по live files и tools.
claude/gemini bridges Внешние peers для observable review, не замена main-thread verdict.

Handoff-таблица

Типичный сбой agents - делать работу в соседнем owner-е. Эта таблица показывает, где должен быть следующий шаг.

Вопрос Первый owner Куда отдаёт
Куда положить правило? 1instruction-layer Если спор уже не про wording, а про право слоя, передаёт в 1folder-contract.
Кто владеет папкой или механизмом? 1folder-contract Выносит verdict и handoff: instruction, skill package, runtime, graph или strategic docs.
Где в Markdown уже есть смысл? 1md-navigator Находит targets; выбранные блоки отдаёт в 1md-reader, последствия в 1md-graph.
Как обновить skill? 1skill-architect Синхронизирует SKILL.md, references/scripts/assets и validation baseline.
Нужен понятный HTML-рассказ? html Делает self-contained explainer. Если нужно именно full-screen SVG, это уже html-diagram.
Нужна независимая проверка? 1fresh-eyes Выбирает critic lens и возвращает finding plus alternative; final verdict остаётся в main thread.

Границы, которые держат систему

Эти границы важнее красивой карты. Они защищают будущую сессию от расползания правил.

1folder-contract против 1instruction-layer самый важный split

1instruction-layer спрашивает: “как написать правило так, чтобы его правильно поняли?”. 1folder-contract спрашивает: “должен ли именно этот слой владеть правилом, и какой механизм реально подтолкнёт агента к цели?”.

Markdown skills не должны давать semantic verdict evidence, not truth

1md-navigator, 1md-reader и 1md-graph дают evidence: targets, related blocks, cycles, anchors, impact. Но owner/canon closure остаётся ручным смысловым решением.

HTML skills не становятся source of truth artifact layer

HTML удобен для понимания, сравнения и передачи состояния. Но если HTML говорит одно, а живой SKILL.md другое, выигрывает SKILL.md. Артефакт можно пересобрать, контракт нельзя угадывать.

Memory ускоряет, но не доказывает freshness gate

Memory помогает быстро вспомнить прошлую развилку. Но runtime-sensitive claims проверяются по текущему config.toml, hook scripts, installed skills, local owner files и живым командам.

Что здесь делает обычный html skill

В этом запросе правильный output - не диаграмма. Ты попросил “рассказать через HTML”, поэтому задача похожа на feature/concept explainer.

Что html делает

Собирает один самодостаточный файл с prose, navigation, tabs, details, tables, dark mode и apply-before-paint theme script. Его цель - объяснить систему так, чтобы её можно было открыть и читать.

Что html не делает

Не решает owner спор, не валидирует skill package, не обновляет canon и не рисует full-screen architecture SVG. Для этого есть другие skills.

Почему не html-diagram

html-diagram хорош, когда надо “увидеть связи”. Здесь важнее “понять правила включения, handoff и ограничения”. Поэтому текстовая структура сильнее.

Как проверить output

Открыть файл в браузере, проверить console, responsive layout, theme toggle и интерактивные tabs/details. Если текст расходится с живым skill, править не HTML в одиночку, а owner-source.
