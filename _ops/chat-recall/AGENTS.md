# chat-recall: Руда И Слой Тем

Один контейнер, два слоя одного знания:

- `raw/` — руда: дословные source-bound выдержки слов владельца, файл на
  разговор;
- `topics/` — то же знание, разложенное по предметам: один предмет — один файл,
  имена работают оглавлением, отдельного указателя нет.

Правда живёт в `raw/`. Слой тем производный: итог, собранный из реплик агентами
по протоколу `quotes-to-topics`. Папки разделены не случайно: у руды и её
пересказа разные контракты, и смешение затянуло бы каждую под правила другой.

## Два Маршрута Чтения

**За позицией владельца по предмету — сперва `topics/`.** Слепая приёмка
2026-08-24 сравнила четыре маршрута к одному знанию на пятнадцати вопросах:
слой тем дал 12 верных ответов при 0 уверенно-неверных и одном файле на вопрос;
штатный поиск по руде — те же 12, но по три файла и с одним уверенно-неверным.

**За доказательством, хронологией и проверкой отмены — `raw/`** через
`chat_digest.py` скила `1chat-recall`. Он же — маршрут, когда предмет не
покрыт ни одной темой или вопрос свежее слоя.

### Якоря и применение

**Якорь `2026-08-09-203500-claude-39f062f3.md#L16` — это файл
`raw/2026-08-09-203500-claude-39f062f3.md`, строка 16.** Каждый пункт темы
несёт такой якорь, и он единственный способ вернуться к словам владельца.

Доказательством позиции остаётся реплика, а не пункт темы. Слой обзорный: он
показывает итог без даты и без того, что владелец позже отменил. Поэтому
применение позиции — два шага, и второй пропускать нельзя:

1. открой якорь и прочитай реплику целиком в её разговоре;
2. проверь, не отменило ли её что-то более позднее — тем же запросом с
   `--since <дата реплики>` через `chat_digest.py`.

Насколько слой отстаёт от руды, написано в `topics/horizon.json`. Процент
покрытия `check_coverage.py` читай вместе с горизонтом: проверка судит только
снимок сборки и по построению не может провалиться на записях новее.

## Контракт raw/

Файл на разговор
`<дата>-<время самой ранней сохранённой цитаты>-<агент>-<session8>.md`, строка
на реплику с полным timezone-aware source timestamp и классификацией
`type: … | topic: …`. Шапка файла — его инвентарь: `types`/`topics` для
сканирования без чтения тела, `session` — ключ к полному транскрипту разговора,
пока его не удалил retention.

Темы записей — имена файлов `topics/`: тема цитаты и файл слоя называют один
предмет, и оба маршрута чтения сходятся в одной точке. `--list-metadata` скила
`1chat-recall` печатает их с частотами. Новая тема рождается только когда
предмет не помещается ни в один существующий файл темы — и тогда
`--new-topic "<граница>"` заводит маленький файл темы вместе с записью;
наполняет его обычное обновление слоя.

Статус файлов разговоров: датированное сырьё, не текущая правда. Сказанное
могло быть позже молча отменено, поэтому цитата не применяется без проверки
scope и более свежего owner-а.

Кто и зачем сюда ходит (замер 79 сессий, 2026-08-12). В рабочих проектах 56%
чтений — агент по своей инициативе закрывает пробел текущей задачи, и 16 из 19
таких находок не существуют нигде в нормативных файлах: оперативные сроки,
коррекции и границы по жанру не попадают в `GOAL.md` и `AGENTS.md`. Типовой
читатель — read-only субагент из свежего окна (goal-lens, premortem, критик):
у него нет истории чата, и корпус — единственный канал к намерению владельца.
Второй канал — harvest (повторяющиеся коррекции → правка инструкций). Явной
команды владельца «найди мои слова» за 79 сессий не было ни разу.

Корпус систематически свежее нормативных файлов и может им прямо противоречить.
Нашёл расхождение — не решай его молча: строкой в `_ops/findings` с адресами
обоих источников, иначе следующая сессия разбирает то же заново.

Свежую реплику `1chat-recall` пишет в том же ходе. Цитату, восстановленную из
старого хода этого же разговора, он пишет с timestamp исходной transcript
record, никогда с часами запуска helper-а. `source-timestamp` — самый точный,
доступный агенту сейчас: exact ISO с таймзоной, минута из транскрипта или дата
дня; `unknown` — только для repair `--kind note`. Дата не угадывается.
Session-файл с legacy approximate-строкой писатель дописывает как есть: старые
грязные строки не переписываются, новая запись пишется чисто.

Сохраняются решение, коррекция, red line, предпочтение, критерий, важное число,
сырая идея на будущее и durable-хвост императива. Выдержка строится
преимущественно удалением речевого шума, повторов, разовой команды и
вставленного чужого материала; сохраняет лексику, смысл, условия и числа
владельца без интерпретации агента. Чужой вставленный текст не попадает;
сохраняется только явно выраженное отношение владельца к нему. Каждый разговор
пишет только свой файл и только про то, что в нём прозвучало; без session id
скрипт отказывает — общий файл смешал бы разговоры.

Ограничения метаданных: `model`, если присутствует, — точно известная resolved
модель, создавшая файл (разговор мог продолжиться другой моделью); `date` —
локальный день самой ранней сохранённой source-цитаты. Если позже добавлена
более старая цитата, helper переименовывает этот же session-файл и обновляет
`date`/заголовок; текст уже сохранённых цитат не меняет.

Текст записей не редактировать. Превращение выдержки в правило `AGENTS.md` /
`CLAUDE.md` или decision `GOAL.md` — отдельный manual проход.

Предшественник — `../user-said/`, заморожен (записи по 2026-05-28).

## Как Обновлять topics/

Руда растёт каждый день, слой — нет. Обновление здесь единственная постоянная
работа: догонять, а не пересобирать. Полная пересборка заберёт новое, но
перепишет больше тысячи уже проверенных фактов — это дорого и не нужно.

Механика лежит не здесь, а в мастерской:
`experiments/openviking-chat-recall/` — `scripts/` и `RUNBOOK.md`. **Все команды
ниже запускаются из корня репозитория** и полными путями: скрипты внутри себя
адресуют `_ops/...` от корня, из папки эксперимента они не найдут корпус.

```bash
python3 experiments/openviking-chat-recall/scripts/build_update_tasks.py _workspace/ox-update/tasks
```

Билдер сам считает дельту: адреса руды, которых нет ни в одном файле темы.

**Задание, чей прогон уже принят, повторно не запускай** — волна пишет поверх,
и готовый ответ пропадает. Поэтому вторая и любая следующая волна идёт не по
исходной папке заданий, а по папке повтора, которую собирает сверка:

```bash
python3 experiments/openviking-chat-recall/scripts/wave.py \
  _workspace/ox-update/tasks _workspace/ox-update/runs --pending _workspace/ox-update/pending
```

Она возвращает ненулевой код, пока разница не пуста, и кладёт в `--pending`
только непринятые задания. Дальше `TASKS=` указывает на неё, а `OUT=` остаётся
прежним — принятые ответы лежат там и не трогаются.

Дальше волна агентов, и запускается она **только фоном**: прогон Ox идёт от
минут до часов, а форграундный вызов вешает сессию. Это правило волн Ox вообще,
не особенность этого конвейера — его владелец `1hermes`:

```bash
TASKS=_workspace/ox-update/tasks OUT=_workspace/ox-update/runs PAR=8 RETRIES=5 MODE=read CWD="$PWD" nohup bash experiments/hermes-ox-alpha/ox_wave.sh > _workspace/ox-update/wave.log 2>&1 &
```

Затем результат кладёт скрипт, а не модель:

```bash
python3 experiments/openviking-chat-recall/scripts/apply_update.py --dry _workspace/ox-update/runs
python3 experiments/openviking-chat-recall/scripts/apply_update.py _workspace/ox-update/runs
```

`--dry` печатает баланс — сколько записей было в дельте и сколько покрыто
новыми пунктами. Это единственное место, где инвариант «ничего не исчезает
молча» становится числом; расхождение разбирают до вливания, не после.

`apply_update.py` называет разговоры, которых нет ни в одной теме, и
пропускает их: дописывать пункт некуда. Им тему назначает отдельная стадия,
и без неё обновление не закончено:

```bash
python3 experiments/openviking-chat-recall/scripts/build_assign_tasks.py _workspace/ox-assign/tasks
# волна тем же способом, OUT=_workspace/ox-assign/runs
python3 experiments/openviking-chat-recall/scripts/apply_assign.py --dry _workspace/ox-assign/runs
python3 experiments/openviking-chat-recall/scripts/apply_assign.py _workspace/ox-assign/runs
```

Прогон назначения вправе предложить новую тему, если предмет не влезает ни в
одну границу; вручную новую тему в `topics/` не заводят.

После назначения записи этих разговоров всё ещё не влиты, и дельту надо считать
заново. Это не противоречит запрету выше: `build_update_tasks.py` строит задания
в **новую** папку (`ox-update2/tasks`), волна пишет в новую папку прогонов, а
прежние принятые ответы остаются нетронутыми. Запрет касается перезапуска поверх
готового прогона, а не повторного круга по новой дельте.

Закрывают обновление две команды:

```bash
python3 experiments/openviking-chat-recall/scripts/reanchor.py fix
python3 experiments/openviking-chat-recall/scripts/reanchor.py map
python3 experiments/openviking-chat-recall/scripts/check_coverage.py
```

`fix` переставляет якоря, разъехавшиеся из-за роста файлов разговоров, по
отпечаткам строк; `map` заводит отпечатки для новых якорей, иначе следующий
`fix` их не найдёт. Любое другое слово команды скрипт отвергает.

Горизонт сдвигает команда, а не рука:

```bash
python3 experiments/openviking-chat-recall/scripts/set_horizon.py
```

Она пересчитывает `topics/horizon.json` из тех же файлов, что и всё остальное.
Слой, знающий меньше обещанного, врёт читателю уверенно.

## Бортики

- **Файл темы руками не правь.** Он собран прогоном из реплик и держит баланс
  якорей: сколько адресов вошло, столько обязано стоять в тексте. Дописанный
  руками пункт не исчезнет сам — `apply_update.py` только дописывает блок в
  конец, — и именно поэтому он опаснее: останется навсегда пунктом без
  происхождения, который читатель примет за собранный из реплики. Ошибку в
  пункте чини прогоном (`build_repair_tasks.py`), а не текстом.
- **Разговор без темы пропускается, а не угадывается.** `apply_update.py`
  назовёт такие файлы. Тему им назначает отдельный прогон по существующим
  темам. Легитимных создателей файла темы два: прогон назначения и
  `--new-topic` скила `1chat-recall` при записи цитаты; руками файл темы не
  заводят.
- **Модель не пишет в дерево.** Волна идёт `MODE=read`, результат кладёт
  `apply_*.py`. Причина: замер 2026-08-22, где модель при верном тексте испортила
  четыре файла служебной логикой.
