# Слой Тем: Как Читать И Как Обновлять

Сорок файлов — то же знание, что в соседней `../chat-recall/`, но разложенное
по предметам. Один предмет — один файл, имена работают оглавлением, отдельного
указателя нет.

Слой производный. Правда живёт в `../chat-recall/` — дословных репликах
владельца. Здесь итог, собранный из них агентами по протоколу
`quotes-to-topics`. Папка отдельная, а не подпапка корпуса: у руды и её
пересказа разные контракты, и смешение затягивало бы каждую под правила другой.

## Зачем Он Есть

Слепая приёмка 2026-08-24 сравнила четыре маршрута к одному знанию на
пятнадцати вопросах: слой тем дал 12 верных ответов при 0 уверенно-неверных и
одном файле на вопрос. Штатный поиск и голая папка — те же 12, но по три файла
и с одним уверенно-неверным. Поэтому маршрут по умолчанию — сюда.

## Как Читать

**Якорь `2026-08-09-203500-claude-39f062f3.md#L16` — это файл
`../chat-recall/2026-08-09-203500-claude-39f062f3.md`, строка 16.** Каждый пункт
темы несёт такой якорь, и он единственный способ вернуться к словам владельца.

**Доказательством позиции остаётся реплика, а не пункт темы.** Слой обзорный:
он показывает итог без даты и без того, что владелец позже отменил. Пункт
говорит, где смотреть; что именно и когда владелец сказал, говорит только
файл по якорю.

Поэтому применение позиции — два шага, и второй пропускать нельзя:

1. открой якорь и прочитай реплику целиком в её разговоре;
2. проверь, не отменило ли её что-то более позднее — тем же запросом с
   `--since <дата реплики>` через `chat_digest.py` скила `1chat-recall`.

Слой не знает ни дат, ни отмен: он показывает итог, а не хронологию. Пункт,
применённый без второго шага, — это позиция без доказательства, что она ещё
действует. Насколько слой отстаёт от корпуса, написано в `horizon.json`.

## Как Обновлять

Корпус растёт каждый день, слой — нет. Обновление здесь единственная постоянная
работа: догонять, а не пересобирать. Полная пересборка заберёт новое, но
перепишет больше тысячи уже проверенных фактов — это дорого и не нужно.

Механика лежит не здесь, а в мастерской:
`experiments/openviking-chat-recall/` — `scripts/` и `RUNBOOK.md`. **Все команды
ниже запускаются из корня репозитория** и полными путями: скрипты внутри себя
адресуют `_ops/...` от корня, из папки эксперимента они не найдут корпус.

```bash
python3 experiments/openviking-chat-recall/scripts/build_update_tasks.py _workspace/ox-update/tasks
```

Билдер сам считает дельту: адреса корпуса, которых нет ни в одном файле темы.
Задание, чей прогон уже принят, не перезапускай — повтор затирает готовый ответ.
Сверка `scripts/wave.py <задания> <прогоны>` возвращает ненулевой код, пока
разница не пуста; она **называет** непринятые, но папку для повтора не собирает —
собери её сам из названных и волну пусти по ней.

Дальше волна агентов, и запускается она **только фоном**: прогон Ox идёт от
минут до часов, а форграундный вызов вешает сессию. Это правило волн Ox вообще,
не особенность этого конвейера — его владелец `1hermes`:

```bash
TASKS=_workspace/ox-update/tasks OUT=_workspace/ox-update/runs PAR=8 RETRIES=5 MODE=read CWD="$PWD" nohup bash experiments/hermes-ox-alpha/ox_wave.sh > _workspace/ox-update/wave.log 2>&1 &
```

Затем результат кладёт скрипт, а не модель:

```bash
python3 experiments/openviking-chat-recall/scripts/apply_update.py --dry _workspace/ox-update/runs
python3 experiments/openviking-chat-recall/scripts/apply_update.py _workspace/ox-update/runs
```

`--dry` печатает баланс — сколько записей было в дельте и сколько покрыто
новыми пунктами. Это единственное место, где инвариант «ничего не исчезает
молча» становится числом; расхождение разбирают до вливания, не после.

`apply_update.py` называет разговоры, которых нет ни в одной теме, и
пропускает их: дописывать пункт некуда. Им тему назначает отдельная стадия,
и без неё обновление не закончено:

```bash
python3 experiments/openviking-chat-recall/scripts/build_assign_tasks.py _workspace/ox-assign/tasks
# волна тем же способом, OUT=_workspace/ox-assign/runs
python3 experiments/openviking-chat-recall/scripts/apply_assign.py --dry _workspace/ox-assign/runs
python3 experiments/openviking-chat-recall/scripts/apply_assign.py _workspace/ox-assign/runs
```

Прогон назначения вправе предложить сорок первую тему, если предмет не влезает
ни в одну границу; вручную новую тему не заводят. После назначения повтори
`build_update_tasks.py` и волну: записи этих разговоров ещё не влиты.

Закрывают обновление две команды:

```bash
python3 experiments/openviking-chat-recall/scripts/reanchor.py fix
python3 experiments/openviking-chat-recall/scripts/reanchor.py map
python3 experiments/openviking-chat-recall/scripts/check_coverage.py
```

`fix` переставляет якоря, разъехавшиеся из-за роста файлов разговоров, по
отпечаткам строк; `map` заводит отпечатки для новых якорей, иначе следующий
`fix` их не найдёт. Любое другое слово команды скрипт отвергает.

После вливания сдвинь дату и счёт в `horizon.json` рядом с темами. Слой,
знающий больше, чем обещает горизонт, врёт в другую сторону.

## Бортики

- **Файл темы руками не правь.** Он собран прогоном из реплик и держит баланс
  якорей: сколько адресов вошло, столько обязано стоять в тексте. Дописанный
  руками пункт не исчезнет сам — `apply_update.py` только дописывает блок в
  конец, — и именно поэтому он опаснее: останется навсегда пунктом без
  происхождения, который читатель примет за собранный из реплики. Ошибку в
  пункте чини прогоном (`build_repair_tasks.py`), а не текстом.
- **Процент покрытия читай вместе с горизонтом.** `check_coverage.py` судит
  только снимок сборки и по построению не может провалиться на записях новее.
  Последние строки его вывода печатают, сколько записей слой не видел никогда;
  без них процент врёт.
- **Разговор без темы пропускается, а не угадывается.** `apply_update.py`
  назовёт такие файлы. Тему им назначает отдельный прогон по существующим сорока
  темам — не заводи новую тему в обход этого.
- **Модель не пишет в дерево.** Волна идёт `MODE=read`, результат кладёт
  `apply_*.py`. Причина: замер 2026-08-22, где модель при верном тексте испортила
  четыре файла служебной логикой.
