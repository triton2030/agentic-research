# Git Backup Workflow Criteria

## Зона ответственности

Когда работа касается `git status`, cleanup перед коммитом, staging, commit,
push, GitHub, remote, веток или pull request.

## Цель

GitHub должен работать как облачный бэкап локальной правды, без лишней
командной ceremony вокруг веток и pull request.

## Критерии

Rule: Локальный `main` считать source of truth, а GitHub — backup, если пользователь явно не попросил ветку, pull request или командный workflow.
Why: Пользователь прямо сказал, что GitHub для него просто бэкап с компьютера в облако, он не пользуется ветками и не ожидает чужой работы в репо.

Rule: Для push-запросов по умолчанию коммитить и пушить текущий `main` в `origin/main`, не создавая ветки, draft PR или pull request.
Why: Branch/PR flow добавляет лишний слой к задаче, где пользователь просит просто отразить локальное состояние в облаке.

Rule: Перед push проверять `git status`, очевидный локальный мусор и проверки, соразмерные изменённым файлам.
Why: Backup-flow всё ещё должен не отправлять случайные артефакты или заведомо битое состояние, но не должен превращаться в командный release-process.

Rule: Грязное git-дерево само по себе не считать блокером: если задача требует править файлы с уже существующими локальными изменениями, работать с текущим содержимым и проверять diff только по смыслу задачи.
Why: Пользователь прямо сказал, что в этом проекте не бывает "чужих правок": есть только его изменения и изменения агента, а грязный git часто становится лишним блокером.

Rule: Если пользователь просит “запушить всё”, после cleanup staging должен забирать все intended изменения репо; исключённые файлы нужно назвать явно.
Why: В этой модели “всё” означает синхронизацию локальной правды с облачным бэкапом, а не аккуратную нарезку изменений под review.
