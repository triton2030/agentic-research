# INTERVIEW

## Тон И Выход

- 2026-04-22 · Писать как можно короче.
- 2026-04-22 · По умолчанию писать только запрошенное, без лишних разделов и пояснений.
- 2026-04-22 · Не выдумывать факты; отделять факты от гипотез.
- 2026-04-22 · Для бизнесовых и стратегических текстов говорить человеческим деловым языком, не языком разработки.
- 2026-04-22 · В конце анализа owner-chain скилла — короткое резюме простым русским языком: что из `_ops/` помнить дальше по работе.

## Repo Shape И Routing

- 2026-04-22 · Живые `SKILL.md` считать load-bearing truth layer для skill-owned поведения.
- 2026-04-22 · `AGENTS.md` и корневые инструкции должны задавать routing и placement rules, а не дублировать skill bodies.
- 2026-04-22 · Перед нетривиальной работой сначала читать релевантный `knowledge/wisdom-*.md`; если неясно, начинать с `knowledge/wisdom-agents.md`.
- 2026-04-22 · Общие выводы класть в `knowledge/`, project artifacts - в `projects/{category}/{name}--{type}-{platform}/`.
- 2026-04-22 · Для новых control surfaces по умолчанию предпочитать `skill`, а не отдельный `agent`, если agent-shaped artifact не запрошен явно.
- 2026-04-27 · `_ops/PROJECT-ROADMAP.md` должен показывать верхнеуровневый путь от абсолютного нуля до конца: Goal, Approach, Stages и Anti-goals. Задачи — второй уровень в task-файлах, Подшаги внутри task-файлов — третий уровень. Запрет на детализацию касается task-level Steps, commands, criteria и evidence, а не полного стратегического маршрута.

## Минимальный След

- 2026-04-22 · Новые файлы не создавать по умолчанию; сначала обновлять существующий правильный файл.
- 2026-04-22 · Side-docs, summaries, handoff notes и дополнительные explainers без явного запроса не создавать.
- 2026-04-25 · Не раскрывать task/subtask/criteria заранее глубже необходимого: фиксировать минимальный next frontier, а новые детали, критерии и уровни декомпозиции добавлять только as-needed, когда без них нельзя выполнить или проверить следующий ход.
- 2026-04-22 · `_ops/` не использовать как общий склад заметок, backlog и случайных планов.
- 2026-04-22 · Имена обычных файлов и проектных папок держать в `kebab-case`.

## Рабочий Режим

- 2026-04-22 · Skills использовать как routing, не как preload.
- 2026-04-27 · Для бизнесовых, желательных и результатных запросов вести себя как экспертный сооснователь: сначала понять цель, не принимать предложенный способ как готовую задачу, сомневаться в формулировке, раскрывать технические и продуктовые развилки, цену вариантов, дешёвые альтернативы и scope tradeoffs; к плану переходить только после выбора способа реализации. Для простого — один короткий раунд вопросов, для сложного — итеративное обсуждение.
- 2026-04-27 · При обсуждении solution-shaping протокола не выводить новую цель из последнего сообщения отдельно от исходной идеи: держать фокус на главном протоколе послойного раскрытия развилок. Не цементировать его как роль технического директора; это гибкая экспертная рамка для пользователя, который может не знать, какие вопросы нужно задать. Считать это не одноразовым intake, а повторяющимся циклом по ходу проекта, где реальность постоянно открывает новые развилки. Проектировать как глобально установленный переносимый skill, а не как локальный костыль текущего репо; соседние owner-skills должны знать, когда отдавать ему сырой intent, новую реальность или нерешённую развилку.
- 2026-04-27 · В разговорных скиллах жёсткие начальные фразы могут быть role/voice anchor, а не протоколом ответа; если пользователь ценит такой старт, сохранять его и не заменять на поля, разделы или чеклист.
- 2026-04-27 · `step-back` должен быть когнитивно-психологическим и гибким: усиливать живое распознавание ошибок мышления, а не превращаться в стратегический фреймворк, planner или классификатор слоёв.
- 2026-04-22 · Для существенной repo-level работы owner-chain по умолчанию: `before-work` -> нужный owner-skill -> execution -> `work-review`.
- 2026-04-24 · `step-back` использовать только для dialog-time framing, а не как постоянный repo owner; прежнее слово `ops` в этом смысле считать устаревшим алиасом.
- 2026-04-27 · `INTERVIEW.md` должен быть живым input/output loop: `user-truth` сохраняет устойчивые предпочтения и ограничения, а downstream skills применяют релевантные строки в scope, routing, Must-not или verification depth.
- 2026-04-27 · `strategy-discussion` должен забирать domain clarification внутрь обсуждения: задавать только consequential questions, где каждый вопрос объясняет, какое решение меняется, почему это важно и какой будущий риск снимается.
- 2026-04-25 · Moment-skills должны освежать контекст в момент действия: `before-work` на старт работы, `before-write` перед substantive Edit/Write, `work-review` перед финальным «готово».
- 2026-04-25 · `task-contract` должен создавать empty task skeletons на фазу, но детализировать Подшаги / criteria / evidence / verification только для текущей задачи.
- 2026-04-25 · Советовать subagents, когда они реально ускоряют независимое evidence/review/validation или disjoint implementation; blocking step, hotspot files и final integration оставлять в main context.
- 2026-04-25 · К проверкам относиться осторожно: не удлинять задачу лишней validation-петлёй; запускать только проверки, которые прямо закрывают критерий, риск или изменённый surface.
- 2026-04-24 · `project-roadmap` должен сверять PROJECT-ROADMAP с реальностью: использовать историю чата, git diff/history и фактически закрытые task-файлы как evidence для синхронизации стратегии и execution layer.
- 2026-04-24 · `brooks` нужен не как code-only reviewer, а как structural critic целой системы: документы, картинки, бизнес-планы, instructions, repo-shape и их связность; downstream-скиллы должны только роутить к нему, не переписывать его роль.
- 2026-04-22 · Task criteria работают как primer + check, не как hard gate; нарушения Must эскалируются обратно вверх по owner-chain, но ход не останавливается на входе.
- 2026-04-22 · `instruction-layer` должен управлять agent instruction layer так, чтобы он защищал горячий `_ops`-контур `project-roadmap`; `_ops/PROJECT-ROADMAP.md`, `_ops/INTERVIEW.md` и `_ops/learnings.md` надо пересинхронизировать почти после каждого значимого изменения.
