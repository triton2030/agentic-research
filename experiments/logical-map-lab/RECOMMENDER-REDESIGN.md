# Контекст: превратить logical-map-lab в рекомендатель изменений бизнес-решений

> Читать вместе с рабочим прототипом операции: `../profit-forecast/forecast.py`
> и `../profit-forecast/nodes.csv` — там уже есть карта→вероятность→рычаги, которую
> этот UI должен потреблять, а не переизобретать.

## Суть изменения в одну фразу

Сейчас система **показывает** причинную карту, извлечённую из канона. Она должна
**рекомендовать изменения бизнес-решений** (аудитория, цена, модель монетизации,
рынок, функционал), которые честно поднимают **вероятность прибыльности**. Из
датчика — в оптимизатор пространства решений.

## Ключевой концепт (без него всё остальное не имеет смысла)

Вероятность прибыльности можно честно поднимать, **меняя сами решения**, ещё до
всякого пилота. Это дизайн, не подделка. Пример на нашей же модели:

- «продавать систему владельцам собак без печатных студий» → некому платить (Z3),
  некому печатать (Z6), нет трафика студий (Z2) → **Y_pilot ≈ 0%**;
- «продавать студиям, которые печатают» → те же звенья существуют → **Y_pilot 6%**.

Смена ОДНОГО решения (аудитория) подняла цифру честно. Система должна перебирать
такие изменения и рекомендовать те, что поднимают fitness = вероятность.

**Владелец не читает канон.** Он смотрит на набор цифр по критериям и одобряет
рекомендации-направления; агенты меняют канон по одобренному; цифра растёт.

## Замок, без которого всё превращается в Goodhart (встроить ПЕРВЫМ)

Есть два способа «поднять цифру», и один — катастрофа:

- ✅ **изменить РЕШЕНИЕ** (аудитория студии→X, модель сбор→подписка, рынок→Y) —
  честно, это другой бизнес с другими шансами;
- ❌ **переписать ОПИСАНИЕ** того же решения убедительнее — фикция, цифра растёт
  без реальности. Это исходная болезнь системы.

Замок: **цифру двигает только (а) смена решения в конфигурации, либо (б) рост
`source_strength` от реального замера — НИКОГДА не правка прозы канона.** Приор
`self_canon` даёт широкий потолок, который не сужается от красноречия. Рекомендация
всегда указывает изменение РЕШЕНИЯ или РЕАЛЬНЫЙ замер, не переформулировку.

## Что конкретно изменить

### 1. Развернуть операцию: цель → канон, не канон → карта

`README.md:13` задаёт pipeline `business prose → extracted claims → typed nodes`.
Это инверсия. Надо: **карта цели строится от дисциплины/owner (`Ставка_MAVO.md`,
9 звеньев), независимо от канона**, затем канон сверяется с ней. Появляются
**красные узлы-дыры** там, где цель требует звена, а канон молчит (Kaspi!). Сейчас
таких узлов нет — все 15 заякорены в канон, поэтому карта наследует его слепые
пятна.

### 2. Модель узла (`src/maps/types.js`, данные в `src/maps/pages/*.json`)

Убрать `confidence` — он смешивает три несовместимых смысла и берётся из воздуха
(`Inspector.jsx:136` рисует его процентом, читается как «риск покрыт»). Заменить на
поля из `profit-forecast/nodes.csv`:

- `requirement_source` — откуда узел: `discipline` / `owner` / `external`. LLM-узел
  без источника = кандидат, не карта цели (иначе снова пересказ канона);
- `gate_role` — `hard_gate` / `soft_gate` / `contributor` / `long_horizon`;
- `group` — `pilot` / `unit` / `scale` (три разных вопроса, не один общий скор);
- `source_strength` — `self_canon`→`observed_reality` (переиспользовать из
  `../prose-audit-lab/schemas/source-strength.md`, не новый словарь);
- `p_low` / `p_base` / `p_high` — приор с интервалом; ширина = сила опоры;
- `kill_criterion`, `lever_evidence`, `evidence_stage` (`pre_pilot`/`pilot`/`post_pilot`).

### 3. Слой конфигураций — НОВОЕ, это ядро оптимизатора

Ввести объект **конфигурация** = набор бизнес-решений:
`{ аудитория, продукт, кому_продаём, модель_монетизации, рынок, функционал }`.
Каждая конфигурация **активирует своё подмножество узлов с своими приорами** →
даёт свою вероятность. Одна карта цели, много конфигураций поверх неё.

Комментарий: именно это делает систему оптимизатором, а не датчиком. Собаки vs
студии — это две конфигурации, активирующие разные звенья карты.

### 4. Движок рекомендаций — НОВОЕ

Агенты-дизайнеры **мутируют конфигурацию** (сменить сегмент, модель, рынок) →
пересчёт вероятности через `forecast`-логику → рекомендация вида:
`смени решение X на Y: Y_pilot 6% → N%, потому что <звенья, которые ожили/умерли>`.
Beam/эволюционный поиск по пространству решений, сходимость к максимуму fitness.

### 5. Замки честности fitness (обязательно, иначе оптимизатор убежит в фантазию)

Без них система найдёт не лучший бизнес, а самый льстивый на бумаге («продавать
всем всё дорого» — все звенья «высокие», если некому возразить):

- **challenger на каждой конфигурации** — что уронит именно этот дизайн (Kaspi для
  студий, отсутствие печати для собак). Defeater — first-class узел/ребро, не абзац;
- **привязка звеньев к base rates**, не к оптимизму агента;
- конфигурация на голом `self_canon`-оптимизме несёт **широкий интервал** → не может
  обогнать заякоренную (честный tie-break: при равной базе выигрывает бо́льшая опора).

### 6. Выход владельцу (не карта для чтения)

- три числа по текущей конфигурации: `Y_pilot` / `Y_unit` / `Y_scale` + интервалы;
- **топ рекомендаций смены решений**, ранжированные по подъёму вероятности, каждая
  с «почему» и audit-diff (что реально изменилось);
- kill-gate статус ведёт **прежде** скаляра;
- галочка владельца: одобрить направление / отклонить.

### 7. Порядок и переиспользование

- **Операция сначала вне React.** Прототип уже есть: `../profit-forecast/forecast.py`
  (детерминированный, аудируемый). UI впитывает его выход как read-only вид —
  **после** того как операция устоялась. Не строить React-машину поверх
  неопределённой операции.
- **Реальность — в конце, сфокусированно.** Структурный поиск сужает пространство до
  1–2 лучших конфигураций; пилот проверяет **финалиста**, не каждый шаг. Найденный
  оптимум — структурная гипотеза, не доказанный факт.
- **Переиспользовать из `prose-audit-lab`:** `source-strength` метки, challenger-роли,
  `check_run.py` (валидатор), правило «не усреднять вердикты».

## Что НЕ делать

- Не агрегировать вероятности в один общий скор (три вопроса — три числа).
- Не давать рекомендаций, меняющих формулировку канона без смены решения или
  реального замера (замок выше).
- Не строить Monte-Carlo/Bayesian-сеть до пилота — входов (V/A/B) нет, это ложная
  точность. Форма — произведение hard-gate × денежный слой, руками аудируемое.

## Критерий, что редизайн удался

Система рекомендует смену бизнес-решения; агент применяет её к канону; пересчёт
показывает **честный** подъём вероятности (звенья реально ожили/умерли, не проза
покрасивела); challenger не смог уронить новую конфигурацию сильнее старой; и
владелец может одобрить направление, **не прочитав ни строчки канона**.
