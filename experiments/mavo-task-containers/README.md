## Доменная модель

### Контейнер

Контейнер — держатель задач с **инвариантом пустоты**:

- обязателен и «висит всегда» — это не задача со сроком, а постоянное
  обязательство;
- **количество живых задач внутри = индикатор его здоровья**: чем больше,
  тем контейнер «хуже»;
- пустой контейнер = хорошо. «Контейнеры должны быть пустые — и только
  тогда можно запускаться»;
- контейнер порождает задачи двух родов: *починить* (что найдено) и
  *проверить* (аудиты, тестирующие инвариант). Пусто = все аудиты прошли
  и ничего не нашли.

Названные контейнеры-кандидаты:

| Контейнер | Инвариант, который он держит |
|---|---|
| Прибыльность бизнеса | аудиты прибыльности проходят, дыр нет |
| Фабрика шаблонов | конвейер шаблонов работает без ручных дыр |
| Фабрика товаров | конвейер товаров работает |
| Интерфейс: взгляд покупателя | UX покупателя не имеет известных проблем |
| Интерфейс: взгляд студии | UX студии не имеет известных проблем |

- У контейнеров есть **теги** — для фильтрации контейнеров между собой.
- Нужен **список контейнеров** и **дашборд здоровья**: одна страница,
  где видно все контейнеры и сколько в каждом живых задач.

> [!note] Контейнер = тег или узел? (открытый вопрос, есть мнение)
> Владелец в разговоре сам заметил: «контейнер — это по сути просто тег,
> имя проекта». Рабочее мнение агента: контейнер лучше держать **узлом**
> (`type: container`, задачи ссылаются на него через `parent`), а не тегом,
> потому что у контейнера есть своё тело (зачем он, что значит «пусто»,
> какие аудиты его проверяют) и свои теги. Тег такого не носит.
> Решение зафиксировать при старте схемы.

### Задача

- Живёт в контейнере (или в другой задаче — вложенность до 3 уровней).
- **Зависимости**: к задаче нельзя приступать, пока задачи из
  `depends_on` не завершены. `blocked` — не статус, а вычисляемое
  состояние.
- Задача-заглушка — легальное состояние: создана заранее («знаем, что
  будем делать»), детали появятся потом; комментарии могут заполняться
  раньше описания.

### Тело задачи — фиксированные разделы

Каждая задача — Markdown-файл с адресуемыми секциями:

1. **Зачем** — какую проблему решает, зачем существует.
2. **Описание** — что делать (у заглушки может быть пустым).
3. **Комментарии / заметки** — неутверждённые мысли, идеи, черновики;
   заполняются в любом порядке, часто раньше описания.
4. **Решения** — принятые решения и историческая информация, *почему*
   решение было принято.
5. **Ссылки** — на канон mavo-short и на источники за его пределами.

### Архивация

Выполненные задачи уходят в архив (отдельная папка `archive/` —
единственное легальное «расположение кодирует состояние»). Правила
переноса и что остаётся видимым в истории — решить при старте схемы.

## Схема хранения (синтез двух blind-советников, Codex GPT-5.6 × Claude)

Оба независимо сошлись:

- **Свой формат; Backlog.md — донор конвенций, не зависимость**
  (decimal-ID сцепляет идентичность с иерархией; кастомные поля не
  первоклассные; их UI — канбан и write-поверхность, отвергнут).
- Плоские файлы `T-0042 — slug.md`; **ID во frontmatter — истина**,
  имя файла — просто locator.
- `parent` — единственная правда иерархии (children вычисляются);
  `depends_on` — направленный список; `related_to` — ненаправленная связь.
- Закрытые словари статусов/тегов/полей в `config.yml`; свободный текст
  в enum-полях — главный failure mode LLM-писателей.
- `rank` разреженными числами (1000, 2000…) — ручной порядок с
  возможностью вставки между.
- **Валидатор (`taskctl check`) — сердце системы**: дубли ID, битые
  ссылки, циклы, глубина, enum-валидность. Прогон после каждой мутации
  агента (обязательный), pre-commit, fail-closed viewer. Advisory-lock
  на выдачу ID (две параллельные агентские сессии — реальность).

Эскиз frontmatter (не финал):

```yaml
schema: task/v1
id: T-0042
title: Доказать серверный рендер
type: task          # container | task | subtask
status: ready       # словарь в config.yml
parent: C-0003      # контейнер или задача
depends_on: [T-0031]
related_to: []
tags: [rendering]
rank: 2000
urls: []
created: 2026-07-12
updated: 2026-07-12
```

## Поверхность просмотра (UI-контракт владельца)

Канбан отвергнут (опыт Backlog.md-прототипа). Нужно как в ClickUp List view:

- **Левая вертикальная навигация** — имена контейнеров/проектов;
  клик → справа таблица его задач.
- **Таблицы — много и создаваемые**: разные сохранённые виды с разными
  фильтрами, группировками, тегами, сортировками (включая «по готовности»).
- **Раскрываемые подзадачи**: строки-родители по умолчанию свёрнуты,
  раскрываются в дереве прямо в таблице.
- **Дашборд здоровья контейнеров** — все контейнеры + счётчик живых задач.
- **Карта зависимостей** — визуальный граф: что от чего зависит и
  **к каким задачам можно приступить сейчас** (фронтир: все зависимости
  закрыты). Такого вида нет даже в ClickUp — одна из главных болей.
- **Просмотрщик Markdown**: тело задачи рендерится с его разделами
  красиво, это в том числе читалка md-файлов.

Технически (решено в обсуждении):

- Тонкий локальный веб-апп, **строго read-only** (сервер только GET).
- Стек из уже проверенных кубиков репо: Vite + React; таблица —
  TanStack Table (группировка, сортировка, раскрываемое дерево из
  коробки); граф зависимостей — React Flow + ELK (опыт
  `flowpage-v4-elk`); чтение файлов — паттерн
  `global-agent-surface-viewer` (express + fast-glob).
- Obsidian Bases — бесплатный бонус-слой поверх тех же файлов
  (мобильное чтение через vault-sync); прототип-разведка уже есть:
  `experiments/obsidian-base-board-mavo-snapshot/`.
