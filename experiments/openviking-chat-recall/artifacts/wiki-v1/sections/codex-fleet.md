# Codex-агенты: воркеры, советы и контроль прогонов

Как ставить задачи Codex-воркерам, делить роли флота, читать сводки продвижения, вмешиваться в долгий прогон, устраивать worktrees и персистентные треды, какие маршруты моделей штатные

- [В каком порядке перестраивались bridge, приложение долгих прогонов и тело скила?](../method/bridge-app-skill-body-order-of-work.md) — Заданный порядок работ: сначала мост, затем приложение про долгие прогоны, затем тело скила.
- [Где видно продвижение Codex-агентов?](../concept/codex-progress-visibility-via-desktop.md) — Треды больших работ видимы в Codex Desktop — он служит способом наблюдать прогресс; одиночные review и scout остаются эфемерными.
- [Как агент вмешивается в долгий прогон Codex?](../concept/intervening-in-a-long-codex-run.md) — Агент может отслеживать стадию долгого прогона, направлять Codex при уходе не туда и отправлять корректирующий комментарий после результата.
- [Как владелец делит работу между Codex-воркерами и что такое дефолт флота?](../concept/codex-fleet-defaults-and-worker-split.md) — Главный агент — оркестратор, анализ и разбор уходят Codex-агентам; дефолт флота учитывает стоимость worktrees: один воркер может вести большую задачу с субагентами, либо задачи делятся группами.
- [Как выглядит сводка прогресса Codex?](../concept/task-line-above-progress-summary.md) — Над сводкой прогресса исходное задание показывается одной строкой.
- [Как поделены роли Opus и Claude при рефакторинге Codex-моста?](../concept/opus-writes-claude-reviews.md) — Пишет Opus, Claude только проверяет его работу.
- [Как работает фоновый Codex-советник перед существенной работой?](../method/background-codex-advisor-before-substantial-work.md) — Перед существенной работой запускается фоновый Codex-советник: цель он получает независимо от выбранного подхода и параллельно предлагает собственный путь решения.
- [Как ставить задачу Codex-воркеру?](../concept/how-to-brief-a-codex-worker.md) — Воркеру задаётся желаемый результат без пошаговой опеки — он сам читает контекст и берёт skills; в 1codex усиливается обучающая часть о формулировке промптов и стиле заданий для движка.
- [Как устроено тело SKILL.md 1codex?](../method/skill-md-body-router-appendices.md) — Тело SKILL.md ужато втрое, роутер поднят наверх, дубли перенесены в приложения.
- [Как устроены worktrees и персистентные треды у ролей флота?](../method/worktree-and-persistent-thread-invariant.md) — Инвариант: worktree только для пишущего воркера, пишущий воркер всегда получает персистентный тред; reviewer/scout/researcher обходятся без того и другого, второй LLM-судья не заводится.
- [Какие маршруты моделей владелец держит штатными?](../concept/sol-xhigh-and-luna-standard-routes.md) — Уровни max и ultra не используются; штатно — sol+xhigh для всего и luna для простой большой работы.
- [Когда wave 1codex считается закрытой?](../method/wave-closure-receipt-in-fleet-md.md) — Wave закрыта только при квитанции в fleet.md с полями wave.cleanup_done, wave.kept_branches и wave.threads_archived; SKILL.md держит указатель на квитанцию, а не её копию.
- [Когда привлекать /1deep-agents при архитектурном разборе?](../concept/deep-agents-in-architecture-review.md) — При архитектурном разборе /1deep-agents учитывается в зависимости от цели.
- [Когда проблему скила решать инструкцией, а не кодом?](../concept/instruction-over-code-for-skill-problems.md) — Для скилов часть проблем проще закрыть инструкцией агенту, чем исправлять код.
- [Сколько хода Codex попадает в контекст оркестратора?](../concept/orchestrator-context-economy-on-codex-run.md) — Контекстное окно оркестратора не заполняется ходом Codex автоматически: происходящее читается только по запросу и в сжатом виде.
- [Чем выбирать на развилках технической работы?](../concept/product-frames-as-fork-selector.md) — Продуктовые рамки применяются как инструмент выбора на технических развилках, без отдельного продуктового обсуждения.
- [Чем мониторить Codex и откуда брать подсказки?](../concept/native-monitoring-over-docs-hints.md) — Мониторинг — нативный инструмент плюс возможности Claude; документация Claude рассматривается как возможный источник подсказок.
- [Чем подтверждать поведение Codex при расследовании?](../concept/codex-behavior-evidence-from-docs-and-github.md) — При расследовании поведения Codex обращаются к документации или GitHub, не полагаясь на один эмпирический опыт; официальная документация анализируется через интернет.
- [Что добавляет канал вмешательства в codex-bridge?](../method/codex-bridge-intervention-channel.md) — В codex-bridge добавляется вмешательство в идущий ход через ящик прогона и сторожа рядом с ходом — примерно 120 строк в codex_progress.py, без смены точки входа; надзор заменяется с двух ходов на четыре, одной репликой.
- [Что должно быть убрано после работы Codex-воркеров?](../method/cleanup-after-codex-workers.md) — Временные git worktrees и ветки после завершения работы воркеров убираются обязательно; контроль GitHub, worktrees и веток опирается на готовые инструменты, а не собственный код.
- [Что такое 1codex и зачем владелец его вызывает?](../entity/1codex-orchestrator-layer.md) — 1codex — оркестраторский слой над Codex: разведка, мнение умной модели, флот пишущих агентов, поиск, читающий review и вызов Codex в том числе как советника.
- [Что такое codex-bridge и как его меняют?](../entity/codex-bridge-and-its-rework.md) — codex-bridge правится сам, а не только текст skill: глубокий рефакторинг для поддерживаемости; код держит необратимые гарантии, агент — семантику diff и выбор маршрута; флаг приоритета, влияющий на скорость, убран.
