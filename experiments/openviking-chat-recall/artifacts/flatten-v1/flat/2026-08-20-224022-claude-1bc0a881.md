- Владелец решил жёстко встроить в `1html` протокол когнитивной работы и планирования, чтобы ни один артефакт не создавался до этой работы, а план обеспечивал использование нужных компонентов и стабильный дизайн без ошибок CSS и HTML. [L21]
- Владелец задал критерий проверки `1html`: сравнить создание артефакта после плана субагента с созданием артефакта без плана и по результату определить, сработало ли правило. [L22]
- Владелец предложил правило-кандидат для `План До Кода`: переиспользовать классы дизайн-системы, ограничить набор типографики примерно десятью видами текста и доказывать responsive-поведение. [L23]
- Владелец решил, что шаблон `1html` должен содержать зафиксированные классы, которые агент использует вместе с DaisyUI, чтобы агентам не приходилось создавать собственные CSS- и HTML-классы. [L24]
- Владелец предложил идею запретить новые классы за пределами готовой библиотеки и проверять этот запрет линтером. [L25]
- Владелец передал агенту выбор между полным запретом собственных классов с линтером и более мягким режимом для `1html`. [L26]
- Владелец решил, что `1html` нужен для быстрых черновых артефактов как визуального способа общения: через красивый дизайн, графики, карточки, вложенность понятий, диаграммы и демонстрацию интерфейса, а не для финального или production-дизайна. [L27]
- Владелец задал критерий успеха: `1html` должен стабильно выдавать читаемый дизайн за один ход при минимальных когнитивных усилиях и без итерации из-за сбоев артефакта. [L28]
- Владелец задал критерий: responsive-поведение нужно для чтения при любом размере браузера, а малый объём кода — для быстрых итераций и генерации множества вариантов прототипов и диаграмм. [L29]
- Владелец решил запускать линтер собственных классов только по явному запросу в виде advisory-команды, а не как хук на запись. [L30]
- Владелец решил привести всю папку HTML-артефактов в соответствие с `1html`, чтобы будущие агенты не перенимали стиль соседних страниц, нарушающий скил. [L31]
