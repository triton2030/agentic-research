# Как Строить Системы Которые Сами Знают Куда Класть Новое

## Зачем Эта Дисциплина

У каждого проекта своя форма. Книга, лендинг, база знаний, агентная база, документация продукта — у каждого своё «правильно». Универсальных правил нет: огромные файлы — норма для книги и смерть для wisdom-базы. Жёсткая иерархия — спасение для wiki и душит лендинг.

Сама система рассуждать не умеет. Но instruction-файл проекта может закодировать правила, которые роутят новое **по смыслу** — если правила конкретные, исчерпывающие и в них же проговорено, по каким симптомам видно, что роутинг сломался.

Эта дисциплина — про то, как для **любого** проекта спроектировать такой слой.

## Что Получается На Выходе

Для проекта — два артефакта:

1. **Routing layer** — короткий instruction-файл проекта (`AGENTS.md`, `CLAUDE.md`, корневой `README.md` — как принято на платформе), который для каждого типа артефакта говорит, куда его положить и почему.
2. **Decay signals** — список конкретных, наблюдаемых симптомов, по которым видно, что роутинг сломался: какие файлы пухнут не на своём месте, где канон расходится, какие папки начинают дублировать друг друга.

## Шесть Шагов

### 1. Назови форму проекта

Одна фраза. Не «база знаний», а «категорийная база эталонов и принципов для авторства агентных артефактов». Не «книга», а «одно длинное связное повествование с минимальной структурой». Форма определяет всё остальное; без неё пороги и правила висят в воздухе.

### 2. Перечисли типы артефактов

Какие куски контента этот проект будет копить? Для агентной базы: wisdom, guide, example, research-note, project, ops. Для книги: глава, заметка автора, цитата, ссылка, draft. Для лендинга: page, component, asset, copy variant.

Не больше 7 типов. Если их 12 — типы плохо нарезаны или проект на самом деле два разных проекта в одной папке.

### 3. Для каждого типа — где живёт и почему

Таблица или короткий список:

```
wisdom → knowledge/wisdom-*.md (повторяемые принципы для всех агентов)
guide  → knowledge/guides/perfect-*.md (эталонные шаблоны и плэйбуки)
ops    → ops/ (операционный слой)
```

«Почему» — не для красоты. Оно проверяет, не один ли это и тот же тип под двумя именами.

### 4. Назови, что туда не кладут

Каждой папке — явный negative list. «В `wisdom-*` не кладём task-level рецепты — они в `practical-guides/`». «В книге `notes/` не кладём финальный текст глав». Без negative list папки начинают повторять друг друга, и роутинг перестаёт быть однозначным.

### 5. Назови сигналы распада

Что значит «система ломается» именно для **этого** проекта?

- Wisdom-база: файлы wisdom больше 200 строк; одна и та же мысль в трёх местах; guide читается как wisdom.
- Книга: ничего из этого. Глава 5000 слов — норма. Сигналы — другие: финальный текст в `notes/`, две версии одной главы без явного `draft-`/`final-`.
- Лендинг: одно и то же копи в трёх компонентах вместо одного источника; имена компонентов перестали соответствовать тому, что они рендерят.

Сигналы должны быть **наблюдаемы** — глазами или grep'ом, не «ощущается перегруженно».

### 6. Закодируй в instruction-файл проекта

Короткий файл в корне. Структура:

- Назначение (одна фраза из шага 1)
- Типы артефактов и где живут (шаги 2-3)
- Не кладём (шаг 4)
- Сигналы распада + триггер для пересмотра (шаг 5)

Никакой философии. Никаких «почему мы выбрали». Только рабочий слой, который агент будет читать каждый раз.

## Чек-Лист Папочных Инструкций

Используй для `GPT-5.5` и `Claude Opus 4.7`: сильные модели лучше следуют
точным правилам, но лишние requirements и конфликты вредят сильнее.

**Root `AGENTS.md` / `CLAUDE.md`:**

- Есть одна фраза формы проекта и главный outcome.
- Есть precedence: что сильнее при конфликте, где source of truth.
- Есть owner map: какие папки/файлы держат контракт, план, знания, runtime.
- Есть глобальные red lines и validation defaults.
- Нет деталей одной папки, task-state, длинных examples и тел скилов.

**Subtree instruction:**

- Файл создан из-за distinct recurring failure или локального owner-а, не
  потому что папка существует.
- В начале сказано, чем зона отличается от root.
- Названы local source of truth, read-before-edit и nearest validation.
- Есть local negative list: что сюда не класть и чего не делать.
- Есть escalation: когда вернуться к root, owner skill или пользователю.
- Нет копии root-инструкций и нет нового канона вместо owner-файла.

**Skill / reference / knowledge:**

- Повторяемый workflow живёт в `SKILL.md`, а не в root prose.
- Редкие длинные детали живут в `references/` или `knowledge/`, с read condition.
- Исследовательская evidence остаётся в `research/`, пока не стала правилом.

**Перед добавлением нового правила:**

- Правило меняет реальное решение агента?
- Агент увидит его до момента, где оно нужно?
- Это minimal requirement, а не полезное пожелание?
- Есть ли уже owner, который держит ту же функцию?
- Если нарушение дорогое, есть ли validator/test/hook/checkpoint?
- Не создаёт ли правило конфликт с соседним instruction-файлом?

## Когда Перепроектировать, А Не Чинить Внутри Старой Формы

Симптомы того, что форма устарела:

- Сигналы распада срабатывают в нескольких местах одновременно
- Появился новый тип артефакта, не попадающий ни в одну категорию
- Два типа начали систематически плодиться в одной папке
- Триггер пересмотра срабатывает чаще, чем раз в квартал

Тогда — не патчи, а пройти 6 шагов заново. Старую форму положить в `_archive/` на одну итерацию, не удалять.

## WRONG / RIGHT — Один Тип, Разные Проекты

Чтобы было видно, насколько правила зависят от формы.

**«Длинная свободная заметка»**

Wisdom-база (`agentic-research`):

- WRONG: положить в `knowledge/agents/runtime-layer.md` потому что «про агентов»
- RIGHT: research-note → `knowledge/research/{category}/learnings.md`; в wisdom поднимается только повторяемый принцип, дистиллированный до 1-3 предложений

Книга:

- WRONG: положить в `chapters/` потому что «длинно»
- RIGHT: `notes/YYYY-MM-DD-slug.md`; в `chapters/` — только финальный обработанный текст

Один и тот же физический файл идёт в **разные места** в зависимости от формы проекта. Без шагов 1-2 агент не сможет это решить.

## Что Делает Эту Дисциплину Слабой

- Универсальные пороги без привязки к форме (200 строк, 7 файлов и т. п.) — навязывают чужую форму
- Routing-правила в виде принципов («кладите туда, где осмысленно») — не работают, агент роутит наугад
- Отсутствие negative list — папки начинают повторять друг друга
- Сигналы распада сформулированы как ощущения, а не наблюдаемые факты
- Перепроектирование без архивации старой формы — теряется возможность откатиться, страшно ломать
- Вера, что nested instruction-файлы сами повысят adherence. Свежая эмпирика
  не подтверждает file-structure variables как главный рычаг; важнее owner,
  минимальные требования и проверка.
