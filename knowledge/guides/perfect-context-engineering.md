# Как Инженерить Контекст

Точный model set задаёт `_ops/GOAL.md`. Модельные различия читать в
`knowledge/wisdom-gpt-5.6.md`, `knowledge/wisdom-claude-opus-4.8.md` и
`knowledge/wisdom-claude-fable-5.md`; здесь только правила сборки контекста.

## Для Чего Нужна Инженерия Контекста

Системный промпт задаёт роль и рамку, а инженерия контекста решает, **что именно** модель видит при выполнении задачи и **в каком порядке**. Её задача — сделать так, чтобы агент принимал правильные решения даже при частичной загрузке, не галлюцинировал несуществующее и не промахивался мимо важного правила.

## Что Обычно Должно Быть в Контексте
- инварианты и бренд-константы, которые нельзя переизобретать
- карта файлов или артефактов с ролью каждого в одной фразе
- главное архитектурное правило с явным «как и как нельзя»
- конкретные copy-paste сниппеты для повторяющихся паттернов
- рецепты для типовых операций, а не абстрактные принципы
- операционные мелочи, которые ломают агента без явного упоминания (cache-busting, хуки регидрации, запреты на один стиль вместо другого)
- каталоги существующих сущностей (таблицы примитивов, паттернов), чтобы не предлагалось несуществующее
- verify-шаги, встроенные в рецепт, а не отдельным блоком «мог бы проверить»
- явный список нежелательных исходов

## Модельная Дельта

- Для `GPT-5.6` сначала прочитать `knowledge/wisdom-gpt-5.6.md`.
- Для `Claude Opus 4.8` прочитать `knowledge/wisdom-claude-opus-4.8.md`.
- Для `Claude Fable 5` прочитать `knowledge/wisdom-claude-fable-5.md`.
- В этом guide не дублировать модельный baseline; переносить сюда только
  правила, которые верны для контекстной сборки независимо от модели.

## Что Туда Не Стоит Класть
- философию и «why we chose this»
- roadmap и статус работ
- ретроспективы и историю изменений
- абстрактные принципы без конкретики
- длинные объяснения того, что понятно по именам
- несколько формулировок одной мысли ради страховки

## Надёжный Порядок Блоков
1. Идентичность и инварианты
2. Карта файлов или артефактов
3. Главное архитектурное правило
4. Полный сниппет ключевого паттерна
5. Где живут данные и конфигурация
6. Операционные мелочи
7. Пошаговый рецепт типовой операции
8. Verify-чеклист
9. Deliberate non-goals

Инварианты в топе, рецепты в середине, запреты в конце. Читатель может остановиться в любой момент и всё равно унесёт главное.

## Приёмы Против Частичной Загрузки
- Главное правило повторять в нескольких местах только при доказанном
  partial-loading risk: в корневом файле как формулировку, в доменном как
  диаграмму, в примере как WRONG/RIGHT пару. Без такого риска для
  для текущих target models повтор становится шумом.
- Двухуровневая иерархия инструкций: корневой операционный файл + доменный, самодостаточный. Каждый читается без другого.
- Живой визуальный или runtime-артефакт рядом с текстом. Текст — индекс, артефакт — источник правды. Каталоги в тексте обязательно синхронизированы с ним через шаг в verify-рецепте.

## Приёмы Против Галлюцинаций
- Явный `Deliberate non-goals` или `Not now` блок в конце: «нет билда, нет dark mode, нет внешней библиотеки X».
- WRONG/RIGHT пары: анти-пример первым, правильный вторым. Закрывает самые частые ошибки.
- Таблицы-каталоги сущностей: одна строка на сущность, одно назначение. Если чего-то нет в таблице — это не существует.
- Полный copy-paste сниппет вместо «используйте утилиту X». Агент не изобретает свою версию.

## Pull vs Push Discovery
- **Pull**: уроки распарсены в `wisdom-*.md` и `perfect-*.md`, агент читает их при начале работы. Эталоны могут быть физически недоступны — не важно, урок уже выжат.
- **Push**: агент читает сырые эталонные артефакты из `knowledge/examples/{slug}/` как живые образцы при написании нового.
- Надёжнее использовать оба слоя: pull даёт быстрый доступ к дистиллированной мудрости, push даёт живой пример для копирования структуры.
- Каждый эталон в `examples/` должен быть **процитирован** хотя бы в одном `perfect-*` или `wisdom-*`, иначе он не всплывёт через месяц.
- Повторять главное правило в нескольких местах стоит только при реальном
  partial-loading risk. Для GPT-5.6 minimal outcome-first context обычно лучше
  старого defensive repetition; добавление оправдывает measured failure mode.

## Правила По Длине
- Сначала короче, чем хочется, добавлять только то, что реально меняет поведение.
- В ядре — основной рабочий путь. Редкие случаи на втором уровне.
- Более длинный текст оправдан, только если он предотвращает повторяющийся сбой.
- Никаких абзацев «на всякий случай» или «для полноты».

## Что Делает Контекст Слабым
- он читается как философия, а не как рабочий инструмент
- он объясняет, но не показывает сниппетами
- он повторяет главное правило без доказанного partial-loading риска или,
  наоборот, оставляет часто теряющееся правило без локальной доставки
- он не проговаривает операционные детали, которые агент предсказуемо проигнорирует
- он разрастается до такой степени, что приоритеты перестают читаться
- каталог в тексте расходится с реальным артефактом
- он подменяет явный scope надеждой, что модель сама "поймёт, что это относится ко всему"
- он сохраняет старую историю и process scaffolding вместо краткого state:
  что уже сделано, что доказано, что заблокировано и какой следующий outcome

## Быстрая Проверка

Перед тем как оставлять контекст, стоит спросить:
- Если в контекст попадёт только один из файлов — догадается ли агент о главном правиле?
- Есть ли там конкретный сниппет или только принцип?
- Закрыты ли самые частые галлюцинации явным негативным списком?
- Синхронизированы ли текстовые каталоги с реальным живым артефактом?
- Встроен ли verify-шаг в рецепт, или он висит отдельным блоком?
- Учтён ли model-specific state/effort/tool-policy baseline из нужного
  `wisdom-*` файла?

## Эмпирика и Сигналы Деградации

Свежая доказательная база для текущего model set пока узкая. Не
делай из неё больше, чем она доказывает:

- Факторный эксперимент по Claude Code config files не нашёл надёжного эффекта
  от size, position, file architecture и adjacent conflicts. Не оптимизируй
  форму файлов как магическую ручку adherence.
- Самый заметный сигнал там — drift внутри сессии: чем дальше агент генерирует
  функции в одном проходе, тем хуже держит target rule. Для длинной работы
  помогай chunking, state refresh и verification gates.
- AGENTS/context files могут ухудшать success и cost, если добавляют лишние
  требования. Контекст должен держать minimal requirements и exact validation.
- Если ограничение дорого нарушить, текст слабоват: нужен executable check,
  validator, hook, test или human checkpoint.
- Стабильный префикс системного промпта или skill description критичен для KV-cache. Любая переменная часть в начале (timestamp, счётчик, динамический ID) обнуляет кеш и удорожает каждый ход.
- Пять паттернов деградации для диагностики раздутого скилла или `CLAUDE.md`: lost-in-middle, poisoning (затравленные ложные факты повторяются дальше), distraction (нерелевантные блоки тянут внимание), confusion (несовместимые куски), clash (прямые противоречия). Симптом — агент уверенно делает не то.
- Filesystem часто выигрывает у любой кастомной «памяти»: scratch pad, plan persistence, sub-agent communication через файлы — простой и проверяемый паттерн. Не выдумывать memory-слой, пока файловая система явно не упирается.
- Model-specific compaction и state rules не дублировать здесь; читать
  соответствующий `wisdom-*` файл.
