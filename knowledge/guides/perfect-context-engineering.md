# Как Инженерить Контекст

Точный model set задаёт `_ops/GOAL.md`. Модельные различия читать в
`knowledge/wisdom-gpt-5.6.md`, `knowledge/wisdom-claude-opus-5.md` и
`knowledge/wisdom-claude-fable-5.md`; здесь только правила сборки контекста.

## Для Чего Нужна Инженерия Контекста

Системный промпт задаёт роль и рамку, а инженерия контекста решает, **что
именно** модель видит при выполнении задачи. Её задача — сделать правильные
решения вероятнее даже при частичной загрузке, несуществующих данных и
конкурирующих правилах.

## Что Обычно Должно Быть в Контексте

- инварианты и бренд-константы, которые нельзя переизобретать
- карта файлов или артефактов с ролью каждого в одной фразе
- главное архитектурное правило с явным «как и как нельзя»
- выразительные interfaces, schemas, tests, source или HTML-артефакты как
  высокоточные references; copy-paste сниппет — только для exact pattern
- рецепты для хрупких операций, где порядок меняет результат; иначе outcome,
  критерии и доступный interface вместо process choreography
- операционные мелочи, которые ломают агента без явного упоминания:
  cache-busting, хуки регидрации, style prohibitions
- каталоги существующих сущностей, чтобы не предлагалось несуществующее
- observable validation рядом с claim или операцией, которую она доказывает;
  для order-sensitive рецепта verify входит в сам контракт операции
- материальные нежелательные исходы, которые нельзя надёжно вывести из context

## Модельная Дельта

- Для `GPT-5.6` сначала прочитать `knowledge/wisdom-gpt-5.6.md`.
- Для `Claude Opus 5` прочитать `knowledge/wisdom-claude-opus-5.md`.
- Для `Claude Fable 5` прочитать `knowledge/wisdom-claude-fable-5.md`.
- В этом guide не дублировать модельный baseline; переносить сюда только
  правила, которые верны для контекстной сборки независимо от модели.

## Что Туда Не Стоит Класть

- философию и «why we chose this»
- roadmap и статус работ
- ретроспективы и историю изменений
- абстрактные принципы без конкретики
- длинные объяснения того, что понятно по именам
- несколько формулировок одной мысли ради страховки

## Желаемая Форма

Контекст достаточен, когда модель может восстановить текущий owner, outcome и
state; найти высокоточную reference/interface; отличить scope от non-goals; и
проверить materially important claims. Это не обязательный порядок блоков.
Самое дорогое для потери должно переживать partial read, а стабильный prefix —
оставаться cacheable. Рецепт появляется только у операции, где порядок сам
является частью корректности.

## Приёмы Против Частичной Загрузки

- Главное правило повторять в нескольких местах только при доказанном
  partial-loading risk: в корневом файле как формулировку, в доменном как
  диаграмму, в примере как WRONG/RIGHT пару. Без такого риска для
  текущих target models повтор становится шумом.
- Двухуровневая иерархия инструкций: корневой операционный файл и
  самодостаточный доменный. Каждый читается без другого.
- Живой визуальный или runtime-артефакт рядом с текстом. Текст — индекс,
  артефакт — источник правды. Текстовые каталоги синхронизируются с ним через
  observable validation.

## Приёмы Против Галлюцинаций

- `Deliberate non-goals` или `Not now` добавлять, когда модель иначе вероятно
  выберет правдоподобный, но нежелательный путь; очевидные отсутствия не
  перечислять.
- WRONG/RIGHT пары использовать для наблюдаемого failure mode или границы
  вкуса, а не как default tool-инструкцию: серия примеров может искусственно
  сузить пространство решений.
- Таблицы-каталоги сущностей: одна строка на сущность, одно назначение. Если
  чего-то нет в таблице — это не существует.
- Для tool use сначала улучшать schema/interface: параметры, enum, constraints
  и description. Пример нужен, только если interface не выражает неочевидное.
- Source code, tests и executable/HTML artifacts обычно точнее prose или
  screenshot. Полный copy-paste сниппет оправдан, когда нужна именно та же
  семантика, а не самостоятельный поиск решения.

## Pull vs Push Discovery

- **Pull**: уроки распарсены в `wisdom-*.md` и `perfect-*.md`; агент читает их
  при начале работы. Raw-эталон может быть недоступен — вывод уже выжат.
- **Push**: агент читает raw-артефакты из `knowledge/examples/{slug}/` как
  живые образцы при написании нового.
- Pull — default. Push добавлять, когда raw reference меняет решение, вкус или
  fidelity; не грузить пример ради самого наличия примера.
- Каждый эталон в `examples/` должен быть **процитирован** хотя бы в одном
  `perfect-*` или `wisdom-*`, иначе он не всплывёт через месяц.
- Повторять главное правило в нескольких местах стоит только при реальном
  partial-loading risk. Для GPT-5.6 minimal outcome-first context обычно лучше
  старого defensive repetition; добавление оправдывает measured failure mode.

## Правила По Длине

- Сначала короче, чем хочется; добавлять только то, что реально меняет
  поведение.
- В ядре — основной рабочий путь. Редкие случаи на втором уровне.
- Более длинный текст оправдан, только если он предотвращает повторяющийся сбой.
- Никаких абзацев «на всякий случай» или «для полноты».

## Что Делает Контекст Слабым

- он читается как философия, а не как рабочий инструмент
- он объясняет, но не показывает сниппетами
- он повторяет главное правило без доказанного partial-loading риска или,
  наоборот, оставляет часто теряющееся правило без локальной доставки
- он не проговаривает операционные детали, которые агент предсказуемо
  проигнорирует
- он разрастается до такой степени, что приоритеты перестают читаться
- каталог в тексте расходится с реальным артефактом
- он подменяет явный scope надеждой, что модель сама «поймёт, что это относится
  ко всему»
- он сохраняет старую историю и process scaffolding вместо краткого state:
  что уже сделано, что доказано, что заблокировано и какой следующий outcome

## Быстрая Проверка

Перед тем как оставлять контекст, стоит спросить:

- Если в контекст попадёт только один из файлов — восстановит ли агент главное
  правило?
- Есть ли высокоточная interface/reference или только общий принцип?
- Не сужает ли пример пространство решения там, где достаточно schema, source
  или критериев?
- Названы ли материальные нежелательные исходы, которые нельзя вывести?
- Синхронизированы ли текстовые каталоги с реальным живым артефактом?
- Привязана ли validation к claim/операции, которую она действительно
  доказывает?
- Учтён ли model-specific state/effort/tool-policy baseline из нужного
  `wisdom-*` файла?

## Эмпирика и Сигналы Деградации

Свежая доказательная база для текущего model set пока узкая. Не
делай из неё больше, чем она доказывает:

- Факторный эксперимент по Claude Code config files не нашёл надёжного эффекта
  от size, position, file architecture и adjacent conflicts. Не оптимизируй
  форму файлов как магическую ручку adherence.
- Самый заметный сигнал там — drift внутри сессии: чем дальше агент генерирует
  функции в одном проходе, тем хуже держит target rule. Для длинной работы
  помогай chunking, state refresh и verification gates.
- AGENTS/context files могут ухудшать success и cost, если добавляют лишние
  требования. Контекст должен держать minimal requirements и exact validation.
- Если ограничение дорого нарушить, текст слабоват: нужен executable check,
  validator, hook, test или human checkpoint.
- Стабильный префикс системного промпта или skill description критичен для
  KV-cache. Любая переменная часть в начале — timestamp, счётчик, динамический
  ID — обнуляет cache и удорожает каждый ход.
- Пять паттернов деградации раздутого skill или `CLAUDE.md`: lost-in-middle,
  poisoning, distraction, confusion и clash. Симптом — агент уверенно делает
  не то.
- Filesystem часто выигрывает у кастомной «памяти»: scratch pad, plan
  persistence и subagent communication через файлы — простой проверяемый
  pattern. Не выдумывать memory layer, пока filesystem явно не упирается.
- Model-specific compaction и state rules не дублировать здесь; читать
  соответствующий `wisdom-*` файл.
