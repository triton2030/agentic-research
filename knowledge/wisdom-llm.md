# Wisdom — LLM

Снимок на 14 июля 2026.

Здесь только общие свойства текущей рабочей пары моделей и повторяющиеся режимы
сбоя. Рабочий baseline этого проекта — `GPT-5.6` и `Claude Opus 4.7`; старые
model-neutral советы держатся только если они подтверждены заново.

## Проверено

- Prompt-only защита хрупка. Если модель работает с инструментами и недоверенным контентом, контроль должен строиться через права, sandbox, approvals, validation и проверки после действия.
- Сикофантия — измеримое базовое свойство фронтир-моделей, а не баг, который чинится просьбой “спорь со мной”.
- Рассинхрон literal-vs-intent систематичен. Модель молча делает допущение о намерении пользователя и действует по нему, если его не вынудить прояснить.
- Узкая настройка даёт широкую разрегулировку: локальный fine-tune на одной задаче может ломать поведение в несвязанных доменах.
- Reasoning-модели не следуют reasoning-инструкциям достаточно надёжно, чтобы верить заявленной стратегии на слово. Проверять нужно по наблюдаемому поведению.
- Для новых reasoning-моделей prompt уже не главный рычаг качества. Сначала
  настроить effort/verbosity/tool policy/schema/state handling, потом чинить
  prompt только под наблюдаемый сбой.
- Старые process-heavy prompt stacks могут ухудшать сильные модели: добавляют
  шум, сужают поиск и провоцируют механическое поведение. Лучше задавать
  outcome, constraints, evidence и stop condition.
- Агент не выводит надёжно подразумеваемые действия из голой цели. «Очевидное
  профессионалу в этом проекте» — тацитное знание проекта, которого нет в окне
  модели; под нагрузкой осыпается даже общеизвестное (instruction density);
  голая цель или KPI без явных критериев провоцирует срезание углов и gaming.
  Поэтому подразумеваемую работу нельзя оставлять подразумеваемой — её надо
  сделать проверяемой.
- `effort` — не ручка "качество вверх". Слишком высокий effort при слабом
  done state, конфликтующих правилах или открытом tool access усиливает
  overthinking и лишний поиск.
- Clarifying agents работают лучше, когда уточнения отбираются по EVPI, а не по любой замеченной двусмысленности.
- Богатый discovery снимает часть EVPI-вопросов до их задания: хороший контекст уменьшает шум уточнений.
- Reasoning не гарантирует распознавание ложной предпосылки: свежий ACL 2026
  benchmark показывает, что reasoning-модели всё ещё пропускают значимую долю
  false presuppositions, особенно при уверенном пользовательском framing.
- Обнаружить missing premise и остановиться — разные способности. Reasoning-модель
  может рано заметить нехватку данных, затем продолжить self-doubt loop и
  додумать ответ; поэтому stop/abstention должен быть отдельным решением.
- Ошибочный draft в контексте создаёт contextual drag: поздний feedback и даже
  успешная self-verification не гарантируют освобождение от старой структуры.
  После invalidating evidence надёжнее re-anchor из чистого набора owner facts.
- Статус знания и рабочее последствие нельзя кодировать одним label:
  `confirmed / contradicted / insufficient / conflicting` — про evidence,
  `none / accepted assumption / blocker / reframe` — про решение.

## Полезные Приёмы

- Вербализация скрытого допущения о намерении пользователя до ответа снижает риск сикофантии сильнее, чем общая инструкция “будь честен”.
- Ролевой фрейминг даёт модели структурное разрешение на позицию лучше, чем прямая просьба “возрази”.
- Анти-сикофантные правила полезнее формулировать негативно на уровне наблюдаемого паттерна, а не общим пожеланием.
- Для сильных моделей проще удалять устаревший scaffolding и переснимать
  baseline, чем добавлять новые слои текста поверх старого prompt.
- Подразумеваемую работу переноси не в процедуру (путь «сделай A, потом B»), а в
  определение готовности — критерии-истины, что обязано быть верно в конце, —
  плюс гейт сверки перед «готово». Это outcome-форма, не рецепт: путь модель
  выбирает сама, но забыть не может, потому что в конце сверка. Роль поднимает
  пол ожиданий, критерии ловят забытое, гейт не даёт объявить «готово» на глаз.
  Пошаговая процедура оправдана только там, где операция хрупкая/необратимая или
  порядок сам — требование продукта; иначе цель — драйвер, процедура — страховка.
