# Wisdom — Skills Plugins

Снимок на 28 апреля 2026.

Здесь только общие принципы про skills/plugins как форму упаковки знания.
Практический authoring canon держит
`knowledge/practical-guides/how-to-write-skills/`.

## Проверено

- Скилл нужен не для хранения темы, а для повторяемого профессионального
  вмешательства с trigger, полезной Delta, границами и признаками качества.
- Скилл слабеет, если дублирует системный prompt, описывает разовую задачу или
  несёт теорию без decision/action contract.
- Плагин оправдан там, где нужно упаковать не один текст, а связку из skills, integrations, MCP и повторяемого workflow.
- Для сложной системы полезнее несколько узких skills и plugins с ясной зоной ответственности, чем один широкий слой “на всё”.
- Вызов скилла — блокирующее требование только при реальном trigger или
  существенном риске ошибки без него. Не активировать скилл как страховку без
  сигнала: это превращает routing в preload. **Оговорка 2026-08-06 — у промаха
  routing есть цена, и она большая:** в замере одна и та же документация дала 53%
  без неё, 53% скилом с дефолтным поведением (скил не вызывался в 56% случаев),
  79% скилом с явной инструкцией вызвать первым и 100% постоянно присутствующим
  индексом. В том замере постоянный индекс был единственным сработавшим
  лечением промаха routing, но это не универсальная рекомендация preload:
  resident delivery несёт постоянные context, conflict и integrity costs. Его
  оставляют для действительно cross-task правила после сравнения с no-skill и
  on-demand delivery; hard invariant обеспечивают runtime gate или validator,
  а не одна root-проза.
- Порядок при нескольких кандидатах: сначала owner outcome/scope, потом
  process-skill только если порядок действий реально меняет результат или
  предотвращает провал.
- Инструкции пользователя задают ЧТО; скилл возвращает недостающие критерии
  решения, evidence и только при необходимости КАК. “Добавь X” или “исправь Y”
  не означает пропустить профессиональный контракт скилла.
- В Claude Code скилл загружается динамически через Skill tool — читать SKILL.md через Read нельзя, это обходит механизм загрузки.
- Control surface для сложной работы полезно проверять цепочкой `goal -> structure -> proof`: зачем существует направление, какая форма заставляет его работать, чем результат доказывается.
- Новый skill / agent / hook нельзя строить по одному старому упоминанию в памяти или заметке. Сначала проверить живой runtime-layer и существующие handles.

## Правило Продвижения

- Повторяемое знание для любых агентов и скиллов идёт в `knowledge/`.
- Знание, которое важно одной линии, идёт в её category `_research/`.
- Устойчивое правило по умолчанию для всей работы поднимается в `AGENTS.md` или в `knowledge/guides/`.
- Устойчивые правила написания системных промптов держим в `/knowledge/guides/perfect-system-prompts.md`.
- Устойчивые правила написания скиллов держим в
  `/knowledge/practical-guides/how-to-write-skills/`.
- Наблюдение не стоит поднимать выше, пока оно не повторилось в нескольких сессиях, задачах или линиях и не начало реально менять решения.

## Рабочие Гипотезы

- Наибольшая ценность research-репозитория может быть в переводе исследований в короткие reusable contracts для ролей, риска, проверки и упаковки знания.
- Adversarial self-play полезен как **генератор** критериев обхода, но не как их проверка: «без внешнего reviewer» снято 2026-08-06 — верность видимой цепочки рассуждения 25–39%, самоотчёт назван наименее надёжным артефактом траектории, а отбор по процессу работает именно потому, что читает его независимая сторона.
- Must-not с явным полем «Why this would be bypassed» надёжнее сухого запрета: в контекст попадает сам паттерн обхода.
- Spec-driven подход полезен не только в коде. Он помогает превращать non-trivial задачи в контракт с наблюдаемыми артефактами.
