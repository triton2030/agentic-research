# Понимание кодовой базы — срез 2026-Q3

Снимок состояния на **7 сентября 2026 года**. Это исследовательский материал
для выбора и пилота, а не утверждённый стандарт проекта.

## Короткий ответ

Лучшее решение сейчас — не единый «AI-индекс всей кодовой базы», а
проверяемая воронка:

1. Короткая Aider-подобная repo map — начальная ориентация и выбор следующего
   места до того, как агент начнёт блуждать по файлам.
2. `rg` на текущем checkout — точный текст, пути, конфиги и fallback.
3. **Serena** — definitions, references, symbols, diagnostics и
   symbol-level изменения через LSP и MCP.
4. **ast-grep** — структурный поиск и проверка синтаксических паттернов.
5. Чтение небольшого фрагмента live source и тест — окончательное
   доказательство перед изменением.

Для очень большого monorepo или многих репозиториев к этому добавляется
**Zoekt**. **CodeGraphContext** имеет смысл только как измеряемый пилот для
call chains и blast radius. Vector retrieval следует добавлять последним —
когда реальные задачи доказали, что lexical + map + LSP систематически не
находят нужный код.

## Какая проблема на самом деле решается

«Моментально понять всю кодовую базу» смешивает девять разных операций.

| Операция | Нужное свидетельство | Подходящий механизм |
| --- | --- | --- |
| Инвентаризация | дерево, языки, workspaces, generated/vendor | filesystem, build manifests |
| Ориентация | entry points, API, центральные модули | token-budgeted repo map |
| Поиск по смыслу | кандидаты при неизвестном identifier | semantic/hybrid retrieval |
| Точная навигация | definition, type, implementation, references | LSP или SCIP-backed index |
| Топология | imports, calls, inheritance, data flow | compiler/LSP/graph, с provenance |
| Context packing | малый связный набор в token budget | ranking + outlines |
| Impact | callers, dependents, tests | reference/call graph + live checks |
| Freshness | текущие branch, SHA и новые файлы | checkout-aware index/watch |
| Intent | ADR, docs, история и соглашения | owner docs и repository instructions |

Ни AST, ни embeddings, ни LSP не закрывают все строки. Правильная цель —
агент за 1–3 дешёвых обращения получает **ограниченный, revision-aware набор
кандидатов и связей**, после чего умеет проверить вывод по исходнику.

## Как отделялся работающий инструмент от хайпа

В первичный фильтр входили:

- лицензия, допускающая open-source использование;
- живой default branch и понятный release/issue lifecycle;
- не только stars, но forks, ширина contributor-base, объём истории и
  downstream integration;
- пригодная агенту поверхность: CLI, MCP, API или библиотека;
- freshness-механизм и наблюдаемый отказ вместо тихо устаревшего ответа;
- совпадение механизма с конкретной операцией из таблицы выше;
- воспроизводимый benchmark или независимое downstream-use сильнее README.

Raw-метрики легко вводят в заблуждение. Bots, дробление изменений и release
bumps раздувают commit count; fork обычно означает эксперимент, а не
production deployment. Например, у `ast-grep` 51 из последних 100 изученных
коммитов были Renovate, а у некоторых новых graph-MCP 87–91 из 100 принадлежали
одному автору. При этом и shortlist нельзя идеализировать: большая часть
истории Serena создана двумя людьми, а ast-grep и Zoekt в недавнем окне также
сильно зависят от одного maintainer. Contributor count включает много разовых
PR и не доказывает высокий bus factor. Поэтому ясный механизм, многолетний
downstream-use, state/freshness contract и скорость ремонта опасных ошибок
весят больше любого одного GitHub-счётчика.

## Что говорит свежая эмпирика

- [Agent Retrieval Bench](https://arxiv.org/abs/2607.24882) включает 427
  samples из 25 репозиториев. Он не тестирует LSP, ast-grep или полноценные
  code graphs, поэтому не доказывает выбранный стек. Его применимый вывод уже:
  разные embedding-модели выигрывают MRR и Recall@20, vectorless RepoMap —
  budgeted context yield при 8K, а retrieval-derived начальный context seed
  даёт выше File F1 при меньшем последующем исследовании. В записанных
  траекториях агенты вообще не открывали gold-файл в 27–35% samples.
- [CodeGrep](https://arxiv.org/abs/2608.05886) показывает не «retrieval всегда
  полезен», а порог precision: слабые BM25/Jina варианты ухудшали либо не
  меняли downstream agent, тогда как обученный retrieval agent сократил
  раунды на 15% и tokens на 19% при сохранении resolve rate.
- [LocAgent](https://arxiv.org/abs/2503.09089) подтверждает пользу
  heterogeneous graph для multi-hop localization, но это исследовательский
  framework, а не универсальный зрелый сервис.
- [ARISE](https://arxiv.org/html/2605.03117v1) усиливает structural graph
  statement-level def-use edges: на SWE-bench Lite он улучшил Function
  Recall@1 на 17 пунктов и Pass@1 на 4,7 пункта против SWE-agent baseline.
  Это аргумент в пользу точного data-flow для отдельных задач, а не в пользу
  любого Tree-sitter graph.

Общий вывод: static retrieval и интерактивное исследование дополняют друг
друга. Качество зависит от вида запроса, а неточный дополнительный контекст
способен сделать агента дороже и хуже.

## Почему верхние кандидаты стоят именно так

### 1. Serena — первый практический выбор

[Serena](https://github.com/oraios/serena) превращает language servers в
agent-oriented MCP tools: symbol overview, definition, referencing symbols,
diagnostics, rename и symbol-level edits. Она поддерживает Codex, Claude Code,
Cursor и другие MCP clients и использует более 40 language integrations.
[Таблица возможностей](https://oraios.github.io/serena/01-about/035_tools.html)
честно показывает, что open LSP backend не гарантирует поиск declarations во
внешних dependencies, implementations доступны не для всех языков, а type
hierarchy и сложные move/inline refactorings относятся к платному JetBrains
backend.

Это лучший первый add-on, потому что он даёт агенту недостающую IDE-семантику,
не вводя vector database. Но собственная
[evaluation Serena](https://oraios.github.io/serena/04-evaluation/000_evaluation-intro.html)
остаётся maintainer-run self-report, а не независимым outcome benchmark.

### 2. ast-grep — дешёвое структурное зрение

[ast-grep](https://github.com/ast-grep/ast-grep) ищет и переписывает AST
паттерны через быстрый CLI. Он полезен для outline, массовых синтаксических
вариантов и post-edit checks, но не разрешает types, cross-file references или
динамический dispatch. Его
[agent outline benchmark](https://ast-grep.github.io/blog/ast-grep-outline.html)
ценен тем, что показывает и проигрыши: на некоторых небольших репозиториях
outline увеличивал стоимость или число tool calls. Поэтому structural layer
должен быть доступен по запросу, а не безусловно загружать контекст.

### 3. Zoekt — масштаб без обещания «понимания»

[Zoekt](https://github.com/sourcegraph/zoekt) — зрелый positional trigram
index для быстрого substring/regexp search по множеству репозиториев и веток.
Он поддерживает CLI, JSON/gRPC и periodic reindex. Его
[design](https://github.com/sourcegraph/zoekt/blob/main/doc/design.md)
оптимизирует исчерпывающий поиск, а не semantic answers. Именно узость обещания
делает его сильным production building block. Для обычного локального repo
`rg` дешевле; Zoekt оправдан измеренной latency или cross-repo потребностью.

### 4. CodeGraphContext — только контролируемый graph pilot

[CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext)
имеет MIT, MCP/CLI, incremental watcher и заметно более широкое участие, чем
большинство новых graph-MCP. Он умеет отдавать callers, paths и graph reports.
Но Tree-sitter call edges остаются эвристикой; в issue tracker есть batch и
backend/freshness incidents. Graph output нельзя считать compiler truth без
source SHA, coverage и выборочной проверки LSP/source.

## Известные опасные отказы

Самый важный критерий — не отсутствие ошибок, а невозможность **тихого
успеха на устаревшем или неполном индексе**.

- В [Serena #1814](https://github.com/oraios/serena/issues/1814) после OOM
  `tsserver` `find_referencing_symbols` мог вернуть `{}` с `isError: false`;
  для агента это неотличимо от реального отсутствия references. Issue закрыт
  20 августа 2026 года после исправления: проект отреагировал примерно за
  15 дней.
- Класс отказа не закрыт целиком: открытая
  [Serena #1937](https://github.com/oraios/serena/issues/1937) описывает
  молча частичные TypeScript references во время загрузки project graph;
  [#1923](https://github.com/oraios/serena/issues/1923) — ложное завершение
  Vue indexing, когда не открылся ни один файл; [#1939](https://github.com/oraios/serena/issues/1939)
  — недосчёт cross-package references без корректных `tsconfig` project
  references.
- [Serena #1712](https://github.com/oraios/serena/issues/1712) ранее описывала
  stale Vue/Svelte snapshots после внешних edits; также есть reports о
  [30 GB memory](https://github.com/oraios/serena/issues/944) и
  [11-часовом LLVM indexing](https://github.com/oraios/serena/issues/890).
- [Claude Context #288](https://github.com/zilliztech/claude-context/issues/288)
  показывает, что hybrid search мог пропускать точный identifier и возвращать
  нерелевантные root scripts. Другие reports описывают рассинхронизацию между
  успешным indexing status и «not indexed» search.
- [CodeGraphContext #750](https://github.com/CodeGraphContext/CodeGraphContext/issues/750)
  фиксирует 107 failures из 172 batch repos; backend fallback и watcher
  regression тоже показывают, что graph availability не равна graph truth.
- [Bloop](https://github.com/BloopAI/bloop) имеет 9,5k stars и 599 forks, но
  архивирован и не обновлялся с 2024 года — хороший пример lagging popularity.

Отсюда обязательные safeguards должны жить у вызывающей стороны, а не
надеяться на одинаковый fail-closed contract десятков language backends:
индекс сообщает checkout SHA и health; ошибка/timeout не превращается в empty
result; пустой `find_referencing_symbols` перепроверяется `rg` по имени;
health-probe использует известный symbol с известными references; новые файлы
и branch switch входят в тест; удаление и cross-file rename не выполняются на
основании одного LSP/graph ответа.

## Предлагаемый стек

### Обычный локальный репозиторий

`rg` + короткая repo map + Serena + ast-grep. Инструкция агенту:

1. Получи versioned tree/build boundaries и компактный context seed до
   первого свободного поиска.
2. Найди кандидатов lexical/structural search.
3. Для известного symbol запроси definition/references/diagnostics через LSP.
4. Открой только малый live-source slice.
5. Перед широким изменением проверь references и затронутые тесты; после —
   выполни тест/линтер.

### Огромный monorepo или много репозиториев

Сохрани Serena как semantic precision layer, а `rg` дополни Zoekt. Если
точность важнее простоты и есть platform team, SCIP/Kythe-подобная pipeline
может дать precomputed cross-repo navigation, но это уже инфраструктурный
продукт, а не MCP-плагин.

### Специализированные задачи

- Joern/Code Property Graph — security, taint и data-flow questions.
- CodeGraphContext — transitive impact, только с provenance и проверкой.
- Semantic/vector layer — поиск по расплывчатой предметной формулировке после
  доказанного miss у lexical/map/LSP.
- Repomix — переносимый snapshot для handoff или внешнего анализа небольшого
  repo.

## Проверяемый пилот

Пилот нужен на настоящем репозитории, потому что GitHub-метрики и чужие
benchmarks не измеряют ваши языки, build graph и задачи.

### Дизайн

- 24 закрытые задачи из истории; checkout фиксируется на commit до исправления.
- Gold: изменённые файлы плюс вручную подтверждённые supporting files — tests,
  configs и docs. Один diff недостаточен.
- Один model, prompt, budget и harness; два randomized повтора на задачу.
- Arm A: `rg/glob/read`.
- Arm B: A + Serena + repo map до 4K tokens + ast-grep.
- Arm C: B + CodeGraphContext либо выбранный semantic layer.

### Метрики

Gold Recall@10, шаг до первого gold-файла, tool calls, input tokens, wall time,
peak RAM, cold/update indexing time и patch test-pass. Отдельно проверить
rename, branch/worktree switch, новый файл, падение LS/indexer и unsupported
language.

### Правило решения

- Serena внутри B сначала проходит посаженные traps: известные references в
  неоткрытом файле, branch switch, новый файл и падение LS. Нужны verified
  reference recall не ниже 95% и ноль тихих ложных ответов после wrapper;
  иначе Serena удаляется независимо от экономии tokens.
- Принять repo map внутри B, если tokens до первой правки снизились минимум на
  25%. Принять ast-grep, только если его outline даёт минимум 20% экономии
  против `rg` + targeted reads.
- Весь B принимается, если test-pass ухудшился не более чем на одну задачу и
  median tokens снизились минимум на 25% **или** time-to-first-gold снизилось
  минимум на 30%; silent-stale answers — ноль.
- Принять C, только если он дополнительно выигрывает минимум 3 из 24 задач,
  которые B не локализовал, при overhead latency не более 10% и нулевых
  silent-stale answers.
- Zoekt добавляется не по слову «большой», а когда p95 горячего `rg` превышает
  примерно 2 секунды либо агент делает больше двух повторных full-repo scans
  за сессию. Порог — инженерная гипотеза пилота, а не свойство Zoekt.
- Иначе удалить дополнительный индекс. Простота baseline — полноценный
  результат, если более сложный слой не доказал выигрыш.

## Покрытие и ограничения исследования

Три независимых потока просмотрели **160 source records** до межпоточной
дедупликации: GitHub metadata, commit histories, contributor graphs, README,
LICENSE, issues, merged commits, official docs и papers. Дополнительный поиск
рассмотрел 40 результатов по исследовательским benchmark. Технические выводы
основаны на первичных источниках; roundup и vendor comparisons использовались
только для discovery.

Главный пробел: для большинства agent-native MCP нет независимых production
case studies с фиксированным model/harness. Поэтому recommendation опирается
на механизм, maintenance, failure evidence и обратимый пилот, а не выдаёт
forks и maintainer benchmark за доказанный business outcome.
