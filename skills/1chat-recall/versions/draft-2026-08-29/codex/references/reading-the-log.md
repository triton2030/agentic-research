# Восстановление покрытия памяти

## Протокол

1. Начинай только с квитанции Retrieval `recovery-needed`; сохрани её claim,
   scope, дату, diagnostics, прочитанные адреса и gaps как вход этого режима.
2. Прочитай `matched`, `returned`, `truncated`, `truncated_by`, `retrieval` и
   уникальные holder-файлы: они описывают набор кандидатов, а не широту claim-а.
3. Один раз переформулируй тот же claim как короткий естественный предмет, а не
   имя артефакта.
4. Сделай не более одного lexical-повтора с тремя-четырьмя различающими
   корнями. Русские корни указывай отдельно со `*` после устойчивой основы;
   точные имена не изменяй.
5. Разложи широкий предмет на существенные фасеты по snippets и
   `session-context`; один фасет сформулируй на языке текущей задачи. После двух
   фасетов без нового holder-а останавливайся с gap, только если не осталось
   названного следующего фасета, способного изменить claim.
6. Если hybrid недоступен, используй `--lexical`; для записей выбранных
   holder-ов используй `--timeline`, помня, что его `--limit` ограничивает
   записи, а не holder-ы. Повышай `--limit` только когда это оправдано
   усечением.
7. Если локальная модель не подготовлена, выполни `--prepare` отдельной
   командой до повторного Retrieval; не добавляй вариант запроса, который не
   способен изменить набор кандидатов:

   ```bash
   ROOT="${CODEX_HOME:-$HOME/.codex}/skills/1chat-recall"

   uv run --locked --script "$ROOT/scripts/chat_digest.py" --prepare
   uv run --locked --script "$ROOT/scripts/chat_digest.py" \
     _ops/chat-recall --query "<claim или корни>" --lexical --json
   ```

8. Открой каждую выбранную дословную запись, нужную для решения, включая адрес
   `superseded_by` или `contested_by`; rankings, cards и snippets лишь
   направляют чтение.
9. Разреши более поздние слова внутри нужных holder-ов, повтори claim с
   `--since <дата evidence>` и сравни применимых живых владельцев проекта.
   Живой owner побеждает, но предъяви оба адреса вместо молчаливого разрешения
   конфликта.
10. Заверши режим применимой позицией либо `abstain` · scope · датой · всеми
    прочитанными адресами · обычным и recovery-маршрутами · проверками более
    позднего evidence и живого owner-а · неразрешёнными gaps. Пустой recovery
    доказывает только результат проверенных маршрутов, но не отсутствие позиции
    владельца.
