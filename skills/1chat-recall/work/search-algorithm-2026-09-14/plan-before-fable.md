# План до консультации Fable — 2026-09-14

## Цель и наблюдения

Улучшить поиск точных цитат рабочим агентом, сохраняя предмет, адрес и
различение найденной опоры и кандидата. Код поиска общий по смыслу, но
runtime owners — skills/codex/1chat-recall и skills/claude/1chat-recall.
Новый посредник или пересказ не вводится. Модель, формат корпуса, Capture
и правила supersedes вне этой правки.

Наблюдения по chat_digest.py:
- search_hybrid возвращает [] до search_dense при нулевом BM25.
- search_topic_candidates допускает только lexical topics, dense их лишь
  переставляет. Отдельная тема не расширяет поиск цитат автоматически.
- --topic применяется до ранжирования: явный фильтр является строгим.
- DOMAIN_STRONG/WEAK калибруют только близость к предмету корпуса;
  в комментариях прямо зафиксировано, что они не доказывают наличие позиции.
- Выдача собирается _merge_file_rankings / _select_holders / _holder_cards;
  комментарий и метаданные темы не должны стать strongest_quote.

## Предлагаемое вмешательство в код

1. Оставить BM25 и dense независимыми источниками кандидатов в search_hybrid,
   объединять существующим RRF. Для случая только dense явно обозначать путь
   допуска, чтобы он не выглядел буквальным подтверждением. Сначала замерить
   рост посторонней выдачи: ближайший вектор существует даже для чужого вопроса.
2. Сделать поиск тем независимым объединением BM25/dense. Темы оставить
   отдельным маршрутом к исходникам, а не доказательством позиции. Рассмотреть
   ограниченное добавление разговоров подходящей темы лишь если Fable и замер
   показывают пользу сверх прямого dense; иначе не раздувать первый diff.
3. Сохранить явный --topic строгим: молча ослаблять фильтр опасно. Обычный
   запрос без него ищет по всему выбранному корпусу; автоматические темы не
   должны отсекать цитаты соседних тем.
4. Сохранить quoted text, source addresses, conflicts, chronological exclusions,
   local/offline model, explicit lexical mode, output limits и runtime differences.
   Обновить только затронутые explanations в search-mechanics/retrieval.

## Варианты и открытые вопросы к Fable

A. Только снять lexical gate: самый маленький diff, но безымянная dense-only
выдача может возвращать случайный текст на любой запрос.
B. Независимые каналы плюс явный provenance semantic-only и отдельный topic
route: предпочтительный кандидат, если формат понятен и замер приемлем.
C. Добавить reranker/query expansion/новую модель: пока нет доказанного
основания оплачивать новые зависимости и изменение масштаба.

Не использую DOMAIN_STRONG как доказательство цитаты. Нужен ли отдельный
conservative admission для semantic-only или лучше честная bounded candidate
выдача? Как отличить рост recall от передачи агенту нерелевантного мусора?

## Проверки до установки

- Зафиксировать baseline текущего движка и размеченные кейсы до правки.
- Структурные regression tests: no lexical match invokes dense; dense-only
  topic route; strict --topic; exact text/address; empty corpus; true lexical
  mode never loads embeddings; ordinary lexical hit ranking preserved.
- Реальный локальный hybrid A/B: существующие релевантные парафразы + специально
  трудные случаи без lexical overlap; явные чужие вопросы и похожие вопросы,
  на которые ответа нет; поздняя отмена и соседняя тема. Оценить hit@5,
  лишних кандидатов и задержку, не только наличие любого результата.
- Полные tests обоих runtime пакетов; файлы установки совпадают с owners.

Это предварительный план, а не принятое решение. Реализация начинается после
ответа Fable и проверки его конкретных возражений.
