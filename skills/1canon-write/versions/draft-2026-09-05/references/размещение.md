# Размещение в каноне

Вход: знание проверено, дом не назван — или рука тянется завести новый файл либо
папку.
Выход: адрес — папка и имя файла; если файл или папка новые — строка ответа
«дома не было» с областью поиска и правилом имени.

Роли проекта называет его GOAL; здесь — устройство, которое владелец задал
словами, и след, без которого его не проверить.

## Папки

- Папки внутри `_canon` — по роли: кто читает и строит. Агент, строящий одну роль,
  читает одну папку целиком; папка по теме или жанру заставляет читать всё.
- Сквозное — то, что читают две роли и больше, — одним файлом в папке роли
  «Компания», соседней с остальными; читаемое одной ролью уходит строкой в её
  файл. Копия в двух ролях расходится тихо.
- Подпапка внутри роли — только когда у роли несколько поверхностей: у студии
  вход до логина и кабинет после. Папка на одного жителя ничего не объясняет.
- Глубже — не стесняясь, если это делает список короче и понятнее: понятность
  важнее плоскости. Папка «на вырост» не заводится: пустую следующий агент примет
  за канон.
- Сценарий лежит в самой нижней папке, вмещающей все его экраны: выше он чужой
  соседям, ниже — не вмещает свои экраны.

## Имена и файлы

- Имя — вид и предмет: `Цель — Корзина`. Вид впереди сортирует список за
  Founder-а, предмет говорит всё о содержимом до открытия.
- Один вопрос — один файл; имя с союзом «и» — два дома.
- Файлов-обзоров, README и пересказов нет: обзор — это сама папка.
- «Факты» живут файлом, только если их читают две роли и больше; иначе строка
  идёт критерием в «Цель» той роли, чтобы чужая роль её не грузила.

## Канона ещё нет

- `_canon` заводится в корне проекта рядом с `_docs` (где решения рождаются) и
  `_ops/GOAL.md` (тайбрейкеры): три ступени с одними именами во всех проектах,
  иначе `1docs-write` и `1goal` ищут канон по разным адресам.
- Папки ролей — те, кто по GOAL читает и строит: покупатель, продавец, владелец
  продукта — как их называет сам проект; заводятся только под файл, который
  пишется сейчас. Папка по памяти о прошлом проекте — чужой канон.
- Вместе с папкой кладётся её `AGENTS.md` для агента-строителя по образцу ниже,
  с ролями этого проекта. Пишущему агенту хватает скила, а строитель без
  инструкции читает весь канон или дописывает его от себя.

```markdown
# AGENTS — `_canon`

## Что это за папка

Канон продукта: то, что Founder утвердил и что дорого переделать после кода.
Три вида файлов — «Цель», «Сценарий», «Факты» — по папкам ролей; сквозное — в
«Компании». Пишет агент со слов Founder-а скилом `1canon-write`; вход для
любого документа — `1docs-write`.

## Что ты здесь делаешь

- Читаешь `_ops/GOAL.md`, папку «Компания» и папку своей роли. Больше не нужно:
  папки нарезаны по ролям затем, чтобы агент, строящий одну роль, не грузил
  другую.
- Строишь так, чтобы каждый критерий из «Цели» стал правдой. Устройство — твоё:
  критерий говорит «что», не «как».
- Нашёл, что канон противоречит сам себе или GOAL, — не выбирай версию сам.
  Покажи Founder-у оба места: канон его.

## Чего ты здесь не делаешь

- Не дописываешь канон от себя: каждая строка восходит к словам Founder-а или
  утверждённому решению. Правдоподобное дополнение агента становится решением,
  которого Founder не принимал.
- Не кладёшь сюда устройство, задачи, находки и статус: устройство живёт в коде,
  задачи — в `_ops`, сырьё решений — в `_docs`.
- Не заводишь файл-обзор, README или карту папки: обзор — это сама папка и
  имена в ней.
```

## След

- Область поиска назови до поиска и запиши отвергнутые имена с причиной: без
  них «дома не было» неотличимо от «не искал».
- Новый файл или папка — отдельной строкой ответа: Founder должен видеть каждый
  прирост поимённо, а не находить его через месяц.
