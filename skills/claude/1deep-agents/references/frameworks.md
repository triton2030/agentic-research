# Framework Routing Seed

This is a compact recall and contrast seed, not a whitelist, candidate boundary
or framework encyclopedia. Situational fit and expected cognitive delta outrank
presence in this file. A better established method outside the list must be
selected when it fits the task more strongly. The seed keeps only the task fit
and compact operational adapters needed to brief a capable clean agent; these
are not claims of canonical branded wording. Do not load full framework essays
into every stream.

The domain headings below are storage shelves, not a routing taxonomy. Start
from the task's underlying cognitive work, then search for a framework with the
same relational mechanism even when it originated in another field. Transfer
framework entities to task entities; do not adapt, shorten, reorder or combine
the selected methodology itself. If the compact spine cannot be defended as the
method's established procedure, verify its primary lineage before spawn.

Contents:

- Framing, reasoning and causality
- Options, decisions and risk
- Programming and software or system architecture
- Database and data architecture
- Information architecture
- Selection boundaries and lineage

## Framing, Reasoning And Causality

### First-Principles Decomposition

Use for inherited assumptions or solution-shaped questions.
Spine: define outcome → list assumptions and components → separate hard facts
from conventions → reduce to necessary constraints → rebuild options from those
constraints → test the rebuild against reality.

### Abstraction Laddering

Use when the problem may be stated at the wrong altitude.
Spine: state the current frame → move upward with `why` to purposes → move
downward with `how` to concrete forms → generate alternative frames at several
levels → choose the most useful altitude → restate the problem there.

### Issue Tree

Use for a broad question that must become an analyzable set of subquestions.
Spine: state the governing question → choose one decomposition logic → build
branches → test coverage and overlap → identify evidence needed at leaves →
prioritize leaves → recombine answers into the governing conclusion.

### TRIZ Contradiction Resolution

Use when improving one property appears to worsen another.
Spine: name the improving and worsening properties → formulate the technical
contradiction → test separation in time, space, condition and system level →
generate solutions that remove the coupling → test whether the contradiction
was dissolved or merely hidden.

### Ladder Of Inference

Use when a confident conclusion may contain unexamined interpretation.
Spine: name the action or conclusion → walk down through assumptions and
meanings → recover selected observations → compare with the fuller observable
data → test alternative interpretations → walk back up to a revised conclusion.

### Toulmin Argument Model

Use to expose why an argument does or does not support its claim.
Spine: state claim → list grounds → make the warrant explicit → add backing →
set qualifier or confidence → surface rebuttals and exceptions → revise the
claim or warrant.

### Competing Causal Hypotheses

Use when several causes could explain one symptom or outcome.
Spine: state the observation → form at least two genuinely distinct hypotheses
→ derive different predictions → choose a discriminating probe → compare the
result with predictions → update or eliminate hypotheses → name the next probe
or bounded conclusion.

Do not call three phrasings of one cause competing hypotheses. This is the
scientific-method move, not the branded ACH matrix.

### Causal Loop Diagramming

Use when feedback, delay or non-linear behavior dominates.
Spine: name material variables → draw directed causal links → assign link signs
→ close loops → label reinforcing and balancing loops → mark delays → explain
observed behavior → identify leverage points and tests.

### Theory Of Constraints

Use when throughput is capped by one current bottleneck.
Spine: identify the constraint → exploit it without major investment →
subordinate other work to it → elevate it if still binding → verify throughput
change → repeat because the constraint may move.

## Options, Decisions And Risk

### Morphological Analysis

Use when the option space is narrow because dimensions were bundled too early.
Spine: define the system → choose independent dimensions → list plausible values
per dimension → cross-combine configurations → remove internally inconsistent
combinations → develop and test the most promising survivors.

### Multi-Criteria Decision Analysis

Use when explicit trade-offs among named alternatives matter.
Spine: define alternatives → derive criteria from the outcome → set weights
before seeing scores → score with evidence and uncertainty → aggregate → run
sensitivity analysis → decide or identify what evidence would flip the result.

### Expected-Value Decision Tree

Use when choices contain quantifiable chance events.
Spine: draw decision and chance nodes → assign outcomes → assign probability
ranges → roll values backward → compare expected value and downside exposure →
run sensitivity → state what would flip the choice.

### Minimax Regret

Use under deep uncertainty when trustworthy probabilities are unavailable.
Spine: define options and plausible states → estimate outcome per cell → compute
regret relative to the best option in each state → find maximum regret per
option → choose the smallest → stress-test omitted states and irreversibility.

### Reference-Class Forecasting

Use when inside-view plans or estimates are likely optimistic.
Spine: define the target outcome → choose a defensible reference class → recover
its outcome distribution → locate the current case → adjust only for evidenced
differences → return a range and confidence → name what would change the class.

### Scenario Planning

Use when strategy must survive divergent external futures.
Spine: set focal question and horizon → identify driving forces → choose the
most critical independent uncertainties → construct divergent internally
consistent scenarios → test the decision in each → find robust moves,
contingencies and signposts.

### Backcasting

Use when the desired future is clearer than the path from the present.
Spine: specify the future state and evidence it exists → move backward through
necessary prior states → identify dependencies and decision points → compare
with present reality → choose first actions → name triggers for revising the
path.

### Premortem

Use immediately before commitment to expose plausible failure paths.
Spine: assume the plan has failed → generate independent causes → cluster and
rank by impact and plausibility → identify leading signals → design prevention
or containment → assign kill or pivot criteria → name residual risk.

## Programming And Software Or System Architecture

### Scientific Debugging

Use for broken, flaky, slow or surprising runtime behavior.
Spine: state the exact symptom → reproduce it → separate observation from
interpretation → form competing causes → run the cheapest discriminating test →
localize root cause → make the smallest causal repair → run regression evidence.

### Design By Contract

Use when an interface is ambiguous about caller and callee responsibility.
Spine: name client and supplier → define preconditions → define postconditions →
define invariants → specify failure semantics → test boundary and invalid cases
→ check whether callers need hidden knowledge.

### Quality-Attribute Scenario Analysis

Use before choosing architecture tactics for a non-functional requirement.
Spine: name stimulus source → stimulus → operating environment → affected
artifact → required response → measurable response target → compare tactics and
conflicts → convert the target into a fitness function or acceptance probe.

### ATAM-Lite

Use for a material architecture choice with competing quality attributes.
Spine: recover business drivers → prioritize quality-attribute scenarios → map
architecture approaches and tactics → identify sensitivity points → identify
trade-off points → classify risks, non-risks and open questions → choose
evidence that resolves the highest-risk trade-off.

### Domain-Driven Design Strategic Modeling

Use when domain language, ownership and service boundaries are unclear.
Spine: map capabilities and domain rules → classify core, supporting and generic
subdomains → identify competing models and language → draw bounded contexts →
map context relationships → assign ownership → test boundaries with change
scenarios and invariants.

### Event Storming

Use to discover domain behavior and seams from a business process.
Spine: place domain events in time → add commands and actors → add external
systems → connect policies and reactions → mark hotspots and questions → group
events around consistency boundaries → propose aggregates and bounded contexts
→ validate with domain experts or evidence.

### Wardley Mapping

Use when technical architecture is inseparable from build, buy, commodity and
evolution choices.
Spine: name user and need → map the value chain → expose dependencies → place
components by evolution stage → examine movement, climate and doctrine →
generate strategic plays → test assumptions and revisit as components evolve.

### Change-Amplification And Deep-Module Analysis

Use when an interface may leak knowledge or make ordinary changes spread.
Spine: choose representative future changes → trace files, callers, concepts and
knowledge each change touches → locate repeated or leaked decisions → identify
shallow seams → redesign ownership or interface to hide complexity → replay the
same changes and compare spread.

### STPA Safety Analysis

Use for software-intensive systems where component reliability alone cannot
explain unacceptable loss.
Spine: define losses → derive hazards and safety constraints → model the control
structure → identify unsafe control actions → construct causal loss scenarios →
derive additional constraints and controls → define verification evidence.

### STRIDE Threat Modeling

Use for security analysis of a system or data flow.
Spine: identify assets and security objectives → draw data flows and trust
boundaries → enumerate spoofing, tampering, repudiation, disclosure, denial and
privilege threats → rank credible abuse paths → select mitigations → verify them
→ state residual risk.

## Database And Data Architecture

### Access-Pattern-First Data Modeling

Use when a logical model must survive real reads, writes and scale behavior.
Spine: inventory representative queries and write paths → state consistency and
latency targets → model facts, identities and relationships → choose keys,
indexes and partitions → model hot paths and failure modes → plan evolution →
validate with representative workloads.

### Functional-Dependency Normalization

Use when duplicate facts and update anomalies threaten relational integrity.
Spine: list attributes and facts → identify candidate keys → state functional
dependencies → decompose toward 3NF or BCNF → verify lossless join and dependency
preservation → test anomalies → denormalize only for a measured access need.

### Transaction-Boundary And Invariant Analysis

Use when atomicity, aggregates or distributed workflows are unclear.
Spine: state business invariants → list commands and concurrent actors → decide
which facts must change atomically → draw transaction or aggregate boundaries →
design cross-boundary coordination → model retries and partial failure → test
invariants under concurrency.

### CAP And PACELC Trade-Off Analysis

Use for distributed data choices where consistency, availability and latency
cannot all be assumed.
Spine: define the partition scenario → choose consistency or availability per
operation during partition → analyze latency versus consistency otherwise →
specify conflict and reconciliation semantics → define recovery targets → test
the chosen behavior under fault and normal load.

### Data Lineage And Lifecycle Analysis

Use when truth, ownership, retention or change impact is unclear across a data
pipeline.
Spine: identify sources and owners → trace transformations and contracts → map
stores and consumers → attach provenance and quality checks → define access,
retention and deletion → simulate a source/schema change → add observability and
recovery ownership.

## Information Architecture

### Object-Oriented UX

Use when navigation and interaction should follow durable domain objects.
Spine: identify objects → map relationships → list calls to action → attach
attributes → prioritize objects and actions → derive navigation and views → test
whether users can find an object and complete its top action.

### Faceted Classification

Use for a large heterogeneous corpus that needs combinable filters.
Spine: inventory content and user tasks → define independent facets → define
values and exclusivity rules → map items to facets → design combination rules
and labels → test representative retrieval tasks → revise ambiguous facets.

### LATCH Organization

Use to choose a primary organizing principle for an information set.
Spine: inventory the items and user question → compare Location, Alphabet, Time,
Category and Hierarchy → choose the principle that best answers the task → sort
and label → expose secondary routes only when earned → test findability.

### Card Sorting To Tree Testing

Use when the user's mental grouping is unknown and a proposed hierarchy needs
validation.
Spine: choose representative content and participants → run open or closed card
sorting → capture groups and labels → analyze stable patterns and outliers →
propose hierarchy → run tree tests on top tasks → revise and repeat.

### Information Scent And Top Tasks

Use when users cannot predict where a needed item or action lives.
Spine: identify top tasks → map entry points, labels and competing noise →
predict the strongest scent path → observe findability attempts → locate scent
loss → rename, regroup or remove noise → measure task success and backtracking.

### Concept Mapping

Use when relationships among concepts are the information product.
Spine: list key concepts → arrange a provisional hierarchy → connect them with
relationship labels that form propositions → add cross-links → locate gaps,
cycles and contradictions → revise → derive navigation, model or explanation.

## Selection Boundaries And Lineage

- Derive the needed cognitive jobs from the task before consulting this seed.
  Never restrict selection to the names below or reward a listed method merely
  for being easy to retrieve.
- Diagnose the task below its surface domain: identify the representation,
  inference, choice, uncertainty, feedback or failure mechanism that must
  change. Match frameworks by relational structure, not shared vocabulary or
  profession.
- Select an unlisted established framework whenever it offers the strongest
  situational fit and decision-changing cognitive move. State its complete step
  spine and topology in the brief. Verify primary lineage when the sequence is
  uncertain or an exact canonical/branded procedure was requested.
- Cross-domain transfer maps framework entities and inputs onto the task while
  preserving the original mechanism, complete step spine, topology and
  completion condition. A transfer that needs omitted, reordered, invented or
  hybrid steps is structural no-fit, not creative adaptation.
- Choose one framework per agent. A chain such as `scenario planning →
  premortem → backcasting` is three frameworks and therefore three streams.
- Prefer a method whose output can change the current decision. Fame, evidence
  tier or technical vocabulary cannot rescue structural no-fit.
- Treat branded or contested methods conservatively. If exact procedure matters
  and this seed is insufficient, verify the primary method owner before spawn.
- General frameworks complement domain-native architecture methods; they do not
  replace them on technical decisions.
