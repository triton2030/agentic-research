# Эксперты Вопросов

## Результат

Один или несколько question-only чек-листов от профессиональных линз:
финансист, маркетолог, юрист, безопасник, product, ops, founder и т.д. Каждый
чек-лист говорит, что с точки зрения этой роли должно быть правдой, какие
вопросы она обязана поставить и почему это важно.

Назначение generative: эксперт задаёт критерии и вопросы до ответов. Он не
оценивает готовую работу, не пишет решение и не превращает рабочую папку в
канон. Дальше главный агент или пользователь проходит по списку отдельно.

## Вход / Пропуск

Используй при запросах вида:

- "вызови экспертов", "нанять консультанта", "поставь вопросы финансиста";
- "что бы спросил CFO / CMO / юрист / безопасник";
- "сделай expert checklist", "questions only", "стресс-тест вопросами";
- "посмотри как внешний профессионал, но ответы пока не пиши".

Пропускай критику или review готового артефакта, выбор подхода, когнитивный
reframe, формы для пользователя, аудит предпосылок принятого плана и
декомпозицию задачи. Это соседние workflows, а не question-only expert pass.

## Claude Runtime

Запускай question-only экспертов через native `Agent` tool с
`subagent_type: general-purpose`. Несколько независимых профессий можно
отправить параллельно одним сообщением; каждая получает отдельный domain и
output file. Named critics из `1fresh-eyes` являются evaluative соседями и не
подходят для генерации вопросов.

Если `Agent` недоступен, сгенерируй checklist локально и честно назови его
профессиональной линзой в текущем контексте, а не свежим subagent-view.

## Default Path

1. Назови цель: какой проект, документ, решение или бизнес-область нужно
   проверить вопросами.
2. Выбери 1-5 профессий-линз. Одна профессия = один домен = один файл. Не
   запускай две линзы в один и тот же домен.
3. Прочитай только owner-минимум: 1-2 ключевых файла цели, локальный `AGENTS.md`
   или project goal, если они меняют scope. Экспертный взгляд должен оставаться
   сверху, не тонуть в корпусе.
4. Конкретизируй линзу: не ярлык "финансист", а угол зрения, зоны проверки,
   чему роль не верит и что для неё крупная дыра. Вопросы не подсказывай.
5. Выбери режим:
   - явная просьба про экспертов/субагентов/параллельность → запусти по одному
     `general-purpose` subagent на линзу через `Agent`;
   - нет явной просьбы на делегацию -> сгенерируй вопросы локально и не называй
     результат свежим subagent-view.
6. Пиши в рабочий слой. Если в проекте уже есть non-canon expert/stress-test
   folder, используй его. Иначе default:
   `_Workspace/Expert-Questions/Вопросы/`, ответы потом в
   `_Workspace/Expert-Questions/Ответы/`.
7. Сохрани сырой checklist каждой линзы. Не фильтруй молча "важное"; максимум
   добавь отдельную сводку после raw-файлов.

Шаблон brief и примеры линз вынесены в
[`references/prompt-template.md`](references/prompt-template.md). Читай его
перед запуском subagents или когда локальная генерация начинает пахнуть generic
учебником.

## Gotchas

- **Question-only is default.** Ответы не писать, пока пользователь явно не
  попросит второй проход.
- **Generic lens даёт generic вопросы.** Разверни профессию в угол зрения и
  дай 1-2 source-файла, иначе получится учебник.
- **Не делай работу за эксперта.** Если в brief уже вставлены готовые вопросы,
  свежая линза исчезла.
- **Рабочий слой не канон.** Принятые решения потом разносятся по owner-файлам
  или task/plan owner-ам; вопросник сам по себе не source of truth.
- **Критика готового = другой skill.** Этот skill говорит "что должно быть
  проверено", а не "хорошо ли сделано".

## Проверка

Готово, когда:

- создан по одному файлу на каждую профессию-линзу;
- внутри вопросы/критерии без ответов;
- пункты идут от главного к мелкому и привязаны к текущему проекту;
- домены экспертов не дублируются;
- путь явно обозначен как рабочий non-canon слой.

## Остановка

Остановись после созданных question checklists и короткого closeout: какие
линзы использованы, куда записано и какой следующий owner нужен для ответов,
планирования или принятия решений.
