# Флот воркеров — Codex пишет файлы ПРОЕКТА

**Владеет:** волной воркеров на ЛЮБОЙ её фазе — нарезка, запуск, надзор за
воркерами, вмешательство, остановка, закрытие, деревья и ветки.
**Никогда не держит:** то, что верно прогону любого вида (это
[`orchestration.md`](orchestration.md)) и то, что переживает прогон (это
[`threads.md`](threads.md)).

Проверка правила: перестаёт ли оно быть верным, если в файлы проекта ничего не
пишется. Да → сюда, на какой бы фазе оно ни применялось.

Читай это перед запуском пишущего флота. Контракт волны — `1orchestration`;
ты — оркестратор, здесь только bridge-дельты. (Артефакты «себе, не в проект» —
это исследователь `codex_investigate.py`, не флот.) Ярус и фоновый запуск —
`SKILL.md` и [`orchestration.md`](orchestration.md).

## Каждый воркер — в своём дереве

По умолчанию (`--isolation worktree`) прогон заводит воркеру отдельный git
worktree от текущего HEAD и работает там. Это меняет три вещи по существу:

- **Атрибуция.** Diff считается в его дереве, поэтому «кто написал этот файл» —
  факт, а не догадка. В общем дереве воркер A мог задеть файл воркера B, и
  union-чек проходил у обоих.
- **Отбраковка.** Запись вне его списка файлов в проект не попадает — но и не
  теряется: любая внесписочная правка удерживает от merge ВСЮ работу воркера
  (правка по списку могла на неё опираться), и всё изменённое целиком
  фиксируется в его ветке на ручной разбор.
- **Свобода тебе.** Пиши recall, планы и артефакты в основном дереве, пока волна
  идёт: волну это больше не валит. Раньше валило — 68% записей
  `out_of_scope_files` по 106 боевым волнам были твоим же служебным шумом.

Цена честная: дерево — выкладка проекта (22 МБ на `agentic-research`, 650–780 МБ
на большом фронтенде), и воркеры не видят правок друг друга. Задачам, которые
обязаны видеть чужие правки, нужен `--isolation shared` — прежнее поведение с
aggregate-чеком.

## Сколько воркеров

Читающий веер бесплатен, пишущий платит диском. Поэтому **единица деления у
пишущих — группа задач, а не задача**: двадцать дел это четыре воркера по пять,
каждому `subagents: true`. Связную работу (одна фича, один слой) не дроби
вовсе — целиком у одного дешевле. Число воркеров выбирай по цене дерева и
связности, не по числу дел.

Делегация внутрь воркера нужна явным словом: системный промпт движка запрещает
субагентов, пока их не попросят — «Do not spawn sub-agents unless the user or
applicable AGENTS.md/skill instructions explicitly ask». Независимым взглядом
они не являются: наследуют рамку родителя.

## Запуск

1. **Разрежь работу на file-disjoint задачи** — два воркера не правят один
   файл. Footprint должен быть известен заранее точными путями: не знаешь набор
   файлов → это ещё не задача флота, сперва discovery (исследователь/чтение).
2. Собери JSON-массив: `[{"id","prompt","files":[...]}]`. Одна запись = один
   воркер = его группа дел: список дел живёт в `prompt`, а `files` покрывает их
   все. `prompt` и `files` обязательны; `files` — exact file paths, не папочные
   scopes; `cwd` в задаче запрещён; для нового файла `allow_create: true`;
   чтобы воркер делил свою группу дел на субагентов — `subagents: true`;
   ремонтная волна кладёт в задачу `thread_id` воркера прошлой (см. «Ремонтный
   круг» ниже). `id` идёт в путь дерева и имя ветки: без `/`, пробелов и
   git-спецсимволов, уникальный в волне.

   В карту волны и её носитель (`context.md` папки волны либо план) handle
   воркера пиши как `thread_id` + `RUN_DIR`: без них новое окно после обрыва
   восстанавливает соответствие «воркер → тред» вручную. Сами треды не
   теряются — они персистентны, их печатает `codex_threads.py mine`.
3. Запусти пул:

```bash
B=/Users/triton/Documents/GitHub/agentic-research/experiments/codex-bridge
echo '[{"id":"t1","prompt":"...","files":["a.md"]}]' \
  | $B/.venv/bin/python $B/codex_orchestrate.py --project "$PWD" --summary-stdout
# большой список — через файл: --tasks tasks.json ; сухой план запуска: --dry-run
# --concurrency N — сколько воркеров разом; дефолт 4, передавай только другое
# --verify "команда" — повтори флаг для КАЖДОЙ проверки, которую иначе прогнал бы руками после интеграции. В дефолтном worktree это ворота: проверка идёт по временному СЛИТОМУ дереву до merge (красный исход — ниже). При --no-integrate пропускается, при --isolation shared ворот нет — воркеры уже в проекте
# посмотреть работу до забора в проект: --no-integrate (деревья и ветки остаются)
```

`--concurrency N` = сколько воркеров одновременно (50 задач идут волнами).
Выход — `result.json` с `worker_status`, `scope_status`, `verification_status`,
`wave`, `fully_verified`, `ok`, `run_dir` и результатами воркеров. **В stdout
компактной проекции ответов воркеров нет** — за ними иди в `result.json`.

## Надзор за волной

Общий надзор — [`orchestration.md`](orchestration.md); у волны три отличия:

- Строка `задание:` в сводке перечисляет ВОРКЕРОВ, а не их задачи. Точное
  задание конкретного воркера — в `manifest.json` прогона, `tasks[].prompt`.
- «Движется?» у флота читается по `stalest` — молчащий дольше всех воркер, а не
  агрегат: средний пульс живой волны прячет вставший воркер. Рядом `active`, и
  активность помечена id воркера.
- В доске `--board` у волны, закрытой без уборки, стоит `ДЕРЕВЬЯ-ВИСЯТ`.
- Реплика требует адресата: `--steer` без `--worker` команда отклоняет и
  печатает состав волны.

**Владелец смотрит воркеров в Codex Desktop.** Тред воркера материализован
намеренно, поэтому каждый виден чатом в приложении — живой прогресс без твоего
участия. Имени мост треду не задаёт, поэтому «который чат чей» определяется по
`thread_id` из `results.jsonl`, а не по названию.

## Закрытие волны идёт само — проверь, что оно случилось

Прогон закрывает волну сам. Несущее: **работа не удаляется никогда** — коммит
в ветку воркера делается до любой уборки, даже когда интеграции не будет.

В проект НЕ вливается — работа целиком остаётся в ветке воркера на ручной
разбор (дерево при уборке сносится, ветка живёт):

- ход воркера не завершился — полуфабрикат не едет в проект;
- воркер писал вне своего списка — половину работы взять нельзя, он мог на
  лишнее опереться;
- дерево родилось грязным **в зоне воркера** (`held_dirty_birth`: post-checkout
  hook писал в файл из его списка — чьё там что, недоказуемо). Посторонний
  артефакт того же hook воркера не держит и в ветку не попадает: боевая волна
  `20260814T085606Z` удержала всех троих из-за одного чужого `.png`, и восемь
  готовых файлов не влились;
- история переписана ниже базы волны (`held_base_rewritten`);
- merge конфликтует — контракт был нарушен;
- проверка волны красная (`held_verify_failed`): воркеры сливаются во временное
  дерево, `--verify` идёт там, и провал оставляет проект нетронутым — в `main`
  не попадает ничего, даже от чистых воркеров.

Что читать в `wave` из результата:

| Поле | Что значит |
|---|---|
| `integration_status` | `integrated` · `partial` (часть удержана) · `conflict` · `held` (`--no-integrate`) · `error` |
| `merged` | воркеры, чья работа уже в проекте |
| `held` / `conflicts` | не влиты: работа цела в ветке, забирать вручную |
| `kept_branches` | **незабранная работа** (held/conflict/уехавшие вперёд/не удалившиеся) — разбери до следующей волны; merged-ветки при `--keep-worktrees` сюда не попадают |
| `cleanup_done` | факт с диска, не просьба; `cleanup_stuck` — что не удалилось |
| `threads_archived` / `threads_stuck` | исход тредов воркеров: снят вместе с деревом либо остался висеть карточкой-проектом (почему — [`threads.md`](threads.md)). Оба пусты при `--keep-worktrees` — там дерево живо |
| `main_tree_drift` | что менялось в основном дереве во время волны (обычно твоё) |

Уборка не заканчивается словом «убрал»: назови `cleanup_done`,
`kept_branches` и `threads_archived`.

## Остановка волны

Мост **interrupt на асинхронном пути не подключил** (SDK его даёт — расхождение
записано находкой 2026-08-16). Прогон успевает зафиксировать работу воркеров в
их ветках и напечатать их, но `result.json` не пишется, а деревья остаются.
После остановки ручки — `git worktree list` и `git branch --list 'codex-fleet/*'`;
прерванную волну проверь руками.

Инвентарь и ручная уборка — готовым git, обёрток для них мост не держит:

```bash
git worktree list                     # чьи деревья висят (наши — в ~/.codex-bridge)
git worktree remove <path>            # откажется, если внутри незакоммиченное
git worktree prune                    # выкинуть мёртвые записи
git branch --list 'codex-fleet/*'     # незабранная работа воркеров
```

Деревья под `~/.codex/worktrees` создаёт Codex Desktop/CLI, а не мост: там
может лежать незабранная работа владельца (запрет на ручное удаление —
[`threads.md`](threads.md)).

## Ремонтный круг

Тёплым воркером: в задаче следующей волны тот же `id` + `thread_id` из
`results.jsonl` прошлой. Дерево, файловый контракт и `--run-dir` всё равно
свежие — «доделай в том же процессе» не существует. Тред у пишущего воркера
есть по праву; чтение и ревью обходятся без него. Второй круг без сходимости —
свежий воркер, без `thread_id`. Счётчик кругов и порог остановки — в теле,
«Stop»; чем мерить сходимость — [`orchestration.md`](orchestration.md).

## Контракт (нарушишь — потеряешь правки)

- **File-disjoint enforced.** Backend reject-ит overlap до запуска Codex. Это
  runtime enforcement общего правила `1orchestration`: пересекающиеся записи
  получают одного писателя либо последовательный handoff.
- **Prompt-обещания ⊆ files.** Каждый путь, который prompt задачи называет к
  записи («положи в X»), проверь в `files` до запуска: запись вне списка
  удержит от merge всю работу воркера, и волна закончится ручным разбором
  ветки вместо результата (реальный случай: протокол вынесли из memo, а его
  новый дом в `files` не положили).
- **Preflight fail-closed.** Невалидный JSON задач падает ДО запуска Codex —
  кредитов это не стоит, ошибку читай в выводе инструмента.
- **Git fail-closed.** Реальный запуск требует git (`--dry-run` работает и без
  него, помечая `git.available=false`), а worktree-изоляция — ещё и `--project`
  в корне репозитория: от подпапки allowlist и дерево считались бы от разных
  корней. Если dirty files пересекаются с `files`, запуск блокируется (иначе
  merge перетрёт твою правку); override осознанный: `--allow-dirty-overlap`.
- **HEAD вперёд — можно, назад — нельзя.** Свои коммиты поверх во время волны
  (recall, планы) — норма, merge их переживает. А `reset`/`rebase` ниже базы
  волны удерживает всех воркеров (`held_base_rewritten`): merge в переписанную
  историю принёс бы разницу веток как «работу воркера».
- **Max-safe permissions.** Default не `full-access`: такой режим может менять
  файлы вне project/git scope, а backend не сможет доказать allowlist. Максимум —
  `workspace-write` внутри дерева воркера + backend guardrails.
- **`scope_status=failed` остаётся failure.** В изоляции он означает запись вне
  allowlist в дереве воркера либо сорванную интеграцию — читай
  `out_of_scope_files` и `wave`. Легитимный deterministic side effect объяви в
  footprint до следующего запуска.
- **`worker_status=completed` не равно done.** Механическая проверка перед
  доверием: `--verify`, `git diff`, тесты. (Почему самоотчёт не evidence — в
  теле, «Дисциплина запуска».)
