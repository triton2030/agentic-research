# Исполнение: Codex делает работу

**Вход:** работа отдаётся целиком, а не выносится на суждение. **Выход:**
результат в проекте либо артефакт, который ты забрал. Берись за эту роль, когда
более высокая уже неприменима.

| Куда падает результат | Вход |
|---|---|
| себе в папку прогона, проект для записи недостижим | `codex_investigate.py "ЗАДАНИЕ + формат выхода" --project "$PWD" --summary-stdout` |
| в файлы проекта | `codex_orchestrate.py` — волна воркеров, контракт ниже |
| адреса в markdown-корпусе | `(cd /Users/triton/Documents/My_projects/md-tools && uv run python scripts/run_md_scout.py КОРПУС --question "ВОПРОС")` — read-only executor `1md-search`, без вердиктов; приёмка по пакету, не по exit code |

**Веер вместо одного прогона** — когда работа делится: каждому свой участок или
своя ось. Схема выхода одна на весь веер, иначе пять форм ответа ты нормализуешь
в своём окне, ради экономии которого веер и заводил.

Минимум схемы, ниже которого возвраты снова читаются, а не просматриваются:
первая строка — вердикт; дальше по пункту на вывод — прибор и его exit code
дословно, адрес `путь:строка`, блокеры отдельно. Логи целиком не заказывай: они
и так лежат в `run_dir`, а в возврате стоят твоего окна. У воркеров флота этот
минимум просит сам мост — там задавай только ось, специфичную для задачи.

**Волна начинается только с точных путей, и полноту списка доказывает критерий
приёмки, а не промпт:** обе стороны `prompt ⊆ files` пишет одна рука в один
заход. Что критерий велит убрать или изменить — имя, поведение, свойство —
считай `rg` по СОДЕРЖИМОМУ проекта: фильтр по именам файлов носители теряет.
Содержимым не ищется — тогда `codex_investigate.py` с формой выхода «точные пути
записи», и лишь с этим списком запускай флот.

## Дерево на воркера — что оно меняет

По умолчанию (`--isolation worktree`) каждому воркеру заводится git worktree от
текущего HEAD:

- **Атрибуция.** Диф считается в его дереве, поэтому «кто это написал» — факт.
- **Отбраковка.** Запись вне списка файлов в проект не попадает, но и не
  теряется: любая внесписочная правка удерживает от merge ВСЮ работу воркера
  (правка по списку могла на неё опираться), и всё изменённое целиком лежит в его
  ветке.
- **Свобода тебе.** Пиши recall, планы и артефакты в основном дереве, пока волна
  идёт: волну это не валит.

Цена честная: дерево — выкладка всего проекта, и воркеры не видят правок друг
друга. Задаче, обязанной их видеть, нужен `--isolation shared` — прежнее
поведение с общей проверкой охвата.

**Мост сам говорит каждому воркеру** его зону, состояние дерева и отказы
песочницы, невидимость соседей, запрет симлинка вместо установки, объявленные
контракты и форму возврата. В задании не повторяй ничего из этого — оно доезжает
до каждого бесплатно для тебя; точный текст волны — `manifest.json`,
`tasks[].developer_instructions`.

## Нарезка

**Единица деления у пишущих — группа задач, а не задача:** двадцать дел это
четыре воркера по пять, каждому `subagents: true`. Связную работу — одну фичу,
один слой — не дроби вовсе, целиком у одного дешевле. Число воркеров выбирай по
цене дерева и связности, не по числу дел.

Делегация внутрь воркера нужна явным словом: системный промпт движка запрещает
субагентов, пока их не попросят. Независимым взглядом они не являются —
наследуют рамку родителя.

**Непересечение файлов зону не доказывает.** Два воркера без единого общего
файла сталкиваются через общий смысл: один меняет семантику, второй её
характеризует, merge зелёный, поломка тихая. Поэтому судящий воркер — аудитор,
характеризатор, верификатор — не идёт в одну волну с тем, кто меняет его
предмет: он идёт следующей волной, по уже слитому дереву. Где смысл делится
шире одной пары ролей, объявляй его `contracts_changed` и `contracts_read`:
backend режектит до траты волну, в которой один меняет контракт, который другой
меняет или читает. Сверка буквальная, поэтому имя контракта бери адресом
(`путь#символ`), а не описанием — и молчание backend'а о контрактах значит лишь,
что сверять было нечего.

Задача воркера: `{"id","prompt","files":[...]}`. Список дел живёт в `prompt`,
`files` покрывает их все точными путями, не папочными scope; `cwd` запрещён; новый
файл — `allow_create: true`; тёплый воркер прошлой волны — `thread_id` из её
`results.jsonl`. `id` идёт в путь дерева и имя ветки: без `/`, пробелов и
git-спецсимволов, уникальный в волне.

**Ярус объявляет задача, а не прогон:** `model` и `effort` лежат в самой задаче,
флаги запуска остаются дном для тех, кто молчит. Поэтому пишущие на
`gpt-5.6-luna` и судящие на `gpt-5.6-sol` идут ОДНОЙ волной — резать логически
одну работу на два флота ради разных ярусов больше не нужно.

Handle воркера пиши в носитель волны как `thread_id` + `RUN_DIR`: без них новое
окно после обрыва восстанавливает соответствие «воркер → тред» вручную. Сами
треды персистентны и находятся `codex_threads.py mine`.

```bash
B=/Users/triton/Documents/GitHub/agentic-research/experiments/codex-bridge
echo '[{"id":"t1","prompt":"...","files":["a.md"]}]' \
  | $B/.venv/bin/python $B/codex_orchestrate.py --project "$PWD" --summary-stdout
# большой список — --tasks tasks.json ; сухой план — --dry-run (это план, не результат)
# --concurrency N — сколько разом, дефолт 4 ; --no-integrate — посмотреть до забора
# --verify "команда" — повтори для КАЖДОЙ проверки, которую иначе прогнал бы руками
#   после интеграции: в worktree это ворота по временному СЛИТОМУ дереву до merge
# --tree-setup "команда" — готовит КАЖДОЕ дерево воркера и слитое дерево
# --run-dir ПУТЬ — папка обязана НЕ существовать: mkdir -p заранее гасит волну
```

**`--tree-setup` обязателен там, где приборы нужны в дереве.** Свежий worktree
несёт только версионированное, поэтому `npm test` и его родня падают по среде и
у воркера, и в воротах волны. Файл, который тронет подготовка, не может быть в
`files` задачи: волна отказывается до траты, потому что в таком файле работу
воркера от кодогенерации уже не отличить.

Ответов воркеров в компактном stdout нет — за ними иди в `result.json`; там же
`verification_status` и `fully_verified`, по которым проверка и засчитывается.

**`--verify` — ворота не всегда.** В дефолтном worktree он идёт по временному
слитому дереву до merge; при `--no-integrate` пропускается вовсе, при
`--isolation shared` отдельных ворот нет — воркеры уже в проекте. Переданный флаг
проверенности не доказывает: сверяй фактическую квитанцию в `result.json`.

## Контракт: нарушишь — потеряешь правки

- **Два воркера не правят один файл.** Backend режектит пересечение до запуска —
  это runtime-исполнение общего правила `1orchestration`.
- **Узкая зона хуже пустой.** Запись вне списка удержит от merge всю работу
  воркера, но упёршийся в границу воркер чаще возвращает другое: алиас
  совместимости, сохраняющий ровно то имя, которое критерий велел убрать.
- **Fail-closed до траты:** невалидный JSON падает ДО запуска Codex. Реальный
  запуск требует git; `--dry-run` работает и без него, помечая
  `git.available=false`. Worktree-изоляция требует `--project` в корне репозитория; пересечение
  dirty files со списком блокирует запуск, осознанный override —
  `--allow-dirty-overlap`.
- **HEAD вперёд можно, назад нельзя.** Свои коммиты поверх во время волны — норма;
  `reset`/`rebase` ниже её базы удерживает всех воркеров.
- **Максимум прав — `workspace-write` внутри дерева воркера.** `full-access` не
  дефолт намеренно: в нём backend не может доказать allowlist.
- **`worker_status=completed` не равно done**, а `scope_status=failed` остаётся
  провалом: читай `out_of_scope_files` и проверяй механически.

## Закрытие

Работа не удаляется никогда: коммит в ветку воркера делается до любой уборки,
даже когда интеграции не будет. В проект НЕ вливается и целиком остаётся в ветке
на ручной разбор, если ход воркера не завершился · он писал вне списка · дерево
родилось грязным в его зоне · история переписана ниже базы · merge конфликтует ·
проверка волны красная (тогда проект не тронут вовсе, даже чистыми воркерами).

| Поле `wave` | Что значит |
|---|---|
| `integration_status` | `integrated` · `partial` · `conflict` · `held` · `error` |
| `merged` | чья работа уже в проекте |
| `held` / `conflicts` | не влиты: работа цела в ветке, забирать вручную |
| `kept_branches` | **незабранная работа** — разбери до следующей волны |
| `cleanup_done` / `cleanup_stuck` | факт с диска, не просьба |
| `threads_archived` / `threads_stuck` | исход тредов воркеров |
| `main_tree_drift` | что менялось в основном дереве во время волны |

При `--keep-worktrees` два поля читаются иначе: merged-ветки в `kept_branches`
не попадают, а `threads_archived` и `threads_stuck` оба пусты — дерево живо, и
пустота там не доказывает уборку.

**Волна не закрыта, пока не названы `cleanup_done`, `kept_branches` и
`threads_archived`** (решение владельца 2026-08-18): непустые ветки — незабранная
работа, висящее дерево — выкладка проекта, неархивированный тред — карточка-проект
в никуда.

## Остановка и ремонт

Мост не подключил interrupt на асинхронном пути: работа воркеров фиксируется в
ветках и печатается, но `result.json` не пишется, а деревья остаются. Ручки —
готовый git, обёрток мост не держит:

```bash
git worktree list ; git worktree remove <path> ; git worktree prune
git branch --list 'codex-fleet/*'          # незабранная работа воркеров
```

Деревья под `~/.codex/worktrees` создаёт не мост, а Codex Desktop: там может
лежать незабранная работа владельца — руками не удаляй.

Ремонтный круг идёт тёплым воркером: тот же `id` плюс `thread_id` прошлой
волны. Дерево, файловый контракт и `--run-dir` всё равно
свежие — «доделай в том же процессе» не существует. Второй круг без сходимости —
свежий воркер без `thread_id`; два-три круга без сужения носителей — стоп и
блокер владельцу.
