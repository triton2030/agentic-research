# Долгие прогоны, циклы, мониторинг — bridge-дельты

Читай перед запуском фонового Codex-джоба, цикла worker→verify→fix или
многочасовой задачи. Контракт волны (fan-out, барьеры, круги, фокус заданий) —
`1orchestration`; здесь только то, чем bridge отличается.

## Фоновый запуск

- `Bash` + `run_in_background: true` — **для любого оплаченного turn-а, а не
  только для заведомо долгого**. Поллинг и foreground `sleep` не нужны:
  завершение само разбудит одной нотификацией. Форграунд вешает сессию и
  показывает пользователю замерший экран.
- **`Monitor` сюда не ставь.** Каждая его строка — сообщение в контексте
  агента; для одного сигнала «готово» штатный ответ и есть фоновый Bash.
  Нужен пользователю живой индикатор без расхода контекста — это statusline
  (внешний UI-слой, агент его не видит), отдельное решение владельца.
- **Запрещены пайпы-фильтры на фоновой команде** (`| head/tail/grep`,
  `2>&1 | …`) — закрытый пайп ронял флот, подменяя готовые результаты
  exception-записями. Канон на диске: после завершения читай `result.json` /
  головы файлов, не stdout.
- К фоновой команде всегда `--summary-stdout --heartbeat-sec 120`. `RUN_DIR`
  можно не задавать (default `<проект>/_workspace/codex-artifacts/<run_id>`);
  именованный — только через `--run-dir`. Перед закрытием хода назови
  `RUN_DIR` и task id — единственные ручки после пробуждения.
- **Прогресс читается сводкой, не журналом.** `codex_progress.py "$RUN_DIR"`
  даёт несколько строк: статус, пульс (`steps`, `idle_sec`, у флота `active` и
  `stalest`) и последние шаги — выполненные команды, изменённые файлы, план.
  Смысл субагента — беречь твоё контекстное окно, поэтому активность скрыта по
  умолчанию: заглядывай по подозрению, а не на каждом пробуждении, и никогда
  не читай сырой `events.jsonl` в окно.
- **Несколько запусков разом — `codex_progress.py --board "$PWD"`:** строка на
  прогон, `ДЕРЕВЬЯ-ВИСЯТ` у волны, закрытой без уборки. Это другой вопрос, чем
  сводка одного прогона: не «что он делает», а «кто ещё жив и кто встал».
- Тесты/хуки проекта-цели чистят его `_workspace/` (случай md-tools) → ставь
  `--run-dir` вне проекта. Потерян run_dir ≠ потеряна работа: у изолированной
  волны правки лежат в ветках `codex-fleet/*` либо уже влиты в проект —
  верифицируй `git log` и `git diff`, отчёт не восстанавливай.
- События в `events.jsonl` двух родов. Вехи моста: `worker_done` (провал в
  `payload.status`), `scope_done`, финальный `done` (`ok=true|false`),
  `interrupt_requested`; отдельного события `failed` у флота НЕТ — оно есть
  только у ревьюера/исследователя. И активность самого Codex: `event=codex`
  (шаги, команды, правки файлов) — её читают сводкой, не грепом.
- Данные между Codex-агентами текут **через диск**: следующему давай ПУТИ к
  findings прошлого, не пересказ; в своё окно читай только `result.json`,
  сводку `codex_progress.py` и головы артефактов — сырой `events.jsonl` в
  контекст не тяни.

## Цикл worker → verify → fix

Код для цикла не нужен — каждый круг это твоё суждение. Bridge-дельты:

- **Верификатор — свежий Codex** через `codex_review.py` в default
  `task`-режиме: исходные done-критерии + пути к артефактам. `--mode review`
  здесь запрещён — тянет транскрипт сессии с самоотчётом исполнителя.
  Механику (`--verify` тесты, `scope_status`) сверь сам параллельно.
- Findings-файл = задание следующего воркера (путь, не пересказ); не «доделай
  в том же контексте». Каждый круг — свой `--run-dir`, фоном.
- Полный список носителей проблемы собирай `rg` по СОДЕРЖИМОМУ корпуса, не по
  именам файлов и не только по диффу — filename-фильтр теряет носителей, и они
  всплывают кругом позже.
- **FAIL верификатора по букве на легитимных вещах** (производственный
  словарь, механика ядра) — дефект критерия, не работы: реши границу сам
  чтением файлов и передай следующему кругу, иначе цикл фейлит вечно.
  Микро-остаток (строки в 1-2 файлах) вкладывай микро-задачей в следующую
  волну, не жги отдельным кругом.
- **Сходимость меряй сужением носителей** (6 файлов → 2 → 1 — продолжай), не
  бинарным PASS/FAIL; 2–3 круга без сходимости → стоп и вопрос пользователю
  (расходящийся цикл жжёт кредиты). Finding ломает саму постановку → step
  back, не чини.

## Надзор за экстрадолгим прогоном

Три разных вопроса, и путать их дорого:

1. **Жив?** — `elapsed_sec` в пульсе. Почти никогда не бывает ответом.
2. **Движется?** — `idle_sec` и последний шаг в сводке `codex_progress.py`.
   Растущий `idle_sec` при живом процессе — единственный честный признак
   зависания; у флота смотри `stalest` — молчащий воркер, а не агрегат.
3. **Туда ли идёт?** — содержание последних шагов против масштаба задачи плюс
   головы свежих артефактов в `out/`. Гоняет ли он те файлы, о которых
   задание? Сомнение → короткий reviewer-пробник: промежуточный артефакт +
   ИСХОДНЫЕ критерии, «идёт ли к цели».

Уехал → останови, почини задание или инструкции зоны (см. «Среда субагента» в
SKILL.md), перезапусти новым run — не доливай указания в мёртвый прогон. Не
говори «готово», пока результат не забран с диска.

Долгая тишина сама по себе не приговор: `max`/`ultra` думают молча, и `steps`
может не расти минутами. Приговор — тишина плюс расхождение последнего шага с
заданием.

**Доказанная сигнатура настоящего зависания** (замер 2026-07-28): `last`
замер на `mcpToolCall`, `idle_sec` растёт часами, `steps` не двигаются. Это
обратный вызов в Claude, который не вернётся никогда — лечится только запретом
в задании (см. SKILL.md), не ожиданием.

**Как останавливать.** SIGTERM процессу прогона просит у движка штатный
`turn/interrupt` и оставляет след в `events.jsonl` плюс провизорный
`result.json` — то есть аудит-запись существует, даже если добить пришлось
жёстко. Но terminal-статус гарантирован только когда движок жив: на зависшем
MCP-вызове он закрыть ход не может.
