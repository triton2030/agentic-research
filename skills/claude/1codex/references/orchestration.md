# Живой прогон: фон, надзор, вмешательство, циклы

**Владеет:** прогоном ЛЮБОГО вида, пока он идёт, — через `RUN_DIR`.
**Никогда не держит:** ничего специфичного для волны воркеров (это
[`fleet.md`](fleet.md) на любой её фазе) и ничего, что переживает прогон
(это [`threads.md`](threads.md)).

Проверка правила: его нельзя исполнить, пока `RUN_DIR` не создан, И оно верно
для `codex_review.py` без всякой волны. Оба «да» → сюда.

Читай перед фоновым Codex-джобом, циклом worker→verify→fix или многочасовой
задачей. Контракт волны (fan-out, барьеры, круги, фокус заданий) —
`1orchestration`; здесь только то, чем bridge отличается.

## Фоновый запуск

- Поллинг и foreground `sleep` не нужны: завершение фонового Bash само разбудит
  одной нотификацией (само правило «любой оплаченный turn — фоном» — в теле).
- **Push над артефактами прогона запрещён — над всеми.** Надзор здесь
  вытягивается: сводкой, по подозрению, в рамку строки `задание:`. Ни
  `events.jsonl`, ни `results.jsonl` волны, ни любой будущий журнал моста не
  будят тебя строкой. Нативный `Monitor` — это и есть push: каждая его строка
  становится сообщением в твоём контексте, а его потолок в час короче прогона.
  Отказан на любой фазе, включая волну. Критерий владельца 2026-08-16:
  наблюдение — по твоему запросу и в сжатом виде, не потоком в окно. Живой
  прогресс воркеров владелец и так видит в Codex Desktop
  ([`fleet.md`](fleet.md)). Единственное исключение — сторож ниже.
- **Запрещены пайпы-фильтры на фоновой команде** (`| head/tail/grep`,
  `2>&1 | …`) — закрытый пайп ронял флот, подменяя готовые результаты
  exception-записями. Канон на диске: после завершения читай `result.json` /
  головы файлов, не stdout.
- К фоновой команде всегда `--summary-stdout`: без него в stdout не придёт
  ничего. `--heartbeat-sec` передавай, только когда меняешь дефолт (120).
  Перед закрытием хода назови `RUN_DIR` и task id — единственные ручки после
  пробуждения.
- Тесты/хуки проекта-цели чистят его `_workspace/` (случай md-tools) → ставь
  `--run-dir` вне проекта. Признак хорошего пути один: переживёт сессию.
- **Потерян `run_dir` ≠ потеряна работа.** Теряется ledger и карта
  `worker → thread_id`. Правки изолированной волны лежат в ветках
  `codex-fleet/*` либо уже влиты — верифицируй `git log` и `git diff`, отчёт не
  восстанавливай. Треды персистентны и находятся `codex_threads.py mine`.
- Данные между Codex-агентами текут **через диск**: следующему давай ПУТИ к
  findings прошлого, не пересказ.

## Сторож «встал» — единственное исключение из запрета push

Решение владельца 2026-08-23: нужен один сигнал, когда прогон встал. Не поток:
одна строка и выход. Ставится ФОНОВЫМ `Bash` рядом с прогоном, а не
`Monitor`-ом: `Monitor` держится до своего таймаута, сторожу же надо завершиться.

Различай два отказа, они не один. **Завис** — пульс идёт, `idle_sec` растёт,
последний шаг `mcpToolCall`. **Мёртв** — пульса нет вовсе, и тогда `idle_sec`
заморожен на последнем записанном значении и не вырастет уже никогда. Сторож
только по `idle_sec` слеп ровно к смерти процесса — то есть к самому дорогому
случаю.

```bash
R="$RUN_DIR"; i=0
while [ $((i+=1)) -le 180 ]; do
  [ -f "$R/result.json" ] && exit 0                 # закончился штатно — молчим
  age=$(( $(date +%s) - $(stat -f %m "$R/events.jsonl" 2>/dev/null || echo 0) ))
  [ "$age" -gt 360 ] && { echo "МЁРТВ: $R — пульса нет ${age}s"; exit 0; }
  idle=$($B/.venv/bin/python $B/codex_progress.py "$R" 2>/dev/null \
        | grep -oE '(^| )(stalest_)?idle_sec=[0-9]+' | grep -oE '[0-9]+$' | tail -1)
  [ "${idle:-0}" -gt 1800 ] && { echo "ВСТАЛ: $R — idle ${idle}s"; exit 0; }
  sleep 60
done
echo "СТОРОЖ ВЫШЕЛ ПО ПОТОЛКУ: $R"
```

- Порог мёртвого — `3 × heartbeat` (дефолт 120 → 360 с). Меняешь
  `--heartbeat-sec` — меняй и порог, иначе сторож начнёт хоронить живых.
- У волны поле зовётся `stalest_idle_sec`, у одиночного прогона — `idle_sec`;
  регексп берёт оба, а пустой захват (волна в postflight, `active: 0`)
  считается нулём — иначе сравнение упадёт на пустой строке.
- `timeout` на macOS нет; потолок держит счётчик итераций: 180 × 60 с = 3 часа.
- Цена известна: штатное завершение будит тебя дважды — самим прогоном и тихим
  выходом сторожа. Это плата за один сигнал, а не сбой.
- Разбудил — читай сводку, потом решай по таблице вмешательства ниже. «Встал»
  не отменяет рамку задания и не разрешает вторую реплику.
- **Ненулевой выход сторожа — про сторожа, а не про прогон.** Его самого могут
  убить; тогда фоновый `Bash` разбудит тебя ошибкой без единой строки на
  stdout. Это не «прогон жив» и не «прогон встал» — это «наблюдения больше
  нет»: перевешивай сторож, прогон при этом не трогай. (Ради этого свойства
  сторож и живёт в фоновом `Bash`: убитый `Monitor`-конвейер так не
  сообщает — он висит до таймаута.)

## Надзор: три вопроса, и путать их дорого

Прогресс читается **сводкой, не журналом**: `codex_progress.py "$RUN_DIR"` даёт
строку `задание:`, статус, судьбу посланных реплик, пульс и последние шаги.
Заглядывай по подозрению, а не на каждом пробуждении, и никогда не читай сырой
`events.jsonl` в окно — сводка показывает всё, по чему принимают решение.

1. **Жив?** — `elapsed_sec`. Почти никогда не бывает ответом.
2. **Движется?** — `idle_sec` и последний шаг. Растущий `idle_sec` при живом
   процессе — единственный честный признак зависания.
3. **Туда ли идёт?** — последние шаги против строки `задание:` сверху сводки.
   Гоняет ли он те файлы, о которых задание? Сомнение → короткий
   reviewer-пробник: промежуточный артефакт + ИСХОДНЫЕ критерии.

**Тишина сама по себе не приговор**: глубокое усилие думает молча, `steps` может
не расти минутами. Признак ухода — не молчание, а **материальное действие, не
служащее цели**: охота за второстепенным багом, чужие файлы, артефакт другой
формы. Приговор — тишина ПЛЮС расхождение последнего шага с заданием.

**Доказанная сигнатура настоящего зависания** (замер 2026-07-28): `last` замер
на `mcpToolCall`, `idle_sec` растёт часами, `steps` не двигаются. Это обратный
вызов в Claude, который не вернётся никогда — лечится только запретом в
задании (см. SKILL.md), не ожиданием.

**Несколько запусков разом — `codex_progress.py --board "$PWD"`:** строка на
прогон. Другой вопрос, чем сводка одного прогона: не «что он делает», а «кто
ещё жив и кто встал». Доска идёт одна: вместе с `RUN_DIR` или `--steer`
команда откажет. Видит только default-каталог проекта и 12 свежих прогонов —
прогон с собственным `--run-dir` в ней не появится, его handle держи сам.

## Вмешательство: четыре хода, различитель — рамка

Разбирайся не «долго ли молчит», а **верна ли ещё рамка задания**.

| Что видно | Ход |
|---|---|
| шаги идут по заданию, пусть и молча | ничего |
| цель верна, но он ушёл вбок | **одна реплика в идущий ход** |
| неверна рамка, объём или предпосылка | остановить, перезапустить с исправленным заданием |
| прогон закончен, недопонимание частное | свежий прогон + путь к его `final.md` + дельта |

```bash
$B/.venv/bin/python $B/codex_progress.py "$RUN_DIR" --steer "ТЕКСТ"
```

- Кредитов не стоит, хода не начинает: команда кладёт реплику в ящик прогона,
  сторож рядом с ходом доставляет её в живой turn.
- Реплика несёт **исходную цель, что именно не служит ей, и следующий
  проверяемый результат** — иначе она добавляет рамку вместо того, чтобы
  вернуть прежнюю.
- **Одна реплика, не серия.** Послал — жди, пока следующие шаги тронут тот
  носитель, к которому ты вернул. Не тронули — останавливай прогон, а не шли
  вторую: вторая поправка превращает задание в движущуюся цель, и виноват уже
  ты, а не исполнитель. (Правило одной реплики — слова владельца; сколько ждать,
  не измерено, поэтому и мерится событием, а не числом шагов.)
- **`steer_accepted` не значит «послушался».** Движок подтверждает приём
  реплики, не смену курса; курс доказывают следующие шаги. Событие `applied`
  отсутствует намеренно.
- `steer_rejected` — нормальный ответ, и он виден в сводке вместе с причиной:
  ход уже сменился, прогон закончился, либо вид хода неуправляем. Неуправляемы
  ровно два: нативное ревью (`--mode diff`) и упаковка контекста. Отвергнутая
  реплика — не непослушание: курс не менялся, потому что реплика не дошла.
- **Новую задачу в старый ход не доливай.** Реплика возвращает к прежней цели.
  Цель другая — это другой прогон.

## После результата

Прогон закончился — ящик закрыт, чинить нечего. Недопонимание лечится **свежим
прогоном, которому дан путь к его собственному `final.md`** плюс одна строка
«вот что понято неверно»: он перечитывает свой прошлый ответ, а не собирает
контекст заново. Тред ради этого не заводится — инвариант «чтение без дерева и
без треда» (владелец 2026-08-14) сильнее удобства.

## Цикл worker → verify → fix

Код для цикла не нужен — каждый круг это твоё суждение. Bridge-дельты:

- **Верификатор — свежий `task`** (правило и причина — в теле, «Дисциплина
  запуска»). Дельта круга: механику (`--verify` тесты, `scope_status`) сверь
  сам параллельно, вердикт Codex её не заменяет.
- **Носителей считай `rg` по СОДЕРЖИМОМУ корпуса**, не по именам файлов и не по
  диффу: filename-фильтр теряет носителей, и они всплывают кругом позже.
- **FAIL верификатора по букве на легитимной вещи** (производственный словарь,
  механика ядра) — дефект критерия, а не работы: реши границу сам чтением
  файлов и передай следующему кругу. Микро-остаток в 1–2 файлах вкладывай в
  следующую волну, а не жги отдельным кругом.
- **Сходимость меряй сужением носителей** (6 файлов → 2 → 1 — продолжай), не
  бинарным PASS/FAIL. Finding ломает саму постановку → step back, не чини.
- Круг ремонта у волны идёт тёплым воркером — состав задачи в
  [`fleet.md`](fleet.md). Счётчик кругов и порог остановки — в теле, «Stop».

## Остановка

SIGTERM просит у движка штатный `turn/interrupt` и оставляет след в
`events.jsonl` плюс провизорный `result.json` — аудит-запись существует, даже
если добить пришлось жёстко. Terminal-статус гарантирован только пока движок
жив: на зависшем MCP-вызове он ход не закроет.

Остановка волны устроена иначе и ручки у неё другие — [`fleet.md`](fleet.md).
