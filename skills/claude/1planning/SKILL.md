# Планирование

План — инструкция от агента агенту. Автономией управляют не длинные чёткие
процедуры — сколько ни расписывай, забытый пункт найдётся, и ошибка живёт
именно в нём, — а цель, которую нельзя понять иначе, чем правильно, плюс
перенесённый замысел, направляющий к ней (commander's intent; карта — от
«Чем закончено» из `GOAL.md`, метод Кови «начинай с конца»). Имена методологий
здесь — ярлыки: ничего сверх названного из книг сюда не входит, правила
остаются у своих разделов и references.

Разделение труда жёсткое: **документация говорит «что и как», планирование —
только «в каком порядке и где мы»**; правило адреса и его противовес —
акт вывода состава — держит [contract](references/contract.md).

Режимов задачи два, и «искать путь — тоже задача, которую надо исполнять»:
**Wayfinding** — путь материально не ясен, подзадачи — вопросы;
**Execution** — путь ясен, подзадачи — результаты. Полный план вперёд +
ре-план по событию кратно дешевле пошагового контроля; устройство режимов и
цикл корректировки — [modes](references/modes.md).

## Структура: папки, файлы, связи

```text
<корень карты — называет инструкция проекта>/
└── <Имя эпика>/              ← папка эпика
    ├── <Имя эпика>.md        ← файл эпика (folder note: имя = имя папки)
    ├── <Говорящее имя задачи>.md   ← задача: ровно один файл
    ├── <Говорящее имя задачи>.md
    └── _evidence/            ← тяжёлые артефакты доказательств; на них
                                 ссылаются отчёты подзадач
```

Ничего другого в папке эпика нет: путь сам объявляет родителя задачи, а
говорящие имена файлов делают работу видимой без открытия.

Связи между файлами — каждая проверяемая:

- **задача → эпик**: frontmatter задачи несёт ссылку `эпик`, `эпик-снимок`,
  строку `траектория` и процитированный критерий эпика — следы, что эпик
  действительно читали; гейт сверки — [contract](references/contract.md).
- **эпик → задачи, прогресс**: счётчики задач и подзадач — производные, их
  пишет только прибор проекта; форма и полный список —
  [map](references/map.md).
- **эпик и задача → принципы**: обязательный раздел «Принципы» со строкой
  влияния — вход `1use-principles`; владелец правила —
  [map](references/map.md), форма задачи — [contract](references/contract.md).
- **карта → дашборд владельца**: карта поставляется с дашбордом в папке над
  корнем карты: `Дашборд.md` — один экран, `Дашборд.base` — эпики и вопросы,
  `Планы.base` — задачи; формы и формулы прогресса — [map](references/map.md).
- **эпики и задачи независимы**, у обоих уровней есть `порядок`; правило и
  сквозная работа как самостоятельный эпик — [map](references/map.md).

## Цель

На руках — карта эпиков и живой файл выбранной задачи (говорящее имя внутри
папки своего эпика), по которым следующая сессия с чистым окном продолжает
или останавливается **по самим файлам**, без скрытого чата, а владелец без
пересказа видит: сколько эпиков осталось по порядку, что заблокировано, где
затык, прогресс подзадач каждой живой задачи. Файл задачи называет
приближаемый пункт `GOAL.md` через критерий своего эпика.

Не входит: цель проекта (`1goal`) · создание принципов (`1product-shaping`) ·
побочные находки (`1findings`) · маршруты к знанию (`1index`) · проектные
вьюхи дашборда сверх формы map (владелец — инструкция проекта).

## Критерии успеха

- Файл задачи проходит cold-start-проверку из
  [contract](references/contract.md): новый агент восстанавливает что · зачем ·
  границы · на каком свидетельстве · когда остановиться.
- Каждое существенное требование несёт происхождение: слово владельца / Frame /
  документ / допущение планировщика; «слово владельца» доказуемо записью
  chat-recall.
- Один текущий Next; записанные ниже подзадачи — очередь, не разрешение
  исполнять всё сразу.
- Затронутые эпики и задачи соответствуют [map](references/map.md): машинные
  инварианты, статусы, зависимости, evidence при `✅`, счётчики прогресса.

## Инварианты

- План доверяет исполнителю маршрут, но не даёт додумывать замысел: пробел
  замысла — вопрос или допущение с происхождением, не тихий дефолт.
- Раздел «Принципы» читается до работы; развилку, не покрытую планом, сначала
  неси в `1use-principles` — принципы и цель закрывают её без владельца;
  молчание принципов — вывод с пометкой «выведено», не эскалация; решение —
  строкой `решение:` в отчёте подзадачи, не в чате.
- Файлы планов пишет только оркестрирующее окно: субагенты и воркеры в них
  не пишут (их возвраты — `_evidence/**`); напоминание и запрет держат хуки и
  прибор проекта.
- Состав карты меняется только по правилам [map](references/map.md): тихая
  правка знаменателя превращает «сколько осталось» в декорацию.
- Вопрос владельцу живёт заметкой-вопросом по
  [questions](references/questions.md), не репликой, умирающей с окном чата.

## Дельта

Модель умеет раскладывать работу на шаги. Она не умеет:

- удержать общий остаток проекта — «сколько осталось» подменяется памятью
  сессии и ощущением;
- остановить разложение до свидетельства — расписывает дерево по трём
  непроверенным маршрутам;
- пересобрать план вместо заплатки — патчит устаревшее;
- отличить «путь ясен» от «путь кажется ясным»;
- резать по зависимостям — режет по хронологии, пряча риск в связи между
  этапами;
- перенести замысел из чата — файл говорит «что», а «зачем» умирает с окном;
- удержать обязательства к концу длинного списка;
- не превратить свой дефолт через два пересказа в «волю владельца».

## Известные сбои

`когда → сбой → цена → куда`

- план до свидетельства → дерево шагов по непроверенным маршрутам → переделка
  всего дерева → [modes](references/modes.md)
- новое свидетельство → заплатка поверх подзадач → зомби-план ведёт работу →
  [modes](references/modes.md)
- путь неясен, но подзадачи — «результаты» → архитектурный выбор на ходу без
  основания → [modes](references/modes.md)
- режу тяжёлую работу → хронология вместо оси → риск спрятан между этапами →
  [decompose](references/decompose.md)
- требование без происхождения → догадка планировщика стала «волей владельца»
  → [contract](references/contract.md)
- план пересказывает SPEC/Canon → вторая правда стареет молча →
  [contract](references/contract.md)
- составом deliverable владеет contract/canon/spec, а акт вывода не выполнен →
  пропущенное требование молчит до приёмки → [contract](references/contract.md)
- `[x]` поставлен без доказательства → прогресс-полоса врёт владельцу →
  [contract](references/contract.md)
- задача переросла список подзадач → файл-монстр, который не перечитывают →
  [contract](references/contract.md)
- сессия сменилась → статусы отчётов не отражают реальность → следующая
  сессия переделывает готовое → [contract](references/contract.md)
- работа шире одного контекста → воркеры без file-disjoint контракта →
  перетёртые правки → [delegation](references/delegation.md)
- воркер пишет в файл плана → сломанная форма и счётчики →
  [delegation](references/delegation.md)
- эпик закрыт со слов исполнителя → `✅` без evidence → карта врёт владельцу →
  [map](references/map.md)
- план записан или задача продолжена, а эпик не перечитан → локальный Next
  ведёт против общей траектории — ловит владелец →
  [contract](references/contract.md)
- вопрос владельцу задан репликой посреди волны → потерян с окном → ветка
  стоит или додумана → [questions](references/questions.md)

## Механика

Жёстких перехода два — остальное постусловия:

- **«да» владельца до файлов, вопросы — до обоснования**: сначала все видимые
  вопросы владельцу оформлены заметками-вопросами по
  [questions](references/questions.md) — что стопорит затронутую ветку и что
  продолжает допущением, решает её словарь блокировки; в обосновании — след:
  адреса заметок или recall-записей либо явное «развилок не обнаружено».
  Обоснование (место на карте: эпик и почему он следующий по порядку и
  блокерам · цель · польза · режим · аппетит) — в чат; файлы — после
  согласия. Работа, не находящая своего эпика, — вопрос к карте, не повод
  углубляться без неё. Обоснованию предшествует прогон `1use-principles` на
  составе плана, а не только на замеченной развилке: без него метка
  `Frame/принцип` в происхождении не ставится.
- **перечитай текущий файл эпика и папку вопросов до нового material-шага**;
  сразу сверь `эпик-снимок` задачи: протух — перечитай эпик и пересверь
  задачу тем же ходом. Продолжение по памяти чата — источник зомби-планов;
  классификация свидетельства и пересборка — [modes](references/modes.md).

Допуск: работа выбрана и переживает сессию; активен нативный Plan Mode →
молчи; иначе — разбор в чате без файла.

Постусловия живого файла задачи — по [contract](references/contract.md):
разделы ровно те, происхождение и «верно, пока» в «Зачем», принципы со
строкой влияния, подзадачи от оси разреза
([decompose](references/decompose.md)), размер по правилу contract.

## Завершение

Закрытие — по критериям файла задачи и правилам
[contract](references/contract.md), не по усталости: доказательства у
чекбоксов и `evidence` задачи на месте, стык принят потребителем. Затронутые
эпики карты обновлены тем же ходом по [map](references/map.md): статус,
evidence-ссылка, освобождённые блокеры, строка «Апдейтов»; прибор проекта
прогнан — счётчики свежие; проектный `STATUS.md` (если маршрутизирован)
обновлён. Следующая сессия может продолжить или закрыть по файлам. Не
вошедшее — отдельной строкой в отчёте последней подзадачи с причиной.
