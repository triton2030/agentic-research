# Смысл И Критерии Зоны

Playbook: понять, что в папке **load-bearing**, что сломается при правке, и какие
**критерии успеха** обязаны стоять в папочной и корневой инструкции, чтобы цель
выполнялась, а агент не забыл подразумеваемое. Это смысловой аудит (структурный —
`audit-placement-structure.md`). Это применение принципа «критерии, не процедура»
к конкретной папке: подразумеваемая работа становится явным определением готовности.

В audit/review mode вернуть load-bearing findings и proposed criteria без edits.
Размещать их в файлах только в change/fix mode.

## Идея

Профессионал в этой зоне надёжен не потому, что держит процедуру, а потому что
держит определение готовности: что обязано быть верно после работы здесь. Папочная
инструкция должна нести именно это — иначе агент выведет из голой задачи только
буквальное и забьёт на подразумеваемое. Аудит вытаскивает невидимое наружу как
проверяемые `Критерии Успеха`.

## Протокол

1. **Прочитай зону, не угадывай.** Что в папке реально живёт: какие артефакты,
   какие команды, какая зависимость от других папок (`depends-on`). Если
   Markdown zone велика, передай map/select/read в `1md-read`; здесь потребляй
   только выбранные bodies и gaps.
2. **Назови load-bearing.** Что здесь несёт основную нагрузку — правка чего ломает
   цель папки? Контракт, который читают соседи; инвариант, на котором держится
   загрузка; источник истины, который дублировать нельзя. 2-4 пункта, не список всего.
3. **Назови, что сломается.** Для каждого load-bearing — какой невидимый инвариант
   рвётся при наивной правке? Это будущие `Ограничения` зоны; структурную
   зависимость папки от папки (`depends-on`) объявляй и проверяй через `1md-graph`.
4. **Выведи критерии успеха.** Что обязано быть верно после работы в этой папке —
   включая подразумеваемое, что профессионал сделал бы «само собой» (проверки,
   синхронность с соседями, обратимость, обновление зависимой папки). Это
   outcome-утверждения по умолчанию. Последовательность добавляй только когда
   order/completeness сами являются invariant. Критерии идут в subtree
   instruction; если правило про всю систему — в root.
5. **Выбери owner; размести только в change mode.** Критерии — в subtree owner
   или root, если они действительно глобальны. Форма и язык — через `SKILL.md` +
   `audit-placement-structure.md`. Сверь с project goal, но добавляй явную ссылку
   только если она улучшает retrieval или меняет решение; не навязывай `_ops`
   layout чужому repo.
6. **Гейт.** Критерий без сверки осыпается. Убедись, что инструкция даёт агенту
   повод свериться перед «готово» (явный `Проверка И Stop`), а дорогой/необратимый
   инвариант держи структурным механизмом (hook / permission / validator) через
   live settings/hook pass, не только прозой.

## Design Mode — Инструкция От Будущих Задач

Открывай, когда пишешь или переписываешь root/subtree instruction или её
routing, а не только аудитишь существующую. Это тот же протокол, направленный
вперёд; шаги 1-3 остаются обязательной evidence-базой.

1. **Evidence сначала, всегда.** Rewrite стартует от живых owners, артефактов
   зоны и прошлых traces/corrections; greenfield — от parent/root instruction
   и intended owner. «Новая зона — читать нечего» не бывает.
2. **Representative probes.** Сформулируй будущие задачи/вопросы, с которыми
   cold-start агент реально придёт в зону. Число — по риску: 2-3 для малой
   зоны, шире для global/risky/уже регрессировавшей surface. Probes — evals,
   не контент: их текст никогда не вставляется в инструкцию.
3. **Из probes — минимальный routing.** Для каждой probe выведи первый шаг,
   который инструкция обязана дать just-in-time — обычно owner +
   read-before-edit; validation/escalation добавляй, только когда probe их
   реально требует. Ориентируй, не погружай: указатель к owner-у вместо
   предзагрузки знаний зоны.
4. **Момент загрузки.** Subtree file не ориентирует агента до своей загрузки:
   маршрут к subtree owner живёт в root/parent chain, а сам subtree file несёт
   self-contained guidance уже после загрузки. Topology и placement —
   `audit-placement-structure.md`, не здесь.
5. **Проверка теми же probes.** Bounded check: для каждой probe убедись, что
   effective chain даёт верный первый шаг; при сомнении — один чистый
   cold-start прогон. Probe без ответа = недостающая delta или неверный owner,
   не повод вставить ответ текстом.

## Findings — формат

На зону: load-bearing (2-4) + что сломается + предложенные `Критерии Успеха` +
куда их положить (папка/root). Каждый критерий — outcome-истина, проверяемая, не
процедура. Рекомендуй один вариант; запрашивай выбор только при материальной
развилке.

## Выход

- Load-bearing зоны назван, риск правки назван.
- Критерии успеха выведены как outcome-истины, включая подразумеваемое.
- В audit mode owner и proposed criteria названы; в change mode критерии
  размещены у owner-а. Goal alignment проверен без обязательного link ritual.
- Есть повод свериться перед «готово»; дорогой инвариант — на структурном механизме.
