# Muse Code под обёрткой

Замеры сделаны 2026-10-13 на Muse Code 1.4.7 с моделью `muse-wonder-1.0`
и усилием `high`, если не сказано иное.
Где сказано «по документации», живой проверки не было.

## Права без диалога

| Действие | Голый `muse exec` | Обёртка по умолчанию | Обёртка с `--read-only` |
| --- | --- | --- | --- |
| читать рабочую папку | да | да | да |
| читать файл вне рабочей папки | да | да | да |
| веб-поиск и чтение страниц | да | да | да |
| писать и править файлы рабочей папки | да | да | нет |
| команда оболочки | да, в песочнице | да, в песочнице | нет |
| запись командой вне рабочей папки | `Operation not permitted` | `Operation not permitted` | — |
| запись инструментом в домашнюю папку | — | `absolute path is outside the workspace` | — |
| запись инструментом во временную папку | — | да | — |
| сеть из команды (`curl`) | да | да | — |

Обёртка по умолчанию передаёт `--disable-approval`, с `--read-only` —
`--disable-write --disable-shell`. Песочница в обоих случаях остаётся
включённой. От голого `muse exec` умолчание обёртки отличается одним:
подтверждения отключены, чтобы прогон не мог на них зависнуть.

Аудитор с правами по умолчанию и словами «файлы не меняй» в пробе запустил
проверочную команду и ничего не изменил: `changed: nothing`.

Встроенный профиль `--permission-profile :read-only` разрешает читающие
команды оболочки, но пишущую команду держит на подтверждении, и прогон висит.
С `--disable-approval` и `--approval-mode` профиль не сочетается, поэтому
обёртка его не использует. Имена профилей начинаются с двоеточия:
`:read-only`, `:ask-me`, `:auto-review`, `:unrestricted`.

Документация обещает, что песочница держит `.git` рабочей папки только на
чтение. На деле `git commit` из команды прошёл. В той же документации сказано,
что без просьбы Muse не коммитит; в пробе правки он оставил изменения
незакоммиченными.

`--yolo` снимает и подтверждения, и песочницу; обёртка его не передаёт.

Браузер внутри песочницы не запускается: Chromium из Playwright падает
с `SIGSEGV` до открытия страницы. Просьбу выполнить команду вне песочницы Muse
Code отклоняет сразу, без зависания: `unsandboxed execution requires human
approval, but approval prompts are disabled`. Проверку страницы в браузере
после Muse запускай сам.

## Что обёртка читает из `muse`

Она запускает `muse exec --json` и разбирает построчные события:

| Событие | Что берётся |
| --- | --- |
| `run.model.configured` | имя модели |
| запись с `stream.kind == "session"` | id сессии |
| `tool.result` | имя инструмента, исход, первая строка текста |
| `task.lifecycle.*` | вызов, который был предложен и не принят |
| последнее `run.terminal.*` | исход хода и текст ответа |

Имя модели в событии повторяет запрос и настоящую модель не доказывает:
на `--model muse-nope-9` пришёл обычный ответ с `model_id: muse-nope-9`.
Поэтому обёртка до вызова ищет закреплённую модель в локальном каталоге
`~/.local/share/muse/model-catalog/`.

Расхода токенов в событиях нет. Он есть в выгрузке
`muse export --session <id> --out файл.json`.

Списки `changed:` и `deleted:` обёртка строит сама. `changed:` — файлы
рабочей папки, изменённые после старта прогона, кроме `.git`; `deleted:` —
файлы, которые были до прогона и исчезли. Git она не спрашивает намеренно: он
скрыл бы файлы в игнорируемых папках. Автора списки не различают: правка,
сделанная рядом другим агентом, попадёт туда же. Правку, после которой файлу
вернули прежнее время изменения, `changed:` не увидит.

По документации код возврата `muse exec` означает исход хода: 0 — завершён,
1 — сбой или отмена, 2 — ошибка вызова.

## Инструкции и чужой контекст

| Источник | Голый `muse exec` | Обёртка |
| --- | --- | --- |
| личные правила и скилы владельца из Claude Code и Codex | грузятся | отключены флагом `--no-foreign-personal-context` |
| `AGENTS.md`, скилы и хуки проекта | только в доверенной папке | то же; `--project-rules` доверяет папке на один прогон |
| встроенные скилы Muse | грузятся | грузятся |

С чужим контекстом Muse Code сообщал о 94 загруженных скилах, сам Muse
насчитал в своём каталоге 93; без чужого контекста — 35. Запрос
подаётся только аргументом или через `--prompt-file`: stdin `muse exec` не
читает, поэтому обёртка пишет бриф во временный файл.

## Разговоры

`--resume` передаёт `--session-id`. Muse отказывает, если рабочая папка
другая, а на несуществующий id молча заводит новый разговор под этим же id.
Поэтому обёртка до вызова ищет сессию в хранилище и без неё отказывает. Сессии лежат в `~/.local/share/muse/sessions/`. Команда `muse resume`
открывает диалоговый интерфейс и для вызова без диалога не годится.

## Медиа

| Вид | Итог |
| --- | --- |
| PNG через чтение файла и через `--image` | открывается |
| PDF, MP3, WAV, M4A | `file is not valid UTF-8; binary tool-output refs are not implemented` |
| MP4 | `the selected model does not support video input` |

Отдельная команда `muse voice transcribe файл` расшифровала MP3 и WAV верно,
а M4A отвергла. Обёртка её не вызывает.

## Модели и лимиты

Видимые модели каталога: `muse-wonder-1.0` (умолчание самого Muse Code),
`muse-wonder-full-1.0`, `muse-spark-1.3`, `muse-spark-1.2`. Уровни усилия,
которые каталог предлагает для них: `minimal`, `low`, `medium`, `high`,
`xhigh`, `max`. Скрытые модели каталога, в том числе варианты `-contributor`,
обёртка не принимает. Умолчание обёртки —
`muse-wonder-full-1.0` + `xhigh`, решение владельца 2026-10-13; оно задано
константами `DEFAULT_MODEL` и `DEFAULT_EFFORT` в `scripts/muse.py`. Значения
флагов `--model` и `--effort` обёртка до вызова сверяет с каталогом.

| Ярус | Вопрос по одному файлу | Правка одной строки с тестом |
| --- | --- | --- |
| `muse-wonder-1.0` + `high` | 15–40 с | 31–102 с |
| `muse-wonder-full-1.0` + `xhigh` | 149 с | 81 с |

Строка старшего яруса — по одному замеру, оба шли одновременно. Аудит скила
из трёх файлов с запуском проверочных скриптов занял на старшем ярусе 519 с.

`muse-wonder-full-1.0` на аккаунте владельца отвечает. По документации это
старший вариант, доступный только в планах Power и Maximum.

По документации лимит подписки считается в запросах за пять часов. Остаток
показывает не команда, а метод `usage/read` программного протокола
(`muse serve`): доля пятичасового и недельного окна в процентах, без вызова
модели.

## Программный протокол и реплика в идущий ход

`muse exec`, через который работает обёртка, одноразовый: послать сообщение
в идущий прогон нельзя. Штатные сообщения между сессиями
(`muse session-message`) по документации доходят только до диалоговых сессий;
в прогоны без диалога — нет.

Реплику в идущий ход даёт `muse serve` — протокол MSP, JSON-RPC построчно
через stdin и stdout. Замер 2026-10-14 на `muse-wonder-1.0`: бриф велел после
команды `sleep 25` ответить «АЛЬФА»; на 11-й секунде метод `turn/steer` принял
поправку «вместо АЛЬФА напиши БЕТА»; ход завершился ответом «БЕТА».

Порядок вызовов: `initialize` (имя клиента из строчных букв, цифр
и подчёркиваний), уведомление `initialized`, `session/start`, `turn/start`,
затем `turn/steer` с `expectedTurnId`. Идентификаторы команд — UUID версии 7.
В том же протоколе есть `turn/interrupt`, `approval/decide`
и `session/setModel`. Схему выгружает
`muse schema generate-json-schema --out ПАПКА`. Обёртка этот протокол пока не
использует.

## Muse через T3 Code

Тот же протокол использует T3 Code. Его MCP-сервер для внешних агентов даёт
инструменты `t3_thread_launch`, `t3_thread_send`, `t3_thread_wait`,
`t3_thread_read` и `t3_thread_interrupt`. Нужны запущенный T3 Code и вход
клиента с уровнем выше «только чтение».

Замер 2026-10-14 на `muse-wonder-full-1.0` + `xhigh`, уровень `full-access`:
задача из пяти шагов с правкой файлов и тестами заняла 130 секунд. Поправка,
посланная режимом `auto` на 24-й секунде, доставлена в тот же прогон
(`delivery: "steered"`) и выполнена. Строгий режим `steer` отклоняется, пока
тред готовится.

| Что | Обёртка | T3 Code, `full-access` |
| --- | --- | --- |
| запись вне рабочей папки | отклоняется | проходит: инструмент записи создал файл в домашней папке |
| личные правила и скилы владельца из Claude Code и Codex | отключены | загружены: Muse назвал 95 скилов и заголовки личных инструкций, файлов ради этого не открывая |
| `AGENTS.md` проекта | с `--project-rules` или в доверенной папке | выполнен без флага |
| модель и усилие | умолчание обёртки, сверка с каталогом | задаёт вызывающий; сверки нет |
| общие правила в приписке | добавляются | нет; в пробе Muse без них не коммитил |
| что изменено | `changed:` и `deleted:` | запись `checkpoint` в ленте треда: изменённые файлы всей рабочей папки; файла вне её там нет |

Другой уровень прав у Muse в T3 Code один — `approval-required`:
подтверждение каждой команды и правки.

Тред запускается в проекте, зарегистрированном в T3 Code, или с
`scratch: true` в отдельной пустой папке. Модель и усилие передаются так:
`{"instanceId": "muse", "model": "muse-wonder-full-1.0", "options": [{"id": "reasoningEffort", "value": "xhigh"}]}`.
`t3_thread_wait` с ожиданием в 180 секунд оборвался на стороне клиента
(`The operation timed out`); ожидание в 45 секунд проходит.

## Данные

Запросы и прочитанные файлы уходят в Meta. По документации в подписке по
умолчанию включён режим Contributor: он даёт больше лимита в обмен на право
Meta учить модели на содержимом. На один прогон его меняет флаг
`--contributor-mode on|off`; обёртка этот флаг не передаёт.

## Дочерние агенты

Muse умеет сам писать сценарий (`workflow`) и запускать дочерних агентов;
по документации одновременно работает до восьми, и они наследуют права
ведущего. Кроме того, каждый прогон
сопровождают его встроенные агенты-напоминатели. Обёртка просит Muse не
запускать сценарии без просьбы в брифе, но не запрещает их.

## Общие правила в приписке

К каждому брифу обёртка добавляет приписку: права прогона и общие правила —
не коммитить без просьбы, чужие правки не трогать и не откатывать, сценарии,
дочерних и других агентов не запускать без просьбы, бриф и свои ответы не
записывать как слова владельца. Текст лежит в константах `SHARED_RULES`,
`WRITER_NOTE` и `READ_ONLY_NOTE`.
