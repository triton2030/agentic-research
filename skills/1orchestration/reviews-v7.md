# Проверки 1orchestration v7

## Первый check-approve

Проверенная версия: первый полный `draft-v7` до исправлений; её manifest не
сохранялся как утверждаемый, потому что обе проверки нашли материальные
расхождения.

### Буквальный checker

1. Принято: отрицательные route-условия допускали разбор «отсутствуют все», а
   «карта принята» вводила несуществующее одобрение. Условия сделаны явными.
2. Принято: обязательный полный `count → budget` противоречил примерной оценке
   и лёгкому direct path. Полные реестры снова условны.
3. Принято: прежний ledger склеивал независимо нарушимые предикаты. Пересчёт
   исправлен, а reference считается локальным active set после раскрытия.
4. Принято: `cut.md` и действующая candidate product frame отставали. Добавлены
   v7-раздел и `product-frame-v7.md`; v6 остаётся историей.
5. Принято: stale status в `refactor-v7.md` исправлен.

### Trajectory checker

1. Принято: номинальные цели могли превратить шесть стадий в фактическую цель.
   Полный commander's intent перенесён в тело.
2. Принято: для очевидного поручения обязательные реестры были дороже задачи.
   Всегда остаются две примерные оценки, полный ledger условен.
3. Принято: `brief` мог потерять критерий адресованного owner-а или входа.
   `outcome` стал конкретным состоянием, `done_when` собирает полный локальный
   набор из цели, каждого источника, входа и `delta`.
4. Принято: изменение входа не инвалидировало старые производные. Добавлена
   одна high-order инструкция с возвратом к ранней затронутой стадии.

### Clean-run

Проба правильно сохранила authority root и вернула `rework` на голословное
«всё совпадает». Наблюдаемый путь также подтвердил избыточность обязательного
полного ledger: простой read-only audit породил actor `17` и root `15`.

Не принято как общая поломка: раннее чтение всех staged references. В этой
пробе сами references были объектами аудита, поэтому правило чтения всех
влияющих источников закономерно схлопнуло progressive disclosure. Повторная
проба должна использовать обычную поручаемую работу и проверить фактическую
траекторию после условного ledger.

## Второй check-approve

Trajectory checker: `PASS`, материальных находок нет.

Clean-run на обычном сравнении `GOAL.md` и Product Frame прошёл по low path:
`orient → brief → estimates → direct-assignment → accept(rework)`. Actor `13`,
root `9`; полный ledger не открылся. Поздно найденный Principles-source
инвалидировал ранние производные, после чего маршрут пересобрался. Слабый
return без адресов не освободил зависимость.

Буквальный checker нашёл пять локальных дефектов:

1. Принято: независимо нарушимые действия `brief`, `shape`, `accept` разделены
   на отдельные строки; общая evidence-policy осталась одной high-order нормой.
2. Принято: receipt теперь различает полный счёт файла и формулу фактического
   active set с carried/domain units; универсальные totals не выдумываются.
3. Принято: `count.md` принимает route шага 5, а тело требует отсутствия хотя
   бы одного из двух реестров.
4. Принято: route `orient` требует не только адреса, но подтверждённое чтение и
   карту влияния.
5. Принято: `shape` возвращает к `brief` только новые результаты multi-схемы и
   отдельно завершает `root-work`, `direct-assignment`, `controller-handoff`.

Это второй и последний repair-pass. Следующий полный повтор терминален: новые
находки не запускают ещё один архитектурный цикл, а остаются явным residue.
