# Фоновые задачи Codex Desktop

## Контекст

Задача приложения — самостоятельный разговор с адресом и сохраняемой
историей. В приложении все задачи равноправны; роли исполнителя, проверяющего
или координатора появляются из поручений и адресов связи между ними.
Новая задача не получает автоматически разговор оркестратора. Её финальный
ответ остаётся в ней и сам по себе не отправляет сообщение другой задаче.

## Задача

Собери и поддерживай связи отдельных задач средствами ПК-приложения:
назначь участникам результат и получателя, передай достаточный контекст,
организуй возврат и наблюдение. Состав и глубину схемы выбирай по работе.

## Цель

Каждый участник может выполнить свою часть и передать её тому, кто принимает
следующее решение. Оркестратор видит состояние общей работы и может продолжить
её по адресам задач. Дополнительный слой оправдан переданным ему решением
или самостоятельным результатом.

## Когда выбираешь канал и связи

`spawn_agent` создаёт собственного субагента; `mcp__codex_app__*` управляют
отдельными задачами приложения. Лимит native-субагентов не является лимитом
задач приложения, но не доказывает доступную одновременную мощность последнего.
Названия ниже сокращены до операции; параметры и права берутся из текущего
контракта доступного инструмента.

В текущем контракте `create_thread` разрешён только при прямом запросе
пользователя на новую задачу; внутренние подзадачи направляются к native
collaboration. Предпочтение владельца не снимает эту границу. Недоступный
маршрут называй прямо; другой способ создания не служит обходом ограничения.

У схемы могут быть писатели, проверяющие группы результатов, координаторы
частей и отдельные участники, получающие мнение через `1claude-mcp`.
Наблюдение становится отдельным поручением, когда оно имеет предмет и
полезный выход.
Проверяющему нужны исходные артефакты и полномочие на вердикт; координатору —
своя область решений. Пересылка чужого «готово» не заменяет такую роль.

Связь задаётся явно: какой результат участник получает, что решает сам,
кому возвращает итог и что передаёт выше при споре. Назначь каждому возврату
одного основного получателя; голову подключай к вопросам её уровня.
Общий владелец приёмки известен и при нескольких уровнях координации.

## Когда подбираешь или запускаешь задачу

`list_threads` даёт кандидатов, их статусы, проекты и адреса.
`read_thread` позволяет проверить подходящий разговор и его текущую работу.
Сохрани полученные `threadId` и `hostId`; заголовок помогает выбрать задачу,
но не заменяет адрес. Правила занятости и личных задач остаются в теле скилла.
`send_message_to_thread` продолжает выбранную задачу новым поручением.
Без `model` и `thinking` сохраняются её текущие настройки.

Для разрешённой новой задачи проекта сначала вызови `list_projects` и возьми
возвращённый `projectId`. После этого `create_thread` получает связное поручение
и целевой проект. Например, для разрешённой работы в общей папке:

```json
{
  "prompt": "<полное поручение с адресом получателя>",
  "target": {
    "type": "project",
    "projectId": "<projectId из list_projects>",
    "environment": { "type": "local" }
  }
}
```

`model` и `thinking` добавляются по разрешённому выбору владельца и текущей
схеме инструмента; параметры `spawn_agent` сюда не переносятся.
У новой задачи свой вход: смысл результата, необходимые источники,
область работы и адрес получателя. Для продолжения с унаследованной историей
есть `fork_thread`; он переносит только завершённые ходы, поэтому активное
поручение головы потребуется передать отдельно. Fork тоже подчиняется
разрешениям на создание задач.

Создание асинхронно. Готовый адрес — `threadId` и возвращённый `hostId`;
`clientThreadId` означает подготовку и не подходит операциям с `threadId`.
Дождись готового адреса через состояние приложения до зависимой отправки.
Если участник должен писать новому проверяющему, сначала получи адрес
проверяющего; затем передай этот адрес исполнителю. Это зависимость адресов,
а не обязательный порядок запуска всей команды.

## Когда задаёшь возврат участнику

Вставь в поручение конкретный готовый адрес получателя, известный `hostId`
и требование выполнить обратную отправку. Если адрес головы ещё не известен,
установи его по контексту текущей задачи или данным приложения до отправки
поручения; имя роли не является адресом.

Подходящий фрагмент поручения после подстановки реальных значений:

> По завершении вызови `mcp__codex_app__send_message_to_thread` с
> `threadId: <адрес получателя>` и `hostId: <его hostId, если известен>`.
> В `prompt` передай свой адрес задачи, итог и адрес артефакта, проверенную
> версию, основание проверки и оставшиеся вопросы. Укажи, какого решения
> получателя требует возврат. После отправки оставь итог в своей задаче.
> Если отправка недоступна или завершилась ошибкой, явно сообщи это в своём
> финальном ответе вместе с итогом, чтобы получатель мог забрать его сам.

Исполнитель возвращается назначенному проверяющему или координатору;
тот — своему получателю. Приёмка не возникает от факта доставки сообщения.
Адресная отправка и финальный ответ внутри задачи дают два способа забрать
один результат; повторно пришедший итог той же версии не запускает новую
работу сам по себе.

## Когда наблюдаешь и продолжаешь схему

`wait_threads` наблюдает за готовыми адресами участников без нового поручения.
Для снимка используй `timeoutMs: 0`; для ожидания — ограниченный интервал.
Передавай `hostId` и следующий `afterCursor` из прошлого ответа: так уже
полученный финал не будет возвращаться заново. Один вызов принимает до восьми
целей; это размер запроса, а не предел схемы. Для большего состава выбирай
нужные группы наблюдения. `read_thread` нужен для конкретного вопроса или
восстановления результата, когда адресный возврат не пришёл.

Завершение инструмента, завершение работы участника и принятие его результата
— разные события. Если участник сообщил о блокере, продолжай с этим блокером;
тишина или один статус `done` не дают оснований принять результат.
Уточнение или следующий заказ отправляется через `send_message_to_thread`
в тот же адрес, когда сессия свободна. При предусмотренном телом завершении
`set_thread_archived` закрывает конкретную задачу по её адресу.
