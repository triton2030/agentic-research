# 1md-search

## Цель

Превратить смысловую неопределённость в минимальный decision-ready контекст:
прочитанные адресуемые тела, честное покрытие и разрыв авторитета — столько,
чтобы следующий агент или владелец домена решил и действовал без догадок.

Не входит: сами вердикты о владельце, каноне, готовности, дубле и
`supported / conflict` — они принадлежат вызывающему владельцу домена · чтение
известных адресов · граф и волна правки (`1md-graph`). Проект
нигде не объявил, что несёт авторитет, — этот разрыв уходит владельцу или
`1ia-audit`.

## Критерии успеха

- Каждый материальный аспект закрыт прочитанным телом по адресу
  `path#heading`; названы фактический scope, фильтры, состояние индекса и
  побочные эффекты.
- Отсутствие сформулировано как покрытие названных проб.
- Поиск не заказан продуктом → наружу ушёл изменившийся вывод и адреса, не
  строки инструмента.

## Инварианты

- Никакой вердикт — владелец, канон, готовность, дубль, `supported / conflict`,
  отсутствие — не выводится из retrieval-сигнала: score, заголовка, описания,
  сниппета, входящих ссылок, направления ссылки, специфичности или видимого
  качества. Вердикт стоит на прочитанном теле либо не выносится. Убери тело:
  вывод не изменился — чтение было церемонией.
- `NO_INDEX`, `NEEDS_WARMUP`, `index_warmup_required` — состояния retrieval, а
  не no-hit.
- До первой платной semantic-команды разрешение на отправку Markdown провайдеру
  и на изменение индекса даёт инструкция проекта или явное «да» владельца:
  это политика владельца по своим данным, а не оценка риска агентом. Просьба
  «найди по смыслу» такого разрешения не создаёт. Сами semantic-команды
  исходный Markdown не меняют.
- Необъявленный `.md-tools.toml` не означает «всё здесь правда»: индексируется
  и уходит провайдеру всё дерево. Ошибайся в сторону узкого — пропущенный
  документ даёт видимый no-hit, который чинит следующая проба, а допущенная
  проекция даёт уверенный неверный ответ, и файл уже отправлен наружу.

## Дельта

Модель умеет запускать поиск и читать выдачу. Семантический результат уже несёт
путь, заголовок, сниппет и число — он выглядит готовым ответом. Поэтому без
скила первый связный кандидат становится истиной, а владелец, дубль и
отсутствие выводятся из этого раннего выбора.

Недостающий оператор:

```text
один аспект → фактический корпус и разрешение
→ ранжированные кандидаты → выбранные прочитанные тела
→ карта авторитета | owner: unresolved
→ решение вызывающего владельца домена
```

## Известные сбои

`когда → сбой → цена → куда`

- top-1 выглядит владельцем → авторитет выведен из ранга и заголовка → ложный
  owner уходит вниз по работе → Механика, шаг 4
- packet заполнен, вывод собран из сниппетов → форма закрыта, гейт открыт →
  Механика, шаг 3
- один запрос вернул пусто → объявлено отсутствие в корпусе → Механика, шаг 5
- работа встала на строках инструмента, исходная задача открыта → поиск
  расширяется по инерции → вернись к последнему непройденному гейту, запросов
  не добавляй
- узкий `--path-include` принят за узкий scope → покрытие объявлено ложно →
  [index-lifecycle](references/index-lifecycle.md)
- `NEEDS_WARMUP`, `NO_INDEX` или `NEEDS_REBUILD` → recovery придуман на ходу →
  [index-lifecycle](references/index-lifecycle.md)
- нужен `cleanup-shadowed`, vacuum, ручное удаление SQLite, forced rebuild,
  `profile-sections` или расширение scope → сделано как ordinary warmup →
  [index-lifecycle](references/index-lifecycle.md)
- `overlaps` или `cluster` дали высокий score → объявлен смысловой дубль →
  [retrieval-engine](references/retrieval-engine.md)
- запрос на одном языке против корпуса на другом → mismatch принят за
  отсутствие → [retrieval-engine](references/retrieval-engine.md)
- `md` не запускается, нет ключа, backend недоступен → объявлена пустота
  корпуса → [setup](references/setup.md)

## Механика

1. **Один запрос — один извлекаемый claim на языке источника.** Составной
   вопрос усредняет ранг и прячет потерянный аспект: разбей его в пачку и веди
   по одному корпусу последовательно — параллельные запросы перехватывают общий
   lock, независимые корни можно вести параллельно. Смешанный корпус — короткий
   запрос на каждом реально представленном языке.

2. **Установи, что уходит наружу.** Для чужого корпуса прочитай его `AGENTS.md`
   и `.md-tools.toml`: scope принадлежит целевому корпусу, не текущему `cwd`.
   Проверь разрешение на отправку и на изменение индекса.

   Границы нет — не выводи её из имён папок и не решай сам, что здесь правда:
   собери предложение владельцу. Раздели кандидатов по функции — авторская
   истина · её производные виды · рабочий процесс — и предлагай извлекаемой
   только первую. Границу докажи фильтрами до записи и прочитай фактически
   вернувшиеся пути; после записи проверь `path_scope` в
   `md status CORPUS --json`. Назови исключённое; молча не расширяй границу в
   следующей задаче.

3. **Карта, потом тела.** Общий вызов один, отличаются пределы:

   ```bash
   md search-read CORPUS --query "ONE ASPECT" --limit 5 --json
   md search-read CORPUS --query "ONE ASPECT" --limit 3 \
     --expanded --token-budget 3000 --json
   ```

   Сначала прочитай envelope раньше хитов: фактически вернувшиеся пути,
   действующие фильтры и исключения, `_envelope.corpus_state`,
   `_envelope.next_step`. Затем разворачивай `--expanded` только для выбранных
   сильных кандидатов — широким первым вызовом он не бывает.

4. **Авторитет отделён от смысла.** Прочитан живой owner-контракт и назван
   отображающий его довод — почему авторитет по этому claim принадлежит именно
   сюда — либо стоит ровно `owner: unresolved`.

5. **Пусто — сначала проверь, что искал не то, не там и не на том языке**,
   потом один альтернативный запрос. Вывод формулируется как покрытие названных
   проб. Вторая материальная промашка останавливает семантическую петлю: дальше
   filesystem-карта и точный поиск через нужного владельца.

| Задача retrieval | Маршрут |
| --- | --- |
| Смысл неизвестен, дальше нужны тела | `md search-read` — обычный дефолт |
| Нужны только ранжированные адреса или сниппеты | `md search` |
| Цель известна, нужны похожие блоки снаружи | `md semantic-neighbors` |
| Нужны секции явного семантического типа | `md query-by-type`, только с готовыми профилями |
| Явно нужны пары, темы или топология | `md overlaps`, `md repeated-concepts`, `md cluster` — кандидаты, не вердикт о дубле |
| Проиндексированные корни неизвестны | `md corpus-scan` |

## Завершение

Стоп, когда материальные аспекты закрыты прочитанными телами, названы
фактический scope и разрывы, а самый сильный правдоподобно пропущенный кандидат
проверен соразмерно цене ошибки.

Поиск заказан продуктом (отчёт, инвентарь, аудит, handoff) — верни packet:
аспект и язык запроса · корень, фактические фильтры, состояние индекса и
побочные эффекты · кандидаты `path#heading` и адреса реально прочитанных тел ·
`authority: <прочитанный owner-контракт + отображение>` или `owner: unresolved` ·
границу «кандидат → тело», разрывы покрытия и владельца следующего вердикта.
В любой другой задаче тот же packet остаётся внутренним контроллером.

Механизм датирован рабочим набором моделей 2026-08. Смена целевой модели или
случаи, где голое «прочитай тело» даёт тот же результат, открывают его на
упрощение.
