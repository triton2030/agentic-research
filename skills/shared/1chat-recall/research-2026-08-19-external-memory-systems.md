## Замеры нашей системы

### Повторяемость цитат: гипотеза не подтвердилась

- Точных дублей: 3 группы / 7 записей. Почти все — двойной capture в один день.
- Near-dup (Jaccard ≥ 0.45) между разными сессиями: **12 пар на 826 кандидатов**.
- Медиана длины цитаты 174 символа, p90 411.

Дословно владелец себя не повторяет. Критерий «часто повторяющаяся цитата»
на этом корпусе пуст. Замер разовый, скрипты в корпус не вносились.

### Разрешающая способность эмбеддингов около нуля

`intfloat/multilingual-e5-small` (384d), 883 цитаты:

- средняя попарная близость 0.845, p50 0.846, p99 0.902 — весь корпус в полосе шириной 0.05;
- разделение «внутри сессии» vs «между сессиями»: **+0.009**;
- запрос по делу → top1 0.843, z 3.10; запрос «игра на гитаре и ноты» (в корпусе нет ничего) → top1 0.799, z 3.10. Уверенность одинаковая.

Centering / all-but-the-top растягивают шкалу в 4× (Δ top1–top10 0.029 → 0.10–0.14),
но **z не меняется** — ранжирование то же. Не лечит.

### Живой прогон: система не умеет сказать «у меня этого нет»

`chat_digest.py --query "игра на гитаре и ноты для начинающих"` →
`matched: 60`, `returned: 10`, `retrieval_complete: true`, 10 холдеров про
оркестрацию и скилы. Единственный слабый сигнал —
`card_route: "closed: no context consensus or lexical novelty"` — выдачу не режет.

Скил требует `abstain` словами; инструмент не даёт данных для этого решения.

### Dense-канал: измеренный recall на закреплённых 20 кейсах

Корпус 932 записи, 24 размеченных релевантных id, `tests/retrieval_cases.json`.
Чистый dense, без лексического канала и RRF:

| Модель | R@1 | R@5 | R@10 | MRR | время индекса |
| --- | --- | --- | --- | --- | --- |
| e5-small 384d, только цитата | 0.275 | 0.325 | 0.425 | 0.343 | 51 с |
| e5-small 384d + context-note (**= прод**) | 0.275 | 0.400 | 0.600 | 0.383 | 58 с |
| **e5-large 1024d + context-note** | **0.450** | **0.625** | **0.775** | **0.581** | 924 с |

e5-large: R@5 **+56%**, R@10 **+29%**, MRR **+52%**, R@1 **+64%**.
Цена: индекс 15 мин вместо 1, модель 2.1 ГБ вместо 465 МБ, запрос — один эмбеддинг.

Уточнение: прод уже эмбеддит `text + context-note` (`chat_digest.py:_dense_text`).
Первая строка — не прод, а контроль, показывающий вклад `context-note`: +23% R@5.

### Graphiti-слой: факты есть, но это протокол поручений

Запрос «как владелец хочет чтобы агент записывал и применял его цитаты» вернул:
«Owner предлагает Agent переписать раздел…», «Владелец просит удалить мд-линт скил»,
«Owner поручил Agent вызвать Opus…». Одноразовые поручения, `invalid_at: null`.

Запрос «лимит длины файла в символах» не нашёл правило 2000 символов, которое
`_ops/plans/graphiti-codex-finish/status.md` сам называет главным owner-правилом.

Собственная квитанция это признаёт: `"unsupported": {"answer_present": false,
"stock_rrf_noise": true}` — та же болезнь, что у `chat_digest`: на вопрос вне
корпуса выдаются шумовые результаты.

## Что нашли в LightMem (zjunlp)

Репо — семейство из четырёх систем: LightMem, StructMem (режим LightMem),
FluxMem, EM²Mem.

### Работает и стоит кражи

**1. `UPDATE_PROMPT` — три действия над существующей памятью.**
`src/lightmem/memory/prompts.py:334-406`, дословно:

> 1. Update: If the target memory and candidate memories describe essentially the same fact/event but are not fully consistent…, update the target memory by integrating the additional information.
> 2. Delete: If the target memory and candidate memories contain a direct conflict, the candidate memories (which are more recent) take precedence. Delete the target memory.
> 3. Ignore: If the target memory and candidate memories are unrelated, no action is needed.

**2. Механическая генерация кандидатов на инвалидацию — LLM только на пары.**
`lightmem.py:459-539`: для каждой записи ищутся top-20 ближайших **с меткой не
позже своей** (`filters={"float_time_stamp": {"lte": ts}}`), топ-10 кладутся в
`update_queue`. Затем инверсия (`:578-585`): для записи E собираются все более
поздние, у кого E в очереди со score ≥ 0.8 — это и есть «новые данные об E».
LLM зовётся только на эти пары.

**3. Причинная дисциплина.** Суммаризация не подглядывает в будущее:
`{"float_time_stamp": {"lt": …}}` (`lightmem.py:816-820`). Флаг
`consolidated=True` не даёт переобрабатывать (`utils.py:640-663`).

**4. EM²Mem — единственное во всех четырёх репо живое «важность».**
`SemanticMemory.py:194-202`:
`confidence = min(0.95, 0.45 + 0.04 * min(support_count, 8))` —
уверенность как функция числа **независимых подтверждений**.
Наполняется реальным `support_count = len(evidence_refs)` из офлайн-пайплайна.
Влияет на ранжирование: `0.55·similarity + 0.30·PPR + 0.15·confidence`.
Плюс `first_seen` / `last_seen` на каждый факт — окно жизни утверждения.

**5. EM²Mem — явное LLM-разрешение конфликтов при консолидации.**
`semantic_consolidation.py:60-93`: новый триплет сверяется по косинусу (порог 0.6)
с накопленными, LLM решает что слить/удалить; **evidence удалённых подмешивается
в выжившую запись** (`:184`) — не теряется.

**6. FluxMem — PEMS, стоп-условие переписывания.** `metrics/pems.py`:
`PEMS = успешность / (число_навыков × log(длина)) × (1 − Δэмбеддинга)`.
Останов не «PEMS высокий», а «PEMS перестал меняться» (ε = 0.01).

### Заявлено, но не работает — не копировать

- `extract_threshold` («порог важности для извлечения», `configs/base.py:57`) — **объявлен и нигде не используется**. Критерия важности в LightMem нет.
- `memory/graph.py` — файл состоит из `class GraphMem:` и пустой строки, `ast.parse` падает. `graph_mem=True` уронит импорт.
- BM25-retriever — пустой файл, зарегистрирован в фабрике; `retrieve_strategy="hybrid"` — мёртвая ветка, все прогоны жёстко пишут `"embedding"`.
- `entropy_compress` — недостижим: опечатка в имени класса в конфиге и точка в конце пути в фабрике.
- Поля `category`, `subcategory`, `memory_class`, `topic_summary`, `hit_time` — объявлены и сериализуются, никогда не заполняются.
- `FluxMem.remove_node` — ноль вызовов; узлы только копятся. `prune_similarity_threshold=0.3` — dead config, реальный порог 0.7 захардкожен и это LLM-verify, а не эмбеддинги; докстринг врёт.
- EM²Mem: ~36% `MemoryCell.py` (≈590 строк «family»-механики) и весь `VisualMemory.retrieve()` недостижимы из живого пайплайна; `habit_strength` нигде не вычисляется.
- Ни одного файла результатов не закоммичено ни в одном из трёх experiments.

## Что нашли в memsearch (zilliztech)

### Работает

- **Три слоя** episodic / semantic / procedural — совпадает с нашей структурой.
- **`distill → candidate → человек ставит`.** `install()` физически отделён от `distill()`, автоустановки нет нигде в коде. `docs/home/skills-from-memory.md:50-54`: *«Humans decide what becomes real… the machine proposes, you dispose.»*
- **Замер эмбеддингов** — 955 чанков × 2172 запроса, билингвально. `bge-m3-onnx-int8` R@5 = 0.776 zh / 0.814 en против `text-embedding-3-small` 0.717 / 0.767. 558 МБ, локально, без API-ключа.
- **Приёмы удержания агента на памяти** (без правки кода агента):
  - хук печатает `[memsearch] Memory available`, а description скила **прямо ссылается на эту строку** — петля замкнута;
  - Claude Code: recall уходит в `context: fork` — цена «на всякий случай проверить» не в главном окне;
  - **DSH: push вместо pull** — на первом шаге каждого хода инфраструктура сама делает поиск и подмешивает результат, платя контекстом только когда что-то нашлось;
  - захват хода не зависит от решения модели вообще.

### Заявлено, но не проверяется

- **`min_occurrences = 3`** — подставляется в промпт как строка (`skills.py:152`) и **в коде никогда не сравнивается**. Тест это подтверждает: один журнал → LLM сама сказала `"occurrences": 3` → принято.
- **Разрешения противоречий нет.** В `project_review.txt` / `user_profile.txt` слов contradict / conflict / supersede / recency — ноль. Конфликт двух заявлений владельца в разное время решает LLM в момент `replace`, **без инструментов** (`--tools ""`), то есть без доступа к первоисточнику.
- **Дедуп только SHA-256 по байтам.** Перефразированный повтор той же мысли не ловится — два разных чанка.
- **`evaluation/` пуст** (только README), хотя документация обещает там сырые данные, скрипты аннотации и шаги воспроизведения.
- **«Append-only, no LLM curation on the write path»** в сравнении с конкурентами — верно только для журналов; `PROJECT.md` / `USER.md` LLM переписывает целиком через `action: "replace"`.

## Диагноз

**1. Критерия важности нет ни в одном из изученных проектов.**
LightMem объявил `extract_threshold` и не реализовал. memsearch объявил
`min_occurrences` в промпте и не проверяет. FluxMem считает зрелость навыка,
но никогда ничего не выбрасывает. Единственный живой ответ — EM²Mem:
важность = число независимых подтверждений. И это **не** «дословно повторяется»,
а «сколько разных эпизодов поддерживают один тезис».

**2. Инвалидация решена только там, где есть темпоральный граф.**
У нас он уже есть и уже работает: 157 инвалидаций из 1365. Второй механизм
строить не надо — надо проверить, что этот ловит нужное.

**3. Наша реальная дыра — не архитектура слоёв, а качество сигнала.**
Замерено: dense-канал даёт R@5 = 0.40; система не отличает «нашла» от
«у меня этого нет». Любой механизм важности или инвалидации поверх такого
сигнала будет генерировать мусорных кандидатов.

## Что взять — по порядку

1. **Сменить модель эмбеддингов на e5-large.** Единственная правка с прямым замером: R@5 0.40 → 0.625, MRR 0.383 → 0.581. Ничего в контракте скила не меняется.
2. **Гейт «у меня этого нет».** Порог по z-score / разрыву top1–top10; честный `abstain` вместо десяти холдеров. Даёт инструменту данные для решения, которого скил уже требует словами.
3. **Важность = число подтверждений (EM²Mem).** Считается механически, без LLM: сколько разных сессий поддерживают тезис. Требует пункта 1, иначе кластеры будут ложные.
4. **Кандидаты на отмену — механически, LLM только на пары (LightMem).** Проверить сначала, ловит ли это уже построенный Graphiti; строить своё — только если нет.
5. **Продвижение в долговременную память: `distill → кандидат → владелец ставит` (memsearch).** `MEMORY.md` уже 24 КБ на каждую сессию и растёт; автопродвижение сделает хуже.

## Чего не делать

- Не строить граф или векторную БД поверх сотен заметок: сложность EM²Mem/FluxMem компенсирует объём, а не качество; на нашем корпусе корпус целиком помещается рядом с запросом.
- Не переносить `min_occurrences` как число в промпте — оно ничего не проверяет.
- Не делать автопродвижение в `MEMORY.md`.
- Не копировать «hybrid» из LightMem — там пустой файл.

## Непроверено

- `bge-m3-onnx-int8` на нашем корпусе **не замерен**: три попытки через `fastembed.add_custom_model` упали —
  неверное имя файла (нужен `model_quantized.onnx`), затем несовпадение формы при MEAN-пулинге
  `(256,1024)` vs `(256,298,1024)`, затем `axis 1 is out of bounds` при CLS. Экспорт `gpahal` —
  мультивекторный (dense + sparse + colbert), custom-model путь fastembed его не разбирает.
  Цифры memsearch по bge-m3 остаются их замером на их корпусе, не нашим.
- Влияние смены модели на end-to-end выдачу (dense + лексика + RRF + holder-ранжирование) — мерян только dense-канал.
- Все цифры LightMem/EM²Mem из их README — ни одного файла результатов в репо не закоммичено; воспроизведение не запускалось.
- Замер «confidence по support_count улучшает ответы» отсутствует и в EM²Mem: измерено «работает и используется», не «работает лучше альтернативы».
