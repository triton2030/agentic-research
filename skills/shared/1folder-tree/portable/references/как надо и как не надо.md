# Как надо и как не надо

Вход: сомнение, появляется ли папка, где она стоит, как называется или как на неё ссылаться. Выход: решение по правилу с парным примером; само правило целиком — в теле скила.

Парные примеры из выдуманных продуктов: клиника, школа, CRM, магазин, туры, ресторан, фитнес. Имена группировок и предметов выдуманы и в реальной базе берутся из `AGENTS.md` базы; `понятия/` здесь — словарь понятий, он держит только файлы, а предметы с аспектами стоят под условной группировкой `вещи/` или там, где им место по принадлежности. В угловых скобках — что раскрывает файл, а не как его назвать: `<чего хочет>` может называться «Мотивы». Набор аспектов в примерах намеренно разный: он зависит от предмета, а не от шаблона. Существующие имена не меняются без решения владельца.

Сгруппировано по правилу. В каждой паре: ошибка, исправление, одна строка почему.

# Путь различает часть, владельца описания и группировку

## Вложенность без принадлежности

Не надо (один тур входит в разные маршруты):
```
вещи/
  маршрут/
    тур/
      день тура/
```
Надо:
```
вещи/
  маршрут/
    <что это>
    <как устроен>          ← перечисляет туры по имени
  тур/
    свойства/
      <что это>
    день тура/
      <что это>
```
В этом примере маршрут выбирает готовые туры, но не владеет их описанием. Вложение тура в один маршрут скроет общий предмет от остальных. День тура — часть тура (part-of), поэтому вложен честно; собственное описание тура получает дочерний предмет, потому что рядом с подпапкой файлов не бывает.

Не надо (клиника):
```
вещи/
  врач/
    приём/
```
Надо:
```
вещи/
  врач/
    <что это>
  приём/
    <что это>
    <как устроено>          ← «проводит один врач»
```
Приём связан с врачом, но не является его частью, и врач не владеет правилами приёма: у приёма есть ещё пациент, кабинет и время. Связь объясняется в тексте, а подробные правила остаются у владельца приёма.

## Владелец результата и его потребители

Редактор выкроек устойчиво определяет формат выкройки; раскройный станок использует готовый результат. Поэтому описание формата может принадлежать редактору, хотя формат не является его частью. Станок цельно описывает приём и обработку выкройки и ссылается на правила у редактора. Несколько потребителей не делают их родителями и не требуют вынести выкройку на уровень приложений. Локальные черновики редактора отделены от контракта готовой выкройки.

Если форматом независимо управляют несколько инструментов и общего владельца внутри одного из них нет, нужен общий дом. Его масштаб выбирают по карте проекта. Сам факт, что редактор создал первую выкройку, не делает его вечным владельцем формата.

## Принадлежность, не отражённая в пути

Не надо (CRM):
```
вещи/
  сделка/
  этап сделки/
  комментарий к сделке/
```
Надо:
```
вещи/
  сделка/
    сущность/
      <что это>
    этап/
      <что это>
    комментарий/
      <что это>
```
Этап и комментарий существуют только внутри сделки. Плоская раскладка теряет это знание, и имена приходится удлинять, чтобы его вернуть.

## «Для» принято за «внутри»

Не надо:
```
люди/
  покупатель/
    <кто это>
    каталог/               ← экран внутри предмета «покупатель»
```
Надо:
```
люди/
  покупатель/
    <кто это>
для покупателей/
  каталог/
```
Каталог — для покупателя, а не часть покупателя. Кружка для чая не лежит внутри чая.

# Папка держит либо файлы, либо папки

## Файл рядом с подпапками

Не надо:
```
каталог/
  <как устроено>
  фильтры/
    <как устроено>
```
Надо (фильтры — предмет со своими аспектами):
```
каталог/
  список товаров/
    <как устроено>
  фильтры/
    <как устроено>
```
или (фильтры — абзац):
```
каталог/
  <как устроено>          ← абзац о фильтрах внутри
```
Файл рядом с подпапками не читается: он про весь каталог или про то, что не влезло в фильтры? Собственное содержимое предмета с дочерними предметами получает отдельную подпапку с настоящим именем, а не файл «общее».

## Группировка с файлами

Не надо:
```
для покупателей/
  чего хочет покупатель
  каталог/
```
Надо:
```
люди/
  покупатель/
    <кто это>
    <чего хочет>
для покупателей/
  каталог/
```
Группировка не владеет аспектами, поэтому в ней нет файлов. Покупатель как предмет живёт среди людей продукта; группировка «для покупателей» собирает относящиеся к аудитории экраны.

## Группировка, названная как предмет

Не надо (клиника):
```
врачи/
  расписание/
  профиль/
```
Надо:
```
люди/
  врач/
    <кто это>
    <чего хочет>
для врачей/
  расписание/
  профиль/
```
«Врачи» здесь — группировка экранов для врачей, но её можно принять за предмет об аудитории. Тип узла определяет смысл: группировка только собирает соседние предметы по признаку, а предмет раскрывается через собственные аспекты или состав. Множественное число здесь помогает заметить группировку, но само по себе её не доказывает.

# Файл — один аспект предмета

## Один ответ разрезали на факты

Не надо:
```
редактор изображения/
  положение зоны.md       ← только «зону двигают мышью»
  размер зоны.md          ← только «размер меняют за угол»
  проверка зоны.md        ← только «смотреть на превью»
```
Надо:
```
редактор изображения/
  настройка зоны.md       ← положение, размер, проверка результата
```
Читатель приходит узнать, как настроить зону. Движение, размер и оценка результата — части этого ответа. Если правил проверки пока нет, объединение файлов не восполняет их: неизвестная часть отмечается знаком пробела.

Короткий ответ с самостоятельной причиной чтения может остаться отдельным файлом. Например, `срок хранения.md`, полностью задающий срок и его условия, не объединяют с другим ответом только ради объёма. И наоборот, файл `настройка зоны.md` с подробными разделами не режут из-за его длины.

## Свойство вместо предмета

Не надо (маркетплейс):
```
безопасность/
  пароли
  оплата
  личные данные
```
Надо:
```
для покупателей/
  вход/
    <как устроено>          ← правила про пароли
общее/
  оплата/
    <как устроено>          ← правила про защиту платежа
```
В этом дереве «безопасность» не выделена как самостоятельный предмет с ясной ответственностью, поэтому папка-свойство становится второй свалкой: правило живёт и там, и у защищаемого предмета, и они расходятся. В другом проекте безопасность может быть отдельным предметом; это определяют её границы и местная карта, а не грамматическая форма слова.

## Имя без ясных границ содержания

Не надо (клиника):
```
запись на приём/
  описание
  функционал
  требования
  спецификация
  заметки
```
Надо:
```
запись на приём/
  <роль в системе>
  <как выглядит>
  <как устроено>
  <что бывает не так>
```
«Описание» и «функционал» — про одно и то же, агент положит факт в оба. «Спецификация» называет тип документа, а не аспект предмета. У каждого ответа один владелец; необходимое объяснение связи между ответами не создаёт копии подробного правила.

## Имя-вопрос

Не надо:
```
корзина/
  Как покупатель добавляет товар в корзину
  Что происходит, когда корзина теряется
```
Надо:
```
корзина/
  <действия>
  <при потере>
```
Вопрос задаёт границы содержания, но не форму имени. Имя — короткое словосочетание об аспекте предмета; по нему и по пути видно, что внутри и когда это читать.

## Мешок

Не надо (CRM):
```
карточка клиента/
  <как устроено>
  детали
  разное
  прочее
  заметки
```
Надо:
```
карточка клиента/
  <как устроено>
  <что бывает не так>
  <что видит человек>
  <техническое>
```
«Детали» и «разное» — «всё остальное». Никто не знает, что туда класть и что оттуда читать. Разобранный на аспекты мешок показывает владельцу то, что было в нём похоронено.

## Файл с именем папки

Не надо (фитнес):
```
тренировка/
  тренировка
  <как устроено>
```
Надо:
```
тренировка/
  <зачем нужна>
  <как проходит>
```
Файл-тёзка пытается описать предмет целиком и дублирует аспекты рядом.

## Гигантский файл, заговоривший за пределами имени

Не надо:
```
каталог/
  <как устроено>          ← 40 экранов текста: и фильтры, и оплата, и что такое товар
```
Надо:
```
каталог/
  <как устроено>          ← только каталог, сколько бы ни вышло
общее/
  оплата/
    <как устроено>
понятия/
  товар
```
Длина не ограничена; границу задаёт самостоятельный вопрос. Экран объясняет своё участие в оплате, а подробные правила оплаты остаются у их владельца: они нужны и другим экранам.

## Вопрос, пересекающийся с соседом

Не надо:
```
корзина/
  <как устроено>
  <что бывает не так>
  пограничные кейсы          ← то же, что «что бывает не так»
  UX-соображения             ← куски «как устроено»
```
Надо:
```
корзина/
  <как устроено>
  <что бывает не так>
```
Два полных ответа на один вопрос создают конкурирующие дома. Необходимый подвопрос раскрывается разделом существующего ответа; новый самостоятельный вопрос может оправдать отдельный файл.

# Когда появляется папка

## Действие без экрана как папка

Не надо:
```
корзина/
  добавление товара/
  удаление товара/
```
Надо:
```
корзина/
  <как устроено>          ← абзацы: добавить, удалить, изменить
```
Но:
```
для мастерских/
  приём заказа/
    <как выглядит>
    <как устроено>
```
Кнопка — абзац. Экран с формой в несколько шагов — самостоятельный предмет документации.

## Папка ради одного абзаца

Не надо (фитнес):
```
вещи/
  подход/
    <что это>             ← три строки, больше сказать нечего
```
Надо:
```
понятия/
  подход
```
Одиночный файл с именем понятия, пока не появится второй аспект. Тогда файл становится папкой.

## Файл порезали вместо предмета

Не надо:
```
каталог/
  как работает 1
  как работает 2
  как работает продолжение
```
Надо:
```
каталог/
  список товаров/
    <как устроено>
  фильтры/
    <как устроено>
  сортировка/
    <как устроено>
```
Рост файла сам по себе не требует деления. Здесь обнаружены самостоятельные предметы — фильтры и сортировка; при согласованном выделении в подпапки собственное содержимое каталога тоже получает имя дочернего предмета. Один законченный ответ с несколькими разделами может оставаться большим файлом.

## Папка, созданная агентом молча

Не надо:
```
[агент получил материал про уведомления и создал]
общее/
  нотификации/
    <как устроено>
```
Надо:
```
[агент спрашивает владельца]
Материал про уведомления не ложится ни в один предмет. Варианты:
1. общее/уведомления — процесс, идущий и студии, и покупателю
2. абзац в общее/путь заказа — если уведомления только про заказ
3. понятия/уведомление — если это понятие, которое встретится во многих экранах
Какой?
```
Папка рождается через владельца. «Нотификации» — агентское слово; владелец сказал бы «уведомления». Выбор записывается в `AGENTS.md` базы.

# Один факт — одно место

## Процесс размазан по экранам

Не надо:
```
для покупателей/
  оформление заказа/
    <как устроено>        ← весь путь заказа
для мастерских/
  карточка заказа/
    <как устроено>        ← снова весь путь заказа
```
Надо:
```
общее/
  путь заказа/
    <как устроено>        ← описан один раз
для покупателей/
  оформление заказа/
    <как устроено>        ← «начинает путь заказа, этап заявка»
для мастерских/
  карточка заказа/
    <как устроено>        ← «показывает путь заказа с этапа согласования»
```
Экран говорит, где в процессе стоит. Два пересказа разойдутся.

## Знание о предмете там, где с ним работают

Не надо (ресторан):
```
для владельца/
  редактор меню/
    <как устроено>        ← здесь требования к фотографии блюда
```
Надо:
```
вещи/
  блюдо/
    <как устроено>        ← требования к фотографии
для владельца/
  редактор меню/
    <как устроено>        ← «собирает меню из блюд» — называет, не объясняет
```
Верно про блюдо независимо от экрана — у блюда. Меню для гостя покажет те же фотографии, и строящий его агент будет искать требования у понятия, а не в чужом инструменте.

## Техническое вынесено в отдельную группировку

Не надо:
```
техническое/
  данные каталога
  вывод каталога
для покупателей/
  каталог/
    <как выглядит>
```
Надо:
```
для покупателей/
  каталог/
    <как выглядит>
    <как устроено>
    <техническое>        ← данные и вывод этого экрана
система/
  <устройство>          ← общее для всей системы: стек, движок, где живёт правда
```
Техническое о предмете — у этого предмета: владелец хочет понимать продукт целиком, а агент должен найти собственные правила предмета в одном доме. Устройство системы целиком — самостоятельный предмет; его потребители ссылаются на него и не копируют его правила.

## Папки по ролям или этапам работы

Не надо:
```
дизайн/
  каталог
разработка/
  каталог
```
Надо:
```
для покупателей/
  каталог/
    <как выглядит>        ← «дизайн»
    <техническое>         ← «разработка»
```
Роль — кто делает, а не что описано. Читает всё владелец, и место в дереве задаёт предмет, а не порядок работы над ним.

## Документация на код

Не надо:
```
система/
  функции корзины/
    addToCart
    removeFromCart
```
Надо:
```
система/
  <устройство>           ← где лежит код корзины, одной строкой
```
Канон кода — код. Описание функций устаревает при первом коммите.

# Упоминают предметы, а не перечни файлов

Ссылка должна объяснять связь предметов; точный адрес сам по себе не заменяет эту связь.

## Ссылка без объяснения связи

Не надо:
```
каталог/<роль в системе>:
  «см. люди/покупатель/<чего боится>»
```
Надо:
```
каталог/<роль в системе>:
  «каталог — то, что видит покупатель; что бы ни решал, помни про него»
```
Сначала понятна связь с покупателем. Для общего контекста достаточно имени или папки; если нужен конкретный аспект, допустим точный переход к нему у владельца.

## Указание, какой файл читать

Не надо:
```
корзина/<техническое>:
  «Перед реализацией прочитай общее/оплата/<техническое> и общее/оплата/<что бывает не так>»
```
Надо:
```
корзина/<техническое>:
  «Корзина передаёт заказ в оплату.»
```
Агент, строящий корзину, открывает владельца оплаты. Если переход зависит от точного контракта, ссылка на его документ или раздел уместна; обязательный перечень всех файлов оплаты не нужен. Адрес источника в сноске отдельно доказывает происхождение факта.

## Пересказ вместо упоминания

Не надо (CRM):
```
сделка/<как устроено>:
  «Клиент — это компания или человек, с которым мы ведём переговоры;
   у него есть контакты, история, ответственный менеджер…»
```
Надо:
```
сделка/<как устроено>:
  «Сделка всегда принадлежит одному клиенту.»
```
Что такое клиент — у клиента. Сделка называет его по имени.

## Связь через конкретное свойство

Можно:
```
напоминания/<как устроено>:
  «Время напоминания зависит от длительности приёма.»
```
Документ по смыслу зависит от одного конкретного свойства другого предмета — можно назвать свойство словами. Если так приходится делать часто, проверь, не стало ли оно самостоятельным предметом с несколькими аспектами.

# Имена

## Имена под агента

Не надо:
```
каталог/
  spec_catalog_v2_final
  каталог 2026 09 09
  как работает (старое)
```
Надо:
```
каталог/
  <как устроено>
```
Версии и даты — признак, что файл боятся править. Правят файл; почему поменяли — в сноске и в корпусе слов владельца.

## Имя не из речи владельца

Не надо:
```
для покупателей/
  модуль оформления/
  экран корзины пользователя/
```
Надо:
```
для покупателей/
  оформление заказа/
  корзина/
```
В этом примере владелец говорит «корзина», не «экран корзины пользователя». Если он выбрал префикс для экранов, действует его соглашение из инструкции базы; пример не запрещает такую пометку.

## Смешение языков и транслит

Не надо:
```
для покупателей/
  checkout/
  katalog/
```
Надо:
```
для покупателей/
  оформление заказа/
  каталог/
```
Язык имён один — язык владельца. Даже если в коде это checkout.

## Переименование существующего

Не надо:
```
[в базе была папка «покупка»; агент переименовал в «оформление заказа», потому что так правильнее]
```
Надо:
```
[агент оставляет «покупка» и пишет владельцу]
В базе есть «покупка», по смыслу это экран оформления заказа. Оставить или переименовать? На «покупку» ссылаются четыре файла.
```
Имя предмета — часть карты владельца и адрес для упоминаний. Меняется только его решением.

# Планы — не источник

## Решение осталось в закрытом плане

Не надо:
```
[план задачи «фильтры каталога» закрыт; в нём «решили: фильтр по цене — ползунок»; в базе про это ничего]
```
Надо:
```
каталог/фильтры/<как устроено>:
  «Цена задаётся ползунком, не двумя полями.»[^1]
[в плане — ничего, или «перенесено в базу»]
```
Через месяц никто не читает закрытые планы. Решение переезжает, не копируется, к своему предмету; откуда оно — в сноске.

## План внутри базы

Не надо:
```
для покупателей/
  каталог/
    план работ
    статус
```
Надо:
```
[в базе — только аспекты каталога; план и статус — в слое планирования]
```
Работа — не аспект предмета. База отвечает «что верно», план — «что делаем».
