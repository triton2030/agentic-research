# Выбор типа

Вход: у проекта нет живого словаря типов, и тип этого документа корпусом ещё не
задан.

Выход: термин типа и имя файла для этого документа.

1. Выбирай тип от вопроса, который переживёт этот разговор, а не от того, о чём
   материал. Стартап несёт мало типов, и тип заслуживает места только тогда,
   когда вопрос возвращается снова и кто-то должен действовать по ответу.
2. Опирайся на именованные рамки, которые модель знает и без этого файла:
   YAGNI, KISS, «just enough documentation», книги и советы, адресованные
   стартапам. Имя рамки работает здесь так же, как имя типа документа: оно
   приносит целый стандарт, которого не нужно выписывать.
3. Бери самый лёгкий стандартный деловой термин, чей жанр владеет этим
   вопросом. Весь механизм — уже готовый прайор модели, поэтому придуманное имя
   («Сводка платёжной аналитики») не включает стереотип и не даёт ни жанра, ни
   адреса: ближайший стандартный термин побеждает более точный придуманный.
4. Оставляй термин деловым стандартом, как правило английским, даже когда тело
   документа на языке проекта. Национальный аналог тянет свой прайор:
   «Техническое задание» приносит регламентный объём, которого ты только что
   избежал.
5. Заводи новый тип и его дом — файл или папку — только вместе с первым
   настоящим документом в нём. Пустой дом следующий агент прочтёт как
   приглашение заполнить его ради покрытия, а скелет из пустых файлов — как
   план работ.
6. Называй файл `<ТИП> — <предмет>.md`, где предмет — устойчивая вещь, которая
   будет существовать и через квартал. Тип читают до того, как файл открыли,
   поэтому он живёт в имени, а не только в заголовке; повод написания
   (`auth-refactor-notes-aug.md`) следующему агенту не угадать, и он заведёт
   второй файл о том же ответе.
7. Где имя задано конвенцией — `README.md`, `CHANGELOG.md` — объявляй тип
   первой строкой документа.
