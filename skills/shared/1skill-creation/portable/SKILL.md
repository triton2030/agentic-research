# Создание скиллов

## Контекст

Для этого пользователя скил — его личный промпт, упакованный под кодовое
слово. Исполняющий агент может не иметь истории разговора, из которой
возникли намерение, местные факты и существенные ограничения.

Пользователь хочет передавать агенту такое понимание ситуации, из которого
компетентный исполнитель способен самостоятельно вывести нужное поведение.
Задача уточняет заказ, а дополнительные условия сообщают то, чего из
описанной ситуации вывести нельзя.

Знания внутри скила нужны в разные моменты. Пользователь придаёт особое
значение тем моментам, где ошибка дорога или правильный выбор требует
сложного понимания.

## Задача

Создай или переработай скил из намерения пользователя, проверь получившееся
поведение и после утверждения установи согласованную версию в нужные среды.

## Критерии принятия

В скилле не больше семи условных наборов. Каждый содержит не больше семи
самостоятельных инструкций или знаний, которые нужно применять при его
активации. Считаются отдельные требования к вниманию, а не маркеры списка.

## Цель

Добивайся, чтобы агент действовал в соответствии с намерением пользователя
при наименьшей необходимой нагрузке на его внимание.

Когда частных инструкций недостаточно или предложенные способы противоречат
друг другу, выбирай решение по этому принципу. Необходимый смысл сохраняется;
способ его передачи можно пересмотреть.

## Когда пишешь раздел «Контекст»

Применимо при выборе и описании мира, который должен стать известен
исполняющему агенту. Выход — достаточное понимание ситуации.

- Контекст передаёт только значимую дельту: сведения, которых конкретный
  читатель не знает и не может надёжно восстановить самостоятельно.
- Описывай состояние мира: положение пользователя, устройство ситуации,
  существующие отношения и последствия. Из этого описания должно быть
  понятно, почему возникла работа.
- Каждый факт должен менять понимание ситуации или правильного поведения.
  Самой новизны недостаточно, чтобы включать факт.
- Опирайся на слова пользователя и проверяемые источники. Правдоподобная
  история, придуманная автором скила, не становится контекстом пользователя.
- Мысленно оставь читателю только контекст. Сможет ли компетентный агент
  понять проблему и вывести разумное направление действий? Если нет,
  найди недостающее звено в описании мира.
- Общий метод построения управляющего текста бери из `1agent-steering`.
  Его применение должно быть видно в существенных авторских решениях.

## Когда уточняешь задачу и решаешь, нужны ли критерии принятия

Применимо после прояснения ситуации.
Выход — конкретный заказ и необходимые уточнения успеха.

- Задача уточняет, какую работу пользователь поручает в описанном мире
  и какой результат должен получить.
- Объяснение ситуации уже принадлежит контексту. Задаче достаточно
  конкретизировать выбор работы.
- Дополнительный критерий сообщает уникальное условие успеха, которое
  исполнитель не восстановит из контекста и задачи.
- Для каждого критерия назови допустимый без него неверный результат.
  Если такого различия нет, критерий не добавляет защиты.
- Если контекст и задача уже определяют необходимое, раздел
  «Критерии принятия» отсутствует.
- При создании используй `references/goal-context.md`; при переработке
  существующего скила маршрут восстановления намерения определяет
  `references/refactor.md`.

## Когда формулируешь раздел «Цель»

Применимо при выборе общего принципа, который будет направлять работу
за пределами перечисленных случаев.
Выход — понятное правило разрешения неопределённости и конфликтов.

- Цель выражает самое высокое намерение пользователя, которому служит
  конкретная задача.
- Её формулировка должна помогать выбрать между правдоподобными решениями:
  какое лучше сохраняет нужный результат и почему.
- При конфликте вспомогательного способа с назначением работы
  пересматривается способ. Смысл заказа остаётся основанием выбора.
- Общая цель не отменяет существенное условие пользователя только потому,
  что без этого условия удобнее выполнить работу.
- Проверяй цель на неописанном случае или конфликте двух требований.
  Если из неё нельзя вывести предпочтение, формулировка пока слишком пуста.

## Когда выбираешь условия активации

Применимо при распределении содержания по случаям.
Выход — группы, соответствующие реальным моментам потребности в знании.

- Отдельного условия прежде всего заслуживают важные или сложные части:
  места дорогой ошибки, существенного выбора или неочевидного понимания.
- Простые действия не требуют собственного раздела только ради полноты
  перечисления стадий.
- Условие может включать знания без отдельной команды к действию.
  «Когда пишешь контекст, учитывай такое устройство ситуации» —
  полноценный случай применения.
- Условие должно позволять распознать начало и окончание применимости
  набора. Тематического заголовка для этого недостаточно.
- При пересечении условий учитывай весь одновременно нужный набор,
  включая общую цель и продолжающие действовать обязательства.
- Самостоятельные режимы и стадии оформляй по
  `references/reference-files.md`. Перенос текста разгружает работу
  только тогда, когда разделяет реальные моменты его применения.

## Когда формулируешь отдельное знание или инструкцию

Применимо к содержанию, необходимость и момент применения которого ясны.
Выход — однозначная единица текста.

- По Minimal Critical Specification оставляй необходимое для правильного
  поведения. Компетентность агента позволяет не предписывать очевидное.
- Одна единица передаёт одно самостоятельное знание или требование.
  Независимо применимые части разделяются.
- Причина находится рядом с требованием: какое обстоятельство делает
  его важным и что изменится при его пропуске.
- Длина определяется ясностью. Экономия символов не оправдывает потерю
  условия, причины или существенного различия.
- Дополнительный протокол проходит отбор по
  `references/behavior-protocol.md`, включая предложенный пользователем
  способ работы.
- При формулировании имени и description используй
  `references/skill-short-description.md`: эта поверхность должна
  приводить к вызову скила в нужный момент.

## Когда проверяешь готовый черновик

Применимо перед утверждением конкретной версии.
Выход — проверенный результат или названное место необходимой доработки.

- Помни о «сломанном джине»: формальное выполнение текста может оставить
  пользователя без желаемого результата.
- Проверь, восстанавливает ли чистый читатель нужное понимание из
  переданного контекста. Знание автора не считается знанием читателя.
- Проверь, добавляют ли задача и критерии необходимые уточнения,
  а цель — правило выбора при неопределённости.
- Условия проверяются при применимости, неприменимости и предусмотренных
  пересечениях. Пересказ всех элементов не доказывает правильной активации.
- Проведи проверку по `references/check-approve.md`.
- Покажи пользователю существенные изменения его предложенного способа
  вместе с основаниями: решение должно оставаться доступным проверке.

## Когда устанавливаешь утверждённую версию

Применимо после утверждения конкретного текста.
Выход — подтверждённая доставка этой версии.

- Утверждение относится к показанной версии. Последующая смысловая
  правка меняет предмет утверждения.
- Выполни `references/install-approved.md`.
- Подтверди совпадение состава и содержимого установленных файлов.
  Недоставленная среда остаётся явно названным незавершённым результатом.
