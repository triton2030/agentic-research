# Исполнение: Codex делает работу

**Момент.** Работа отдаётся целиком, а не выносится на суждение. Третья роль по
приоритету владельца — и самая дорогая, потому что только у неё есть право
писать.

**Выход.** Результат, доехавший до проекта, либо артефакт в папке прогона,
который ты забрал сам.

Разделитель один: **правит ли Codex файлы проекта.**

| Куда падает результат | Вход |
|---|---|
| себе в папку прогона; проект для записи недостижим | `codex_investigate.py "ЗАДАНИЕ + формат выхода" --project "$PWD" --summary-stdout` — забирай `result.json` и `out/` |
| в файлы проекта | `codex_orchestrate.py` — волна воркеров, контракт ниже |
| markdown-адреса «сходи в knowledge и принеси» | `(cd /Users/triton/Documents/My_projects/md-tools && uv run python scripts/run_md_scout.py КОРПУС --question "ВОПРОС")` — read-only executor `1md-search`, без вердиктов; приёмка по пакету, не по exit code |

**Веер вместо одного прогона** — когда работа делится. Читающим по своему
участку, исследователям по своей оси: расхождение осей и есть находка, а пять
одинаковых прогонов её не дают. **Схема выхода одна на весь веер** — иначе пять
форм ответа ты нормализуешь в своём окне, ради экономии которого веер и заводил.

Работа не поделена точными путями — это ещё не волна: сперва read-only разведка
исследователем, потом флот.

## Каждый воркер — в своём дереве

По умолчанию (`--isolation worktree`) прогон заводит воркеру отдельный git
worktree от текущего HEAD и работает там. Это меняет три вещи по существу:

- **Атрибуция.** Диф считается в его дереве, поэтому «кто написал этот файл» —
  факт, а не догадка. В общем дереве воркер A мог задеть файл воркера B, и
  union-чек проходил у обоих.
- **Отбраковка.** Запись вне его списка файлов в проект не попадает — но и не
  теряется: любая внесписочная правка удерживает от merge ВСЮ работу воркера
  (правка по списку могла на неё опираться), и всё изменённое целиком
  фиксируется в его ветке на ручной разбор.
- **Свобода тебе.** Пиши recall, планы и артефакты в основном дереве, пока волна
  идёт: волну это больше не валит. Раньше валило — 68% записей
  `out_of_scope_files` по 106 боевым волнам были твоим же служебным шумом.

Цена честная: дерево — выкладка проекта (22 МБ на `agentic-research`, 650–780 МБ
на большом фронтенде), и воркеры не видят правок друг друга. Задачам, обязанным
видеть чужие правки, нужен `--isolation shared` — прежнее поведение с
aggregate-чеком.

## Сколько воркеров

Читающий веер бесплатен, пишущий платит диском. Поэтому **единица деления у
пишущих — группа задач, а не задача**: двадцать дел это четыре воркера по пять,
каждому `subagents: true`. Связную работу (одна фича, один слой) не дроби
вовсе — целиком у одного дешевле. Число воркеров выбирай по цене дерева и
связности, не по числу дел.

Делегация внутрь воркера нужна явным словом: системный промпт движка запрещает
субагентов, пока их не попросят — «Do not spawn sub-agents unless the user or
applicable AGENTS.md/skill instructions explicitly ask». Независимым взглядом они
не являются: наследуют рамку родителя.

## Запуск волны

1. **Разрежь работу на file-disjoint задачи** — два воркера не правят один файл.
   Footprint должен быть известен заранее точными путями.
2. Собери JSON-массив: `[{"id","prompt","files":[...]}]`. Одна запись = один
   воркер = его группа дел: список дел живёт в `prompt`, а `files` покрывает их
   все. `prompt` и `files` обязательны; `files` — exact file paths, не папочные
   scopes; `cwd` в задаче запрещён; для нового файла `allow_create: true`; чтобы
   воркер делил свою группу на субагентов — `subagents: true`; ремонтная волна
   кладёт в задачу `thread_id` воркера прошлой. `id` идёт в путь дерева и имя
   ветки: без `/`, пробелов и git-спецсимволов, уникальный в волне.

   В карту волны и её носитель (`context.md` папки волны либо план) handle
   воркера пиши как `thread_id` + `RUN_DIR`: без них новое окно после обрыва
   восстанавливает соответствие «воркер → тред» вручную. Сами треды не теряются —
   они персистентны и печатаются `codex_threads.py mine`.
3. Запусти пул:

```bash
B=/Users/triton/Documents/GitHub/agentic-research/experiments/codex-bridge
echo '[{"id":"t1","prompt":"...","files":["a.md"]}]' \
  | $B/.venv/bin/python $B/codex_orchestrate.py --project "$PWD" --summary-stdout
# большой список — через файл: --tasks tasks.json ; сухой план запуска: --dry-run
# --concurrency N — сколько воркеров разом; дефолт 4, передавай только другое
# --verify "команда" — повтори флаг для КАЖДОЙ проверки, которую иначе прогнал бы руками после интеграции. В дефолтном worktree это ворота: проверка идёт по временному СЛИТОМУ дереву до merge. При --no-integrate пропускается, при --isolation shared ворот нет — воркеры уже в проекте
# посмотреть работу до забора в проект: --no-integrate (деревья и ветки остаются)
```

Выход — `result.json` с `worker_status`, `scope_status`, `verification_status`,
`wave`, `fully_verified`, `ok`, `run_dir` и результатами воркеров. **В stdout
компактной проекции ответов воркеров нет** — за ними иди в `result.json`.

`--dry-run` создаёт run_dir со `status=validated` — это план, не результат.

## Контракт: нарушишь — потеряешь правки

- **File-disjoint enforced.** Backend режектит overlap до запуска Codex. Это
  runtime-исполнение общего правила `1orchestration`: пересекающиеся записи
  получают одного писателя либо последовательный handoff.
- **Prompt-обещания ⊆ `files`.** Каждый путь, который prompt называет к записи
  («положи в X»), проверь в `files` до запуска: запись вне списка удержит от
  merge всю работу воркера, и волна кончится ручным разбором ветки вместо
  результата.
- **Preflight fail-closed.** Невалидный JSON задач падает ДО запуска Codex —
  кредитов это не стоит, ошибку читай в выводе инструмента.
- **Git fail-closed.** Реальный запуск требует git, а worktree-изоляция — ещё и
  `--project` в корне репозитория: от подпапки allowlist и дерево считались бы
  от разных корней. Пересечение dirty files со списком блокирует запуск; осознанный
  override — `--allow-dirty-overlap`.
- **HEAD вперёд — можно, назад — нельзя.** Свои коммиты поверх во время волны
  (recall, планы) — норма, merge их переживает. `reset`/`rebase` ниже базы волны
  удерживает всех воркеров (`held_base_rewritten`).
- **Max-safe permissions.** Дефолт не `full-access`: такой режим может менять
  файлы вне project/git scope, а backend не сможет доказать allowlist. Максимум —
  `workspace-write` внутри дерева воркера плюс guardrails моста.
- **`scope_status=failed` остаётся failure.** В изоляции он означает запись вне
  allowlist в дереве воркера либо сорванную интеграцию — читай
  `out_of_scope_files` и `wave`. Легитимный детерминированный side effect объяви
  в footprint до следующего запуска.
- **`worker_status=completed` не равно done.** Механическая проверка перед
  доверием: `--verify`, `git diff`, тесты.

## Закрытие волны идёт само — проверь, что оно случилось

Несущее: **работа не удаляется никогда** — коммит в ветку воркера делается до
любой уборки, даже когда интеграции не будет.

В проект НЕ вливается, а целиком остаётся в ветке воркера на ручной разбор:

- ход воркера не завершился — полуфабрикат не едет в проект;
- воркер писал вне своего списка;
- дерево родилось грязным **в зоне воркера** (`held_dirty_birth`: post-checkout
  hook писал в файл из его списка). Посторонний артефакт того же hook воркера не
  держит: боевая волна `20260814T085606Z` удержала всех троих из-за одного чужого
  `.png`, и восемь готовых файлов не влились;
- история переписана ниже базы волны (`held_base_rewritten`);
- merge конфликтует;
- проверка волны красная (`held_verify_failed`): воркеры сливаются во временное
  дерево, `--verify` идёт там, и провал оставляет проект нетронутым.

Что читать в `wave` из результата:

| Поле | Что значит |
|---|---|
| `integration_status` | `integrated` · `partial` · `conflict` · `held` (`--no-integrate`) · `error` |
| `merged` | воркеры, чья работа уже в проекте |
| `held` / `conflicts` | не влиты: работа цела в ветке, забирать вручную |
| `kept_branches` | **незабранная работа** — разбери до следующей волны; merged-ветки при `--keep-worktrees` сюда не попадают |
| `cleanup_done` | факт с диска, не просьба; `cleanup_stuck` — что не удалилось |
| `threads_archived` / `threads_stuck` | исход тредов воркеров; оба пусты при `--keep-worktrees` — там дерево живо |
| `main_tree_drift` | что менялось в основном дереве во время волны (обычно твоё) |

**Волна не закрыта, пока не названы `cleanup_done`, `kept_branches` и
`threads_archived`** — решение владельца 2026-08-18. Уборка не заканчивается
словом «убрал»: непустые ветки — незабранная работа, висящее дерево — выкладка
проекта, неархивированный тред — карточка-проект в никуда.

## Остановка и ремонт

Мост **interrupt на асинхронном пути не подключил** (SDK его даёт). Прогон
успевает зафиксировать работу воркеров в их ветках и напечатать их, но
`result.json` не пишется, а деревья остаются. Ручки после остановки:

```bash
git worktree list                     # чьи деревья висят (наши — в ~/.codex-bridge)
git worktree remove <path>            # откажется, если внутри незакоммиченное
git worktree prune                    # выкинуть мёртвые записи
git branch --list 'codex-fleet/*'     # незабранная работа воркеров
```

Деревья под `~/.codex/worktrees` создаёт Codex Desktop/CLI, а не мост: там может
лежать незабранная работа владельца — руками не удаляй.

**Ремонтный круг тёплым воркером:** в задаче следующей волны тот же `id` плюс
`thread_id` из `results.jsonl` прошлой. Дерево, файловый контракт и `--run-dir`
всё равно свежие — «доделай в том же процессе» не существует. Второй круг без
сходимости — свежий воркер, без `thread_id`.

**Стоп:** два-три круга verify→fix без сужения носителей — стоп и блокер
владельцу, а не третий круг.
