# Design Review

## Контекст

Владелец выбрал физическое разделение внимания, чтобы локальные дефекты не
терялись в большом скриншоте, а правдоподобный отчёт не подменял проверку: «один субагент
получает одну картинку», «целый субагент анализирует только свой маленький
участок». Целостный взгляд и решение о значимости замечаний остаются у
главного агента: отдельный участок не показывает, как работает вся страница.

## Задача

Проведи визуальное ревью отрендеренного интерфейса по скриншотам и верни
вердикт о его готовности с лично проверенными замечаниями. Для полного
ревью собери независимые локальные оценки через изолированных проверяющих;
условие узкого прохода описано ниже.

## Цель

Пользователь понимает, что действительно мешает готовности интерфейса и что
следует сохранить. При конфликте целостной композиции и локальной полировки
приоритет имеют композиция, согласованность и распределение смыслового веса.

## Когда определяешь объём ревью

Скилл применяется к видимому дизайну: иерархии, композиции, читаемости,
типографике, перекрытиям, обрезанию и воспринимаемым возможностям элементов.
Создание UI до render, функциональная проверка браузера, диагностика причин
в CSS/DOM/code, редактирование Figma, OCR и критика изображений вне UI
относятся к другим задачам. Если render отсутствует, сначала нужна реализация;
если запрос о том, что не нажимается, ломается или тормозит, нужен QA/diagnosis.

Полное ревью — оценка готовности экрана/страницы, нескольких самостоятельно
оцениваемых областей или состояний, milestone/final signoff. Оно требует
локальных evidence tasks и изолированных проверяющих. Узкий проход — одно
заранее названное визуальное условие в одном target: его может закончить
главный агент самостоятельно по исходному изображению, без crop и fanout,
если изображение достаточно. Размер viewport сам по себе объём не определяет.

## Когда осматриваешь страницу перед локальным разбором

Открой обычный rendered frame. Зафиксируй первое впечатление и известные
аудиторию, основное действие, задуманный характер и требования к вкусу;
неизвестное оставь неизвестным. Итоговый вердикт пока не выноси.

Для полного ревью выбери первый экран, каждый существенно отдельный смысловой
блок, значимые переходы, семейства компонентов и responsive/interaction
states, где меняется дизайн. Существенен участок или state, способный изменить
готовность, главные действия или решение сохранить удачное. Это определяет
охват и число изображений; числовой квоты нет.

## Когда выбираешь локальные вопросы

Один обычный target или видимая связь получает одну открытую задачу поиска
материальных дефектов: id, question, один evidence id и решение, на которое
повлияет ответ. Не дроби тот же участок на отдельные typography, spacing,
color, hierarchy и alignment tasks: они размножают мнения об одних пикселях.
Другой captured state/relationship — самостоятельный вопрос.

Большой кадр остаётся только у главного агента. Для локального вопроса нужен
маленький crop, для перехода секций — узкая полоса, для семейства — один
коллаж максимум из четырёх явно выбранных элементов. Вопрос обо всей странице
«что здесь не так» не становится локальным от уменьшения изображения.

## Когда обычного изображения недостаточно

Для того же target создай один дополнительный diagnostic, только когда
обычные пиксели не изолируют конкретный вопрос плотности текста или отступов,
а ответ способен изменить вердикт или действие. По умолчанию они не нужны.

Плотность текста показывается белым фоном и красными блоками вместо текста;
карта отступов убирает контент и выделяет отступы цветом. Это разные
изображения и разные tasks; смешение скрывает, что именно измеряется.
Технический способ их создания относится к следующему случаю.

## Когда готовишь изображения

Прочитай [evidence-protocol.md](references/evidence-protocol.md) до создания
capture plan: файл задаёт вход и преобразования для live UI и supplied images.
Для live UI используй bundled `scripts/design-review`; для derived artifacts
из готовых скриншотов — image sources с явными rects.

Весь project run — PNG, manifest, reviewer logs/reports и adjudication — держи
в `<project>/_workspace/design/1design-review/<MM-DD>/<run-id>/`. Для projectless
screenshot используй отдельную temporary run directory и верни её точный путь.

Открой manifest и каждый PNG, проверь target, state, контекст и читаемость.
Ошибку capture исправь до запуска проверяющих. Затем выполни:

```bash
scripts/approve-design-evidence.mjs \
  --run-dir "<absolute-run-dir>" \
  --all-reviewer-evidence
```

Этот gate связывает личный осмотр с конкретными файлами. Изменение manifest
или PNG требует нового осмотра и approval; механизм проверяет SHA-256 manifest,
canonical path, SHA-256, размер файла и размеры изображения.

## Когда запускаешь проверяющих

Один проверяющий получает ровно один назначенный PNG; один PNG — ровно одного
проверяющего. Передай question, минимальный известный контекст аудитории,
основного действия, характера и вкуса и [questions.md](questions.md).
История чата, инструкции проекта, код, чужие находки, интерпретация главного
агента, соседние crops и исходный большой кадр ему недоступны.

Используй bundled runner: он обеспечивает temporary CODEX_HOME с auth-only
copy, neutral cwd, ignored rules/config, OS allowlist sandbox и task-local
копию одного attachment с запретом чтения общего run directory. Эти границы
нельзя заменить обещанием в prompt не смотреть соседние файлы.

Runner допускает до трёх процессов глобально и не допускает второй run
параллельно. Очередь может включать 50–60 задач: доведи её до завершения
ограниченными партиями; это допустимый масштаб, не норма для каждого экрана.
При промахе evidence допустимо одно ограниченное исправление; повторный
промах завершает задачу как failed.

## Когда проверяешь замечания

Для каждого candidate заново открой точные пиксели и зафиксируй finding id,
evidence id, видимое условие, эффект для пользователя/дизайна,
confirmed/challenged/unverified, собственную severity и действие при
подтверждении. Итоговое суждение принадлежит главному агенту; отдельный
агент, агрегирующий отчёты без пикселей, не используется.

Общий вкус без видимого основания, невидимое условие, дубликат и находка вне
question отклоняются. Изображение не подтверждает условие — claim остаётся
unverified. Код не доказывает визуальный дефект; поиск его причины переходит
в отдельный technical pass после подтверждения пикселями.

Точные размеры, цвета, ratios, contrast и tap-target thresholds, фактическая
clickability, runtime overflow и скрытое поведение требуют deterministic
manifest/check. Визуальное впечатление об этих свойствах не является замером.

В run с artifacts сохрани `adjudication.json` с lifecycle
open/fixed/rejected/deferred/routed уже при первичной проверке замечаний.

## Когда возвращаешься после исправлений

Повторным проверяющим передавай только
open ids и свежие изображения. Fixed/rejected/deferred возвращаются в разбор
только при противоречащих пикселях: иначе проход превращается в бесконечную
полировку уже принятого.

Routed не возвращается визуальному проверяющему. Главный агент пересматривает
его после результата названного deterministic/technical check; для этого
противоречащие пиксели не обязательны.

## Когда сравниваешь состояния до и после

На подготовке создай две независимые state tasks по одному PNG и проведи
каждую через соответствующие случаи выше. После проверки обоих отчётов сам
открой оба изображения, назови видимое изменение и только затем оцени
better / worse / merely different. Само различие не доказывает улучшения.

## Когда выносишь вердикт

Первая строка — ready / not ready / evidence-limited и сильнейшее видимое
основание. Затем дай 1–3 подтверждённых приоритета с evidence ids и эффектом
для пользователя; что уже держится и должно сохраниться; недостающие
проверки и один следующий gate либо stop. Если подтверждённых проблем нет,
не заполняй число приоритетов выдуманными. Отклонённый шум нужен в ответе лишь
тогда, когда он мог изменить решение. Для failed task назови id и log path;
частичный run не означает, что его вопрос покрыт.

Остановись, когда минимально достаточные изображения поддерживают вердикт,
все полученные candidate findings разобраны, а каждый оставшийся пробел,
способный изменить решение, назван как конкретный missing state или check.
