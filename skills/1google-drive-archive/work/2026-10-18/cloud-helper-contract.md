# Metadata adapter contracts

Date: 2026-10-18. Status: offline-tested portable asset; this version has not been run in Apps Script. Source: `Code.gs`, manifest, `node --test test.mjs` on Node 26.10.0. No real user files, UI, OAuth flow, or Google cloud calls were used in these tests.

Only install `Code.gs` and `appsscript.json` in an owner-only private Apps Script project. The companion tests use Node built-ins with fake Drive, Properties, LockService, Utilities; one compatibility test invokes Python's `valid_remote` from the sibling local-helper without hashing or opening user files. The manifest enables Drive v3, V8, one `drive.metadata.readonly` scope and `exceptionLogging: NONE`. The helper has no token getter, HTTP client, upload, delete, content-download, or Drive mutation path. ScriptProperties writes only helper checkpoints; project editors can read them. Never share this project or its properties with third parties.

## Snapshot

Set nonempty `FILE_IDS` to real IDs obtained through an authorized path. Empty defaults reject before any Drive call. `metadataSnapshot()` fetches `About.user.permissionId` plus explicit `Files.get` metadata fields; it emits one JSON line per ID, after validating **all** requested rows. Exact schema: `schemaVersion`, `checkedAt`, `accountKey`, `fileId`, `size`, `sha256Checksum`, `md5Checksum`, `version`, `trashed`, `binaryFile`, `canDownload`, `ownedByMe`.

`size` is a canonical decimal string (at most 25 digits, matching the local validator). Missing size, MIME type or ID, a different returned ID, malformed checksums/version/booleans, and API failures produce a generic `SNAPSHOT_FAILED` line instead of partial snapshot rows. Optional checksums/version/booleans may be null; that is not proof of a backup. Native Google MIME types have `binaryFile=false`; native objects without size fail this snapshot contract. `canDownload` comes from `capabilities.canDownload`. Account identity is a permission ID, never email or an OAuth token. Actual `About.user.permissionId` availability for the intended authorized account still needs a future live run; the older pilot established identity separately through browser/connector.

Save fresh snapshots immediately before and after a fresh local byte hash. These metadata rows alone do not establish a local `MATCH`. The separate local verifier owns comparison and stability rules. Names, descriptions, HTTP headers, full response objects, error text and stacks never enter helper output. Apps Script's own authorization UI/execution envelope is outside the helper's log contract; caught exceptions are never rethrown.

## Paginated search

Set `TARGETS` to 1–32 records `{index, name, size, sha256, md5}`. Index is a unique nonnegative safe integer; size is a decimal string, and at least one checksum is required (null means unavailable). Names participate only in config binding and weak fallback comparison; they are never output or stored in plaintext state. Set `RUN_ID` to a **new unique** alphanumeric/underscore/hyphen value for each new inventory. Keep the same ID/config only to resume. Empty run or targets reject before any Drive call. Optional `DRIVE_ID` selects one shared drive.

`continueArchiveScan()` issues `Files.list` with `spaces=drive`, `corpora=user` or `corpora=drive` plus `driveId`, `pageSize=1000`, and `trashed=false` / nonfolder query. It explicitly requests `files(id,name,size,sha256Checksum,md5Checksum,mimeType,trashed),nextPageToken,incompleteSearch`. Each invocation processes at most 20 pages / starts new pages for at most 150 seconds. One API call can exceed the time budget; this cannot cancel an in-flight call.

Private ScriptProperties checkpoints are keyed by a SHA256 of RUN_ID and bound to account permission ID, run ID, a digest of normalized targets/scope, and exact scope `{corpora,spaces,driveId,trashed:false,excludeFolders:true}`. State saves `startedAt`, `lastPageCheckedAt`, `completedAt`, and an invocation count; load validates identity, timestamp formats/order, scope, progress and token fingerprints before emitting any stored values. Old checkpoints from versions lacking these fields fail closed with `STATE_INVALID`; use a new RUN_ID. New unique RUN_ID adds a separate run; it does not delete prior checkpoints. Reusing a completed RUN_ID emits `SCAN_ALREADY_COMPLETE` with `freshInventory=false`, without listing files. Reusing any RUN_ID with changed config or account rejects. A new unique RUN_ID can bind a new config/account. No automatic deletion or cleanup of stored runs exists.

Each valid page is committed as one property (under an 8,000-byte conservative bound), with read-back verification. Failed requests retry the same saved cursor on the next call. Setter errors are checked by reading back the intended value; otherwise the output stays incomplete. Script lock prevents concurrent helper executions. The helper does not print cursors; SHA256 token fingerprints (16 hex) detect repeated/cyclic next tokens and are saved with progress. Empty pages with advancing tokens are supported. `incompleteSearch=true`, missing required page/file fields, malformed metadata, duplicate IDs within a page, token cycles and cap failures halt without committing that page. A persisted halt needs a new run after resolving its cause; rerunning returns `SCAN_HALTED`.

The whitelist scan result contains schema/status/code, accountKey/runId/configDigest/scope, startedAt/lastPageCheckedAt/completedAt, `complete`, `freshInventory`, page/file counts, candidate count, and bounded `{index,id,matchkind}` candidates. Unavailable manifest fields are null on errors before valid state is loaded. `startedAt` never resets on resume; `lastPageCheckedAt` advances only with an accepted committed page, and completedAt equals the terminal page check time. These dates describe a collection window. Candidate pairs are deduplicated across pages. SHA256 with equal nonzero size emits `SHA256_CANDIDATE`; if SHA256 is unavailable on either side, equal MD5/size emits `MD5_CANDIDATE`; if comparable hashes are unavailable, exact name/size emits `NAME_SIZE_CANDIDATE`. A mismatching comparable stronger hash never falls back to a weaker match. All are **candidates**, never a final local `MATCH`. Zero-byte targets/files and native Google objects never become backup candidates.

## Limits and safe failure

- Candidate cap is 32 total, not 32 per target. Overflow rejects the **whole current page**, retains previously committed candidates/cursor, and reports `complete=false` / `CANDIDATE_LIMIT`. Retry with smaller target batches and a new RUN_ID; inspect overly common weak matches. Do not infer no other matches from retained candidates.
- State-size overflow reports `STATE_LIMIT`, with the offending page uncommitted and no claim of completion. Narrow targets, split target batches and/or select a narrower supported corpus. Token history alone eventually fills state for sufficiently large page counts; smaller batches alone cannot solve that case. The synthetic 201-page/201-file run fits below 8 KB. No unlimited-inventory guarantee is made.
- ScriptProperties quota, permission or service errors report `STATE_WRITE_FAILED`, retaining the last committed checkpoint when the write is known not to have committed. If the platform cannot confirm a write by read-back, outcome remains incomplete; inspect/retry before assuming progress. Quota can also accumulate across many retained RUN_IDs; manage only this helper's run properties manually after exporting evidence, never clear unrelated project state.
- Drive page tokens expire. A rejected token is a generic `API_FAILED`; raw messages are deliberately suppressed. Retry once; if it remains rejected, begin a new RUN_ID from page one. Do not replace the saved cursor inside the same run or combine partial inventories.
- Counts are API rows, not globally distinct file IDs. Keeping a seen-ID set for every object in a 157k-file Drive exceeds this small helper's persistence design. Arbitrary duplicate noncandidate IDs across distinct pages are not detected; duplicate candidate pairs are deduplicated, within-page duplicates halt. This is an explicit limitation, not production-complete duplicate detection.
- A fully paginated Drive listing can change while scanning. `complete=true` means every accepted next-page token was followed to exhaustion in the selected corpus, not a transactionally immutable snapshot or proof of visibility into every shared drive. `freshInventory=true` requires a new run to finish during its first invocation; a resumed run always returns false, even when it completes today. No time-based freshness verdict is implied, even within one invocation; use the preserved collection dates. `corpora=user` covers files owned/shared to the authorized user, not every file in all shared drives. Run a specific DRIVE_ID separately when that scope matters.
- Official `files.list` documentation explicitly assigns absent nextPageToken the end-of-list meaning, but does not explicitly authorize treating an absent files field as an empty array or absent incompleteSearch as false. The inspected earlier pilot used `page.files || []` and `page.incompleteSearch === true`; that implementation is not evidence that those fields were present in its live responses. This helper therefore retains strict `MISSING_FIELDS` for either omission. A live service that omits them will stop safely incomplete; compatibility of that behavior remains unverified.
