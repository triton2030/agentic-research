```md
# Project-local packages 2*

## Граница ответственности

Этот скил владеет только локальной дельтой упаковки: именем `2*`,
совместимостью с инструкциями проекта, единственным project owner и одинаковым
состоянием Claude/Codex.

Всю обычную работу над содержанием и структурой скила, authoring-проверки и
exact approval выполняй через `$1skill-creation`. Не повторяй здесь его
методику, не создавай собственные trigger/behavior checks и не запускай второй
процесс утверждения.

Если `$1skill-creation` недоступен или exact-approved состояние не получено, не
изменяй package surfaces.

## Установи фактическую topology

До первого изменения установи по применимым инструкциям проекта и уже
существующей topology:

- единственный project owner;
- Claude projection;
- Codex projection;
- действующий в проекте механизм projection.

Учитывай применимые global и root instructions отдельно для Claude и Codex.

Не выводи owner из одной из projections и не выбирай projection источником
правды по свежести файлов. Не выдумывай отсутствующий путь, source tree или
механизм projection. Если topology неполна, неоднозначна или противоречива,
остановись и назови точный пробел.

## Передай authoring владельцу

Передай `$1skill-creation` локальные ограничения: package name начинается с
`2`, один и тот же полный artifact предназначен обоим runtime, а его правила
не могут ослаблять применимые global или root instructions.

До projection сопоставь exact-approved artifact с применимыми инструкциями
обоих runtime. Project-local skill может добавлять относящуюся к проекту
конкретику или более строгое ограничение, но не может ослаблять либо
опровергать действующее требование. Более узкий scope и обычный precedence не
исправляют такой конфликт.

При конфликте не исправляй artifact самостоятельно и ничего не проецируй.
Верни конфликт в `$1skill-creation`; изменённый artifact должен пройти его
authoring flow и exact approval заново.

## Сведи три поверхности к одному состоянию

При создании или обновлении помести exact-approved package в установленный
project owner и получи обе projections только из него существующим механизмом
проекта. Никогда не редактируй projections независимо и не создавай
runtime-specific варианты.

Завершённое состояние создания или обновления имеет одинаковый разрешённый
набор относительных файлов и одинаковое содержимое файлов у owner, Claude
projection и Codex projection.

При снятии package сначала получи exact approval операции через
`$1skill-creation`, затем обеспечь полное отсутствие package у owner и в обеих
projections.

Считай переход неделимым. Если целевое состояние нельзя получить полностью,
верни предыдущее согласованное состояние либо предыдущее полное отсутствие.
Частичная topology, расхождение projections и придуманная поверхность не
являются результатом.

Если обнаружен прежний drift, не принимай ни одну projection за правду;
восстанавливай согласованность только из установленного owner и exact-approved
artifact.

## Доказательство результата

Не повторяй authoring-, trigger- или behavior-проверки `$1skill-creation`.
Здесь докажи только локальные инварианты:

- topology подтверждена существующими инструкциями или устройством проекта;
- artifact не ослабляет и не опровергает применимые инструкции обоих runtime;
- exact approval относится к фактически установленному artifact или к его
  снятию;
- три поверхности имеют одинаковые разрешённые file manifests и byte hashes
  либо package отсутствует на всех трёх.

Если любой инвариант не доказан, назови результат незавершённым.

В сдаче укажи операцию, owner и обе projections, основание topology, ссылку на
exact approval, проверенные instruction surfaces, доказательство parity либо
полного отсутствия и оставшиеся неизвестные.
```
