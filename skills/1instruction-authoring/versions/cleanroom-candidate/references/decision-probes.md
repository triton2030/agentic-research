# Решенческие probes для проектных инструкций

## Цель

Этот протокол самостоятельно проверяет, что кандидат доставляет внешнюю правду
до зависимого решения, меняет наблюдаемое поведение и не покупает локальную
пользу постоянной нагрузкой или закрытием законного пути.

## Входы

Подготовь:

- один реальный рабочий сценарий с первым зависимым решением;
- адрес единственного владельца факта, который должен изменить решение;
- текущее состояние и состояние с кандидатом;
- один нерелевантный сценарий из соседнего рабочего пути;
- ожидаемые допустимые исходы, записанные до запуска, но не показанные
  испытуемому агенту.

Не конструируй сценарий из формулировок кандидата. Возьми обычную задачу,
ради которой инструкция создаётся.

## Контрастный запуск

1. Запусти два свежих изолированных контекста с одинаковой задачей и одинаковыми
   полномочиями. Контекст A видит текущее состояние, контекст B — кандидата.
2. Не сообщай агентам ожидаемый ответ, адрес владельца и критерии оценки.
3. Сохрани по каждому запуску порядок открытых источников, момент первого
   решения, само решение и адресованное evidence, использованное до него.
4. Сравни наблюдения по таблице:

| Проверка | A: текущее состояние | B: кандидат |
| --- | --- | --- |
| Владелец достигнут до первого решения | | |
| Решение согласуется с внешней правдой | | |
| Истина не скопирована в нового владельца | | |
| Активированы только нужные инструкции | | |

Кандидат проходит контраст, если B достигает владельца до решения и принимает
допустимое решение, а A этого не делает. Если оба запуска уже одинаково
успешны, новый маршрут не доказал необходимость. Если оба неуспешны, исправь
точку доставки или найденного владельца и повтори на свежих контекстах.

## Негативный и нагрузочный запуск

Запусти нерелевантный сценарий в текущем состоянии и с кандидатом. Зафиксируй
фактически активированные instruction-файлы, переходы к владельцам и чтения
соседних зон. Кандидат проходит, только если он не добавляет нерелевантную
нагрузку и не меняет допустимый исход.

Проверь как минимум формы путей, которые реально существуют у кандидата:

- путь внутри зоны, где правда уже наследуется;
- путь через явный межзонный маршрут;
- путь, на котором новый маршрут не должен активироваться.

Не заменяй этот запуск подсчётом общего размера пакета: важен фактический active
set каждого пути.

## Проверка владельца и адресов

- Каждая доставленная истина имеет один канонический адрес.
- Маршрутизатор содержит условие и адрес, но не самостоятельный пересказ истины.
- Все ссылки существуют из фактического рабочего каталога агента.
- Канонические и итоговые адреса не изменились без явного разрешения на точную
  новую версию.
- Более приоритетные инструкции и границы полномочий продолжают действовать.

## Проверка законного пути

Составь один сценарий, который не должен следовать предпочтительному маршруту.
Он проходит, если агент распознаёт неприменимость маршрута и может выполнить
разрешённый альтернативный ход. Без такого негативного примера запрет может
выглядеть безопасным, одновременно закрывая работу.

## Receipt

Верни:

```text
Scenario:
First dependent decision:
Sole owner:
Baseline observation:
Candidate observation:
Evidence opened before decision:
Unrelated-path active set:
Legitimate alternative-path result:
Mechanical checks:
Verdict: pass | fail | unknown
Unverified:
```

`pass` требует наблюдений двух свежих запусков и негативного сценария.
Самооценка автора кандидата без этих наблюдений даёт только `unknown`.
