## Находки

### Н1 — закрытие задачи не доносит evidence до эпика; 1plan-task об этом обязательстве не знает

**Слово владельца:** `ba9f96c3:23` — «правило писать evidence в эпик тем же ходом при закрытии задачи **остаётся**» (сохранено ровно при исключении поля из хеша снимка).

**Адрес.** `packages/1plan-task/SKILL.md:54` (C4) обязывает только к производным: «Производные счётчики задачи и эпика синхронизированы»; `1plan-task/references/task-schema.md:89` — то же, «тем же ходом обновляют **производные** поля карты». Содержательное обязательство существует единственный раз и в чужом пакете: `1plan-map/references/epic-schema.md:110` — «затем состояние эпика содержательно обновляет ответственный агент». Закрывающий агент работает по `1plan-task` и epic-schema не открывает. Baseline связывал это прямо в том файле, который агент читает: `1plan-task/versions/baseline-2026-09-08/references/task-schema.md:86`.

**Прогноз траектории.** Дефолт: закрыть работу, когда прибор зелёный → первое изменённое решение: агент ставит `✅ готово` + evidence задачи, гоняет `--sync`, получает exit 0 → останавливается. «Проверено:» в эпике (`assets/epic-template.md:51`) остаётся прежним, а `задач-готово/задач` в Дашборде растёт. Это ровно тот вред, который пакет называет сам (`1plan-map/SKILL.md:23`: «число закрытых задач скрывает неизвестный остаток»); расхождение всплывёт только на следующем аудите 1plan-map, если он вообще случится.

**Минимальная правка** (в существующий критерий, без новой инструкции) — `1plan-task/SKILL.md:54`:
> «Производные счётчики задачи и эпика синхронизированы, **а закрытие тем же ходом вносит evidence задачи в «Состояние» эпика; выросший счётчик следом закрытия не является.**»

### Н2 — у 1planning нет описанного выхода, когда допуск дать нельзя: вопрос владельцу живёт только в чате

**Слово владельца:** `01a07f80:21` (владелец смотрит два Bases по метаданным эпиков и задач); `01a066d9:19` — «Задавай мне вопросы. Если почувствуешь что-то странное».

**Адрес.** Единственный выход скила — передать допуск (`1planning/SKILL.md:11-12`). Критерий `:52` требует «Вопрос до ответа остаётся вопросом», `:46` — «возвращают владельцу материальный выбор», но носителя не называет. Встречный конец маршрута замкнут: `1plan-map/SKILL.md:40` отправляет нерешённый выбор обратно «в `1planning`». Файл вопроса упомянут только в `1plan-map/SKILL.md:57-59` и `1plan-task/SKILL.md:59`; `1planning` не называет `question-schema.md` ни разу.

**Прогноз траектории.** 1planning видит конфликт предложенной работы с каноном → пишет владельцу в чат → окно кончается → в `_ops/plans/вопросы/` пусто, вид «Открытые вопросы» Дашборда пуст → работа либо стоит без видимой причины, либо следующий агент решает продуктовый вопрос сам. Это логика самого пакета (`1plan-map/SKILL.md:25`: «проблема, видимая только внутри задачи, для него легко теряется»), не применённая на уровень выше, где цена ошибки больше.

**Достраивать нечего — маршрут уже исполним, он просто не назван** (проверено на коде, не предсказано): `epic-schema.md:42` разрешает `допуск: ""` у ещё не допущенного предложения, и checker непустого допуска эпика не требует (`check_plans.py:459-462`); `касается` вопроса принимает эпик (`check_plans.py:827`).

**Минимальная правка** — `1planning/SKILL.md:49-53`, дописать в критерий «Продуктовый ответ получает владельца»:
> «**Выбор, который агент не вправе сделать сам, до ответа владельца получает один файл по `1plan-map/references/question-schema.md`, привязанный к эпику или к предложению эпика с пустым допуском; сказанное только в чате вопросом владельцу не считается.**»

### Н3 — `допуск` принимает неразрешимую строку, и критерий «Допуск восстановим» выполняется на вид

**Адрес.** `1plan-map/references/epic-schema.md:42` — «адрес решения владельца», форма не задана; `1plan-task/references/task-schema.md:17` — то же; критерий `1planning/SKILL.md:40-43`.

**Наблюдение.** Прибор требует только непустую строку (`check_plans.py:459-462`, `:796`) — это признано в `decisions.md:22`. Фикстура кейса заполнила поле именно свободным текстом — «решение владельца 2026-09-08» (`probes/case.md:6`), и исполнитель воспроизвёл эту строку как основание в «Зачем» (`probes/plain.md`, блок про допуск эпика). **Прогноз** (не наблюдение): на живом эпике агент напишет ту же неоткрываемую строку.

**Прогноз траектории.** Следующий агент не может открыть допуск → либо принимает его на веру (предложение агента становится разрешением), либо переспрашивает владельца. Первый исход критерий `1planning:43` называет вредом дословно; второй прямо ломает автономность из `01a07f80:22`. Соседний глобальный скил `1chat-recall` уже даёт решениям владельца адрес `файл:строка` — тот самый, которым пользуется этот review; ни один из трёх пакетов его не называет. В baseline тоже не назывался — это не регресс, а незакрытая дыра, ставшая заметной ровно потому, что автономность теперь опирается на поле `допуск`.

**Минимальная правка** (одна ячейка схемы, не инструкция) — `epic-schema.md:42`:
> «`допуск` | адрес решения владельца, **открываемый другим агентом: файл и строка записи решения (например, запись `1chat-recall`)**; `""` только у ещё не допущенного предложения»

Тем же словом — `task-schema.md:17`.
