# Форма планов

Вход: создаёшь или меняешь файл в `_ops/plans/`, заводишь карту в новом
проекте или проверяешь её. Смысл работы задаёт тело скила; здесь — адреса,
поля, разделы и механическая проверка, на которые опираются Bases владельца.

## Адреса

| Файл | Адрес от корня проекта |
| --- | --- |
| Обзор эпиков и вопросов | `_ops/plans/Дашборд.base` |
| Обзор задач | `_ops/plans/Планы.base` |
| Эпик | `_ops/plans/эпики/<Эпик>/epic - <Эпик>.md` |
| Задача | `_ops/plans/эпики/<Эпик>/task - <Задача>.md` |
| Вопрос | `_ops/plans/вопросы/<Вопрос>.md` |

Новая карта получает оба Bases из [assets/map](../assets/map/) без правок.
Файлы заполняются из шаблонов: [эпик](../assets/epic-template.md),
[задача](../assets/task-template.md), [вопрос](../assets/question-template.md).
Закрытые файлы остаются на своих местах.

## Шапка

Значения — YAML: пустое `""`, список `[]`, дата `YYYY-MM-DD`, wikilink в
кавычках от корня проекта без `.md`: `"[[_ops/plans/эпики/Имя/epic - Имя]]"`.
Производные поля пишет только `--sync`.

| Поле эпика | Смысл |
| --- | --- |
| `тип` | `эпик` |
| `описание` | ожидаемый исход одной строкой — его видит Дашборд |
| `область` | область результата |
| `статус` | словарь ниже |
| `порядок` | положительное целое; у эпиков главного пути уникально |
| `запуск` | `true` — главный путь, `false` — остальные эпики |
| `health` | `🟢`, `🟠`, `🔴` или `не проверено` — по раннему сигналу |
| `ранний-индикатор` | сигнал, по которому отклонение видно до провала |
| `зависит-от` | ссылки на эпики, которые завершаются раньше; `[]`, если таких нет |
| `допуск` | адрес решения владельца: `путь.md:строка`, якорь цитаты или permalink; `""` у ещё не допущенного |
| `задач`, `задачи`, `задач-готово` | производные: число задач, их ссылки по порядку, число закрытых |
| `evidence` | адрес доказательства исхода при закрытии; до этого `""` |
| `обновлено` | дата последней содержательной правки |

| Поле задачи | Смысл |
| --- | --- |
| `тип` | `задача` |
| `эпик` | ссылка на эпик той же папки |
| `допуск` | `эпик`, если работа стоит в «Порядке» допущенного эпика; иначе адрес решения |
| `режим` | `execution` — путь известен; `wayfinding` — итог работы — проверенное знание для выбора пути |
| `статус` | словарь ниже |
| `порядок` | положительное целое, уникальное внутри эпика |
| `подзадач`, `подзадач-готово` | производные: чекбоксы «Готово, когда» и отмеченные из них |
| `evidence` | адрес свидетельства целого — коммит, отчёт проверки; до закрытия `""` |
| `обновлено` | дата последней содержательной правки |
| `вопрос` | необязательное: ссылка на файл вопроса либо `""` |

| Поле вопроса | Смысл |
| --- | --- |
| `тип` | `вопрос` |
| `статус` | `открыт` или `отвечен` |
| `касается` | ссылка на эпик или задачу |
| `адресат` | кто решает |
| `срок` | дата либо `""` |
| `ответ-опора` | адрес ответа владельца; `""` до ответа |
| `обновлено` | дата |

Статусы эпика и задачи: `◽ в очереди`, `🔨 в работе`, `🔒 заблокировано`,
`🛑 затык`, `⏳ отложено`, `✅ готово`. Отложение — решение владельца: его
адрес и условие возврата стоят строкой в «Цели».

## Разделы

H2 идут точно в этом порядке и не пусты; подробности — H3 или списки.

| Файл | Разделы |
| --- | --- |
| Эпик | «Цель», «Не входит», «Порядок», «Готово, когда» |
| Задача | «Цель», «Прочитать», «Не входит», «Готово, когда» |
| Вопрос | «Вопрос», «Влияние», «Варианты», «Ответ» — пуст до ответа |

«Цель» эпика ссылается хотя бы на одно основание — решение владельца или
принцип, определившие цель, границу или порядок. «Порядок» ссылается на
каждый файл задачи в папке эпика. В задаче чекбоксы стоят только в «Готово,
когда», отчётов под ними нет; в «Прочитать» есть хотя бы одна ссылка.
У вопроса «Влияние» отделяет зависимую работу от той, что продолжается;
«Варианты» — альтернативы с последствиями и рекомендацией; «Ответ» —
принятое решение с адресом источника.

Ссылка на документ — относительный путь в угловых скобках, до раздела:
`[Документ — раздел](<../../../../docs/Папка/Документ.md#Раздел>)`.
Подходит и wikilink с путём от корня проекта: `[[docs/Папка/Документ#Раздел]]`;
голое имя файла в проекте с архивами бывает неоднозначным.

## Прежняя форма

Задача: «Задача», «Зачем», «Цель», «Критерии приёмки», «Основания»,
«Подзадачи», «Состояние»; поля `эпик-снимок` и `траектория`; от трёх до семи
подзадач, под каждой свёрнутый `> [!note]- Отчёт` со строкой
`статус YYYY-MM-DD: …` и `доказательство:`, обязательным у отмеченной.
Эпик: «Зачем», «Цель», «Основания», «Границы», «Критерии завершения»,
«Аппетит», «Состояние»; поле `основания`. Проверка принимает эту форму до
закрытия файла; формы в одном файле не смешиваются.

## Проверка

Из корня проекта, где `<1planning>` — папка установленного скила:

```sh
uv run --script <1planning>/scripts/check_plans.py --root .
uv run --script <1planning>/scripts/check_plans.py --root . --sync
uv run --script <1planning>/scripts/check_plans.py --root . --snapshot '_ops/plans/эпики/Имя/epic - Имя.md'
```

По умолчанию только чтение; с установленным PyYAML подходит и `python3`.
Exit 0 — механика прошла, 1 — ошибка данных, 2 — ошибка вызова. `--sync`
пишет только производные поля и не пишет ничего, пока есть другие ошибки.
`--snapshot` нужен лишь прежней форме: печатает снимок эпика для поля
`эпик-снимок` после сверки задачи с изменившимся эпиком.

Проверка ловит адреса, поля, разделы, статусы, ссылки шапки и тела роутера,
размер роутера, счётчики и формальное закрытие. Полноту роутера, истинность
evidence и отрисовку Bases она не доказывает.
