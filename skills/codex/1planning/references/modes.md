# Два режима задачи

«Искать путь — тоже задача, которую надо исполнять»: нельзя планировать глубоко,
пока не выполнены части, дающие свидетельства. Режим — свойство задачи, не
скила; один контракт переходит между режимами без нового файла и не держит
обе формы одновременно.

## Wayfinding — путь материально не ясен

Задача разрешает решения, а не изображает преждевременный план исполнения.

Держи одну живую карту решающих вопросов:

- **готовые** — точный вопрос, ответ на который меняет маршрут: назови живые
  варианты ответа, расхождение маршрутов ниже и различающее свидетельство;
- **заблокированные** — точный вопрос + названный пререквизит;
- **туман** — in-scope область, которую пока нельзя честно выразить вопросом;
  из тумана не делают вех;
- **решено** — компактный вывод + указатель на свидетельство, не копия.

`Next` — один готовый вопрос: выбирай по раннему дорогому расхождению и снятию
блокеров, не по лёгкости. Неизвестный факт → ограниченное исследование;
наблюдаемая форма → прототип; разовый tradeoff → решение владельца.
Повторяющийся класс владельческих вопросов — дыра в принципах
(`1product-shaping`), не поток эскалаций.

## Переход в Execution

Только после пробы первого действия:

> Первый шаг исполнения не заставляет исполнителя изобрести продуктовое,
> архитектурное или полномочное решение?

Заставляет — неснятый вопрос вернулся в карту, задача осталась в Wayfinding.
Пустая карта решений «выглядит готовой» — проба ловит именно это.

## Execution — путь ясен

2–5 наблюдаемых вех одного независимо закрываемого Outcome — от оси разреза
([decompose](decompose.md)), не от хронологии. `Next` называет ближайшее
наблюдаемое состояние. Обратимую процедуру оставь исполнителю: полнота
контракта — это покрытие результата, границ, решений и proof, не пересказ
каждого будущего движения.

При равном результате выбирай минимальный обратимый commitment, сохраняющий
живые ветки до свидетельства.

## Цикл корректировки — по событию

После material-свидетельства, перед новым material-шагом, при возврате в
задачу:

1. перечитай текущий файл эпика, `status.md` и папку вопросов; сразу сверь
   `эпик-снимок` в `task.md`. Протухший `эпик-снимок` → перечитай `task.md` и
   `context.md`, пересверь задачу с текущим эпиком и обнови контракт тем же
   ходом. `task.md` и `context.md` читай по триггерам [contract](contract.md)
   (раздел context.md), независимо от свежести `эпик-снимок`. Это
   копия гейта [contract](contract.md) в цикле; не продолжай по памяти чата;
2. классифицируй свидетельство: подтверждает · противоречит · недостаточно ·
   конфликтует;
3. следствие: продолжить · принятое допущение · блокер · пересборка · handoff;
4. при противоречии — **пересобери** затронутую часть из текущих фактов;
   заплатка поверх устаревших вех оставляет зомби-план, который выглядит
   живым и ведёт работу;
5. перепиши текущую правду `status.md` без хроники; новое материальное
   неизвестное → задача возвращается в Wayfinding.

## Контрастные случаи

**Преждевременное исполнение.** Destination принят, но первый шаг требует
выбрать модель владения данными. Пустая карта выглядит готовой; проба первого
действия возвращает выбор в Wayfinding.

**Театр планирования.** До первого прототипа расписаны 40 файловых действий по
трём непроверенным маршрутам. Оставь Outcome, границы, конкурирующие посылки и
один различающий прототип — остальное появится из его свидетельств.

**Лёгкий фронтир.** UI-текст закрывается быстро, а владелец хранилища меняет
API и миграции. Дешёвый вопрос выигрывает только при равном downstream-весе.
