# Форма карты и эпика

Вход: создание или изменение эпика, полей карты, Bases; аудит или закрытие.
Выход: понятный эпик и согласованные файлы, прошедшие механическую проверку.
Смысл и допустимость работы определяет тело скила, а не эта схема.

## Размещение

Общий стандарт — `_ops/plans/` от корня проекта:

| Артефакт | Адрес |
| --- | --- |
| Обзор эпиков и вопросов | `Дашборд.base` |
| Обзор задач | `Планы.base` |
| Эпик | `эпики/<Имя>/epic - <Имя>.md` |
| Задача | `эпики/<Имя>/task - <Имя задачи>.md` |
| Вопрос | `вопросы/<Имя вопроса>.md` |
| Объёмные доказательства | `_evidence/` внутри папки эпика |

Новый эпик заполняется из [шаблона](../assets/epic-template.md). Два файла
Bases поставляются в [assets/map](../assets/map/). Закрытые файлы остаются
на своих местах. Существующую структуру проекта эта схема сама не мигрирует:
миграция — отдельная согласованная работа с обновлением ссылок.

## Поля эпика

Все поля таблицы обязательны. Пустое значение пишется `""`, список — `[]`;
даты ISO `YYYY-MM-DD`, wikilinks — YAML-строки в кавычках.

| Ключ | Тип и смысл |
| --- | --- |
| `тип` | строка `эпик` |
| `описание` | непустая строка, краткий ожидаемый исход для Bases |
| `область` | непустая строка, область результата |
| `статус` | общий словарь ниже |
| `порядок` | положительное целое; у эпиков главного пути уникально |
| `запуск` | boolean; `true` — главный путь, `false` — остальные эпики |
| `health` | `🟢`, `🟠`, `🔴` либо `не проверено`; оценка по раннему сигналу |
| `ранний-индикатор` | непустая строка: сигнал, позволяющий заметить отклонение до провала |
| `канон` | список существующих файлов канона, пути от корня проекта; `[]`, если канона нет |
| `зависит-от` | список ссылок на необходимые завершённые эпики; `[]`, если зависимостей нет |
| `допуск` | открываемая другим агентом запись решения: `путь.md:строка` (например, из `1chat-recall`) или permalink на ответ; `""` только у ещё не допущенного предложения |
| `задач` | целое ≥ 0, вычисляемое число задач в папке |
| `задачи` | вычисляемый список полных wikilinks, в порядке задач |
| `задач-готово` | целое ≥ 0, вычисляемое число завершённых задач |
| `evidence` | адреса доказанного прогресса; при закрытии — доказательство исхода целого; `""`, пока доказательств нет |
| `обновлено` | дата последней содержательной проверки состояния |

Полная ссылка: `"[[_ops/plans/эпики/Имя/epic - Имя]]"`. Короткое имя
допустимо, только если однозначно среди Markdown-файлов проекта. Необходимые
зависимости не образуют циклов. Активная задача требует активного допущенного
эпика и завершения его необходимых зависимостей.

## Разделы эпика

Порядок H2 фиксирован; внутренние подробности используют H3 или списки.

| Раздел | Что должен понять читатель |
| --- | --- |
| `Зачем` | Какая проблема или возможность оправдывает эпик и как он служит GOAL |
| `Цель` | Какой наблюдаемый исход должен наступить |
| `Канон` | Адреса применимых правил и их влияние; продуктовая правда остаётся по адресам |
| `Границы` | Что включено, что исключено, пример правдоподобной запрещённой задачи |
| `Критерии завершения` | Какие свидетельства докажут исход и что мешает принять его |
| `Аппетит` | Допустимое вложение и наблюдаемое условие остановки или возврата к выбору |
| `Состояние` | Проверенное достигнутое, остаток по критериям, следующая выводимая задача, блокер или вопрос |

В «Состоянии» сначала короткая актуальная картина; история подчинена ей.
Алгоритм исполнения и самостоятельные подзадачи живут в task-файле. Счёт
закрытых задач означает только «закрыто из созданных», не процент эпика.

## Статусы и завершение

| Статус | Значение |
| --- | --- |
| `◽ в очереди` | работа ещё не началась |
| `🔨 в работе` | работа исполняется |
| `🔒 заблокировано` | продолжение зависит от названного внешнего условия |
| `🛑 затык` | выбранный путь не даёт результата; нужен разбор |
| `⏳ отложено` | решение владельца отложить; причина и условие возврата в «Состоянии» |
| `✅ готово` | критерии целого выполнены и подтверждены evidence |

Словарём владеет эта схема; задача использует его без новых значений.
Отложение старше выводимой блокировки. Проверка не меняет статусы, даты,
health или evidence. Зелёный health не означает завершение.

Закрывая задачу, агент тем же ходом добавляет в `evidence` эпика адрес её
доказанного вклада и обновляет «Состояние». Это промежуточное evidence не
закрывает эпик: для закрытия требуется доказательство исхода целого по его
критериям. Закрытый эпик не содержит незавершённых задач: реальный перенос
в другой эпик требует сохранённых адресов и нового содержательного допуска,
а не удаления неудобной задачи ради проверки.

## Встроенная проверка

Из корня проекта, где `<1plan-map>` — папка установленного скила:

```sh
uv run --script <1plan-map>/scripts/check_plans.py --root .
uv run --script <1plan-map>/scripts/check_plans.py --root . --sync
uv run --script <1plan-map>/scripts/check_plans.py --root . --snapshot '_ops/plans/эпики/Имя/epic - Имя.md'
```

По умолчанию только чтение. Скрипт использует PyYAML; с уже установленным
PyYAML возможен `python3 <1plan-map>/scripts/check_plans.py ...`.
Exit 0 — механические свойства прошли, 1 — ошибка данных, 2 — ошибка вызова.

`--sync` вычисляет только `задач`, `задачи`, `задач-готово` эпика и
`подзадач`, `подзадач-готово` задач. Перед записью проверяет остальные условия;
при их ошибке не пишет ничего. Другие поля и тело сохраняет. После создания
или закрытия задачи синхронизация выполняется тем же ходом, затем состояние
эпика содержательно обновляет ответственный агент.

Снимок включает преамбулу и намерение эпика, непроизводные поля, GOAL и
содержимое файлов из `канон`. Исключены раздел «Состояние» и поля `статус`,
`health`, `обновлено`, `задач`, `задачи`, `задач-готово`, `evidence`.
Снимок сравнивается у незакрытых задач; история закрытой задачи сохраняется.
Изменение канона или цели требует сверки живых задач до обновления снимков.
Скрипт никогда не обновляет снимок задачи автоматически.

Проверяются пути, поля, порядок разделов, ссылки, зависимости, отчёты,
счётчики и условия формального закрытия. Скрипт не доказывает прочтение
канона, подлинность допуска, качество декомпозиции, истинность evidence или
отрисовку Bases в Obsidian. Нулевой exit не является содержательной приёмкой.
