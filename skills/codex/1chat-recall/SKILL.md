# Chat recall

## Контекст

Слова владельца — датированное evidence, а не вечный профиль. Отдельный hit
может быть точным и уже отменённым; свежий разговор — лишь частично связанным,
но содержать актуальную коррекцию. Поэтому продукт retrieval — применимая
позиция для текущего claim, а не список похожих цитат.

Один holder хранит один разговор. Default-поиск семантически выбирает до десяти
holder-ов по `session-context` и цитатам, затем показывает выбранное множество
от свежего к старому. `semantic_rank` отвечает за связь с запросом,
newest-first — за место возможной поздней позиции. Полный `session-context`,
strongest quote и counts помогают выбрать чтение, но owner evidence появляются
только после полного holder-а и проверки более поздних слов.

Агент гарантированно читает тело, но может не открыть reference. Поэтому
обычные Capture и Retrieval полностью исполнимы отсюда. References — только
для наблюдаемого исключения: плохого coverage или ремонта повреждённой записи.

## Цель

Полезные слова владельца сохраняются в ходе высказывания, а перед существенным
решением прежняя позиция восстанавливается со сценой, scope, хронологией,
вытеснением и честными gaps. Если применимость не разрешена, результат —
`abstain`, а не уверенная догадка.

## Evidence

Записывай самостоятельный тезис, который вне соседних сообщений меняет будущее
решение, границу, критерий, предпочтение или понимание владельца. Служебное
согласие хода знания не несёт; в сомнении полезный тезис лучше сохранить.

- `quote` — буквальная речь владельца. Сокращение допустимо только
  вычёркиванием по источнику; удаление — только по его слову.
- `selection` — выбранный владельцем агентский вариант. Выбор не доказывает
  одобрение текста рядом.
- `context-note` — только внешняя сцена или референт одной записи, которых нет
  в самой цитате. Не пересказывай тезис и не расширяй его scope.
- `session-context` — однострочная поисковая карточка всего разговора: задачи,
  артефакты, операции, устойчивые имена и полезные синонимы через `;`. Это не
  позиция владельца и не summary решений.

Обычные понятия карточки пиши на языке проекта; устойчивое чужое имя оставляй
рядом как синоним (`мокап/mockup`), точные имена (`Next.js`, `BDR-002`) не
переводи. Scope по умолчанию — текущий проект; cross-project позиция требует
явных слов владельца. Живое слово владельца сильнее любой записи, а
расхождение остаётся видимым.

## Capture

Перед записью прочитай holder текущей сессии. Тот же тезис второй раз не пиши;
каждый новый тезис сохраняй отдельно. Для `quote` и `selection` передай полную
актуальную `session-context`: сохрани прежние крупные предметы и добавь новый.
В `context-note` назови одно внешнее обстоятельство, которое исчезнет без
соседних сообщений.

```bash
ROOT="${CODEX_HOME:-$HOME/.codex}/skills/1chat-recall"
SESSION="$CODEX_THREAD_ID"

python3 "$ROOT/scripts/chat_capture.py" \
  --quote "<слова владельца>" \
  --context-note "<сцена, не пересказ>" \
  --session-context "<задачи; артефакты; операции; имена и синонимы>" \
  --source-timestamp "$(date -Iseconds)" \
  --type <речевой-акт> --topic <долгоживущий владелец темы> \
  --agent codex --project "$PWD" --session "$SESSION" --json
```

Текущее время верно только для same-turn capture. Для прежней реплики бери
timestamp из native transcript; дату из воздуха не восстанавливай.
`--list-metadata` из корня проекта печатает канонические type и существующие
темы. Словарь тем — файлы слоя `_ops/chat-recall/topics/`, когда проект его
держит, иначе темы корпуса. Тему выбирай из существующих; если предмет не
принадлежит ни одной — и только тогда — создай новую:
`--new-topic "<граница темы одним предложением>"` заводит вместе с записью
маленький файл темы. Имя — долгоживущий владелец предмета латиницей через
дефис; сперва убедись, что близкой темы нет. Выбранный вариант пиши с
`--kind selection`. Повторный capture с актуальной карточкой обновляет
`session-context` даже при уже существующей цитате.

Закрой ветку адресом записи и назови, что сохранено. Если записи нет, назови
причину: служебное согласие либо уже сохранённый тезис.

### Reconcile загруженной темы

Если проект держит `_ops/chat-recall/topics/` и файл выбранной темы уже
прочитан в текущем окне ради этой же работы, после успешной записи в `raw`
сравни новую позицию с загруженной темой. Это использует локальность текущего
контекста, но не превращает каждую цитату в обновление второго слоя.

По умолчанию тему не меняй. Материальное расхождение есть только когда свежие
слова добавляют долговечную позицию, меняют её границу либо исправляют или
отменяют утверждение, которое тема сейчас показывает как действующее. Повтор,
уточнение сцены, разовая команда, согласие реализации и стилистическое
улучшение расхождением не являются. Неясны commitment, scope или связь с
предметом — оставь только `raw`; непрочитанную тему специально ради записи не
пересказывай.

Если запись явно не имеет эффекта на тему либо сравнение с уже загруженной
темой дало no-op, зафиксируй это fingerprint-квитанцией. Она не меняет topic и
не двигает horizon, но не даёт позднему batch принять осознанный no-op за
неразобранную запись:

```bash
python3 "$ROOT/scripts/topic_reconcile.py" acknowledge-noop \
  --project "$PWD" --topic "<receipt.topic>" \
  --session "<receipt.session>" \
  --record-sha256 "<receipt.record_sha256>" \
  --source-anchor "<receipt.anchor>"
```

Если topic не загружен и материальность неясна, квитанцию не ставь: raw
остаётся честным backlog. Для очевидного повтора, разовой команды или
session-only style квитанция допустима без открытия topic-файла.

При расхождении этот же агент формулирует адресный patch к уже прочитанной
теме: добавляет claim в точный существующий раздел, точно заменяет один claim,
переносит отменённый claim в точный раздел либо меняет только вводную границу
темы. Каждый изменённый claim или boundary получает якорь новой raw-записи;
одна запись может обосновывать несколько операций. Пункт — производный обзор,
цитата по якорю остаётся evidence. Не дописывай механически новую цитату и не
переписывай общий файл напрямую.

Capture запускай с `--json`: receipt даёт `topic`, `session`, `anchor` и
`record_sha256`. Затем подготовь typed patch и возьми
`expected_sha256` из ответа `prepare`:

```bash
PATCH="$(mktemp -t chat-recall-topic.XXXXXX.json)"
python3 "$ROOT/scripts/topic_reconcile.py" prepare \
  --project "$PWD" --topic "<receipt.topic>" --patch "$PATCH"
```

`prepare` оставляет в `operation_schema` точные поля всех четырёх операций.
В `operations` перенеси только нужные объекты, например exact replacement:

```json
{
  "version": 1,
  "topic": "<receipt.topic>",
  "operations": [
    {
      "kind": "replace",
      "before": "- <точный существующий claim>",
      "after": "- <новая формулировка> [<receipt.anchor>]"
    }
  ]
}
```

```bash
# Заполни operations в $PATCH; каждый claim/after цитирует [<receipt.anchor>].
# insert: exact `## section` + новый `- claim`
# replace: exact `- before` + новый `- after`
# move: exact `- before` + target `## section` + новый `- after`
# replace-boundary: exact вводный абзац before + новый after

python3 "$ROOT/scripts/topic_reconcile.py" apply \
  --project "$PWD" --topic "<receipt.topic>" --patch "$PATCH" \
  --expected-sha256 "<prepare.expected_sha256>" \
  --session "<receipt.session>" \
  --record-sha256 "<receipt.record_sha256>" \
  --source-anchor "<receipt.anchor>"
```

Helper под блокировкой сверяет исходный hash, принадлежность записи теме,
адресует только заявленные claims/границу, находит raw-запись снова после
сдвига строк, пересчитывает `sources` и сам собирает новый файл. Произвольного
whole-file содержимого patch не принимает. Конфликт означает «не записано»:
перечитай новую версию, снова подготовь patch и разреши обе дельты; не
перетирай её. Если честное слияние сейчас невозможно, закрой capture как
`raw saved; topic pending`.
Локальная правка не двигает общий `horizon`: batch-проход позже отвечает за
остальной backlog.

## Retrieval

Подключай субагентов, только если ответ может изменить существенное решение,
границу или долговечный артефакт и сам запрос указывает, что применимую
позицию владельца могли обсуждать раньше. Простой запрос, рабочий момент или
уточнение отработай локально по умолчанию: сами по себе они не требуют
отдельных агентов.

Когда этот порог сработал, спроси корпус сам и одновременно отправь несколько
дешёвых субагентов по разным направлениям искать дополнительные holder-файлы.
Повтори при смене предмета, только если новый предмет тоже проходит порог. Пока
разведка идёт, продолжай независимую работу, но перед зависимым решением собери
результат каждого: путь и одно предложение о связи файла с текущим claim-ом,
явное «ничего не найдено» либо blocker — без цитат, snippets и пересказа
позиции владельца.

Ищи предмет claim-а, а не только имя артефакта: короткая естественная
формулировка должна описывать, о чём решение.

```bash
uv run --locked --script \
  "${CODEX_HOME:-$HOME/.codex}/skills/1chat-recall/scripts/chat_digest.py" \
  _ops/chat-recall \
  --query "<короткая естественная формулировка предмета>" \
  --json
```

Corpus остаётся локальным: цитаты не отправляй в network tools.

Default возвращает единый `holders`. Не пересчитывай его ranking по длине
файла, общему числу цитат или counts type/topic: эти поля описывают содержание,
но сами relevance не создают. Legacy-holder без `session-context` остаётся
видимым и может быть найден по цитатам.

`query_domain` — сырая близость ближайшей записи, снятая до слияния каналов;
RRF-ранг такого смысла не несёт, и десятка выдаётся всегда. `off-domain`:
в корпусе нет ничего даже по теме — закончи ветку `abstain`, не пересказывая
выдачу. `in-domain` говорит только, что запрос про предмет проекта, и ничего
о наличии искомой позиции: замерено, что вопрос о правиле, которого в корпусе
нет, получает тот же вердикт, что и вопрос о записанном.

Позицию владельца доказывает только его текст, который главный агент
прочитал в holder-е от первой строки до последней.

Top-10 — карта, не очередь и не десять обязательных чтений. Обычная глубина —
три-четыре полных holder-а: сохрани сильнейший релевантный контекст и самые
свежие из связанных сессий. Свежесть без связи с claim — шум; связанных
holder-ов меньше — не добирай число. Три-четыре — калибровка, не квота:
глубину меняют расхождения и цена ошибки.

Тема может содержать несколько claim-ов с разной лексикой. Coverage должен
охватить материальные фасеты, найденные в карточках и snippets, включая хотя
бы один запрос языком текущей задачи. Если обычная выдача пустая, чрезмерно
широкая, конфликтующая, усечённая или hybrid-route недоступен — прочитай
[reading-the-log](references/reading-the-log.md), чтобы получить bounded
recovery routes и честный coverage packet.

Сначала разреши хронологию внутри holder-а: поздняя реплика может
отменять раннюю, а смена type часто обозначает разворот. Затем сформулируй тот
же claim лексикой owner-записей и повтори ту же команду с
`--since <YYYY-MM-DD даты применяемого evidence>`. Прочитай каждый найденный
более новый holder; исходная выдача later-check не заменяет.

Итог ограничивай наблюдаемым coverage: более поздняя позиция найдена либо не
найдена в названных routes. `truncated=true` — отдельный gap; любой gap,
способный изменить решение, заканчивается `abstain`. Сверь применяемую позицию
с `AGENTS.md`, `GOAL.md` и другим живым project-local owner-ом; при расхождении
предъяви оба адреса, не выбирай молча. Соседняя задача может объяснять claim,
но не задаёт статус текущей.

Закрой ветку применимой позицией, scope, датой, адресами прочитанных полностью
holder-ов, результатом later-check и оставшимися gaps.

## Repair

Повреждённая запись или явный запрос владельца восстановить докаптурную историю
→ прочитай [repairing-the-log](references/repairing-the-log.md), чтобы получить
native provenance, честную хронологию и integrity proof. Обычный historical
retrieval этим маршрутом не является.

## Завершение

Ход завершён, когда каждая активная ветка оставила проверяемый след:

- Capture — адрес и сохранённый тезис либо причина отсутствия записи; при
  no-op — адрес fingerprint-квитанции; при материальном расхождении — адрес
  применённой правки или `topic pending`;
- Retrieval — применимая позиция или `abstain`, full-holder addresses,
  later-check, scope и coverage gaps;
- Repair — восстановленный сигнал и proof provenance/chronology/structure либо
  точный blocker.

Список цитат, верхний hit, неполный holder, цитата без сцены и непомеченный
агентский вывод результатом не являются.
