## Часть 2. Findings

Порядок — по величине вреда. Каждая находка: механизм → точное evidence →
repair. Правки не вносились.

### F1 — «Граф зон — `depends-on`» описывает граф, которого нет — **самая вредная**

**Failure mode:** literal scope + утверждение о состоянии, которое ложно.

**Evidence:** `AGENTS.md`, раздел «Локальная Правда»: «Граф зон — `depends-on` в
шапках subtree `AGENTS.md` (читает `1md-graph`)». Реально `depends-on` живёт в
**одном** subtree-файле из восьми. `_workspace/HTML_artifacts/AGENTS.md`
использует другой ключ (`read-before-edit`), шесть файлов вообще без шапки.

**Steering cell.** Fork: агенту нужно узнать, от чего зависит зона, до правки.
Естественный акт **с этим правилом**: открывает шапку subtree `AGENTS.md`, не
находит `depends-on` (7/8) и заключает «зависимостей нет». Вред: правило не
просто молчит — оно **производит ложноотрицательный вывод**, что хуже отсутствия
правила. Целевой акт: читать тело зоны и её `README.md`, а `depends-on` считать
сигналом только там, где он объявлен.

**Нюанс в защиту фразы.** В пробе `P3` агент собрался писать `depends-on` в новый
файл — то есть как **авторская норма** конвенция работает. Но `P3` сослался на
«местную конвенцию» субтри, не на корень, поэтому атрибуция к `AGENTS.md`
недоказана.

**Repair (одно предложение, не применялось):** разделить описание и норму —
`«Зависимость зоны объявляет её собственный AGENTS.md/README; frontmatter
depends-on есть не везде, его отсутствие не значит отсутствие зависимостей.
Новую шапку заводи с depends-on.»` Альтернатива в change-mode: проставить
`depends-on` в семь файлов и оставить фразу как есть. Выбор между «поправить
текст» и «поправить мир» — материальная развилка, оставляю владельцу.

### F2 — owner ↔ install: правило верное, но без датчика дрейфа и уже нарушено

**Failure mode:** job `Prove / enforce` провален; hard invariant держится прозой.

**Evidence:** правило — «Если package имеет tracked owner в `skills/**` …, сначала
правь его, а global install считай projection». Живой замер `diff -rq`:

- `1cli-tools`: расходятся `SKILL.md` + два `references/`; owner `Jul 30`,
  install `Aug 2` — **правили install**;
- `1local-rules`: расходится `SKILL.md`; owner `Jul 22`, install `Jul 28`;
- 4 пакета — симлинки (`1chat-recall`, `1distill`, `1html`, `1tailwind-dev`), для
  них дрейф структурно невозможен.

**Независимое подтверждение пробой `P2`:** агент правило **применил** (назвал
`AGENTS.md`, выбрал repo-owner, проверил симлинк против копии) и нашёл тот же
дрейф самостоятельно. Дальше он показал вред, который я не предсказал: в
установленных копиях `1cli-tools` лежат ~1.7 КБ полевого знания
(`brew upgrade --dry-run`, `uv tool install --reinstall`, точечный
`npm install -g --allow-scripts`, `trash --stopOnError`), которых нет в git.
**Наивное исполнение правила** — «правлю owner, копирую поверх install» —
уничтожит их в обеих копиях сразу.

**Steering cell.** Fork: агент собирается менять глобальный скил. Естественный
акт без датчика: доверяет правилу, что owner канонический, правит его, проецирует
поверх — тихая потеря. Целевой акт: перед правкой сравнить owner и install и
объявить направление дрейфа; после правки — либо спроецировать, либо явно сказать,
что проекция не обновлена.

**Repair:** правило нужно дополнить одной операцией и одним fallback-ом:
`«Перед правкой package сверь owner и install (diff -rq). Install новее — сначала
верни его содержимое в owner, потом правь. После правки owner проекция обновляется
или отсутствие обновления называется вслух.»`
**Enforcement уже существует и не подключён:**
`skills/shared/sync_simple_projections.py` живёт в репо, а корневая инструкция о
нём не знает. Это самый дешёвый доступный детерминированный слой (хуки владелец
отвергает). Наблюдение `P2`, которое разделяю: перевод копий на симлинки убирает
класс проблемы целиком.

### F3 — приоритет 2 (`wisdom-*` + guide) не сработал ни разу

**Failure mode:** требование узнать без операции узнавания + нет evidence gate.

**Evidence:** «Перед правкой skill / agent / instruction начинай с ближайшего
`knowledge/wisdom-*` и одного guide; для skills сперва
`knowledge/practical-guides/how-to-write-skills/`».

Замер по двум применимым пробам:

| | `knowledge/wisdom-*` | `how-to-write-skills/` |
|---|---|---|
| `P1` (правка описания скила) | **не читал** (0 из 8 файлов) | читал, но **позиция 5**, после тела скила и после `1skill-architect` — не «сперва» |
| `P2` (правка скила) | **не читал** | **не читал**, отказ обоснован явно |
| эта сессия (аудит инструкции) | **не читал** | неприменимо |

Итог: `wisdom-*` — **0 из 3**. «Сперва» — 0 из 2.

**Механизм провала:** «ближайший» из восьми `wisdom-*` — это требование выбрать
без операции выбора; агент, не имея правила выбора, не выбирает вовсе. Плюс нет
предъявляемого следа: ничто не отличает «прочитал» от «мог бы прочитать».

**Repair:** заменить «ближайший» на маршрут по классу работы (правишь Claude-скил
→ `wisdom-claude-opus-5.md`; инструкцию → `science/how-to-make-llm-obey.md`;
мышление → `knowledge/how-llms-think.md`) и потребовать один предъявляемый
след — процитированную строку источника. Без следа правило останется в единицах
процентов независимо от формулировки — это же говорит и сам `AGENTS.md` строкой
ниже, но применяет только к скилам.

### F4 — «перед правкой» буквально исключает аудит и планирование

**Failure mode:** literal scope.

**Evidence:** оба приоритета (2 и 3) начинаются с «Перед правкой …» / «До принятия
… skill». В пробе `P2` агент **прямо процитировал** этот scope как причину не
применять правило: «Файлы … и вызов `1skill-architect` (обязательны по `AGENTS.md`
перед правкой скила) я намеренно **не** открывал: это метод письма, а вы просили
не редактировать». Второе независимое наблюдение — эта сессия: аудит инструкции
не запустил чтение `wisdom-*`, потому что аудит — не правка.

Наблюдаемое обязательство относится к классу «работа над скилом/инструкцией»
(включая аудит, ревью, план правки — именно там решение и принимается), а правило
называет один экземпляр — момент записи.

**Repair:** назвать класс, а не экземпляр: `«Когда работа меняет или оценивает
skill / agent / instruction — включая аудит и план правки — …»`.

### F5 — приоритет 3: корень пересказывает метод скила, которого сам назначил владельцем

**Failure mode:** text-level duplicate + risk-word overclaim.

**Evidence:** бульет длиной 9 строк содержит и правило («обязательно вызови
`1skill-architect`»), и его метод («Наблюдаемый gate обязателен всегда»,
«требуй операцию, а не совет о мышлении», контрастивная пара), и вердикт
«Процедурой и evidence владеет живой `1skill-architect`». Проверка: скил
**действительно** владеет этим содержанием — `1skill-architect/SKILL.md`
строки 156 (`→ наблюдаемый proxy или gate`), 175 (`Operators: одна-три операции`),
185–188 (мысленное удаление operator-а), 228–233 (`Operator без причины —
optional ceremony`). Удаление корневой копии функцию не теряет: она приходит в
момент действия вместе со скилом.

Контраргумент, который проверил: корневая копия грузится **раньше** вызова и могла
бы служить поводом вызвать. Но повод даёт первое предложение бульета; шесть строк
метода приходят тогда, когда применить их ещё не к чему, и приходят снова, когда
есть к чему.

**Второе:** `**обязательно**` + `**Наблюдаемый gate обязателен всегда**` — сильные
слова на правиле, которое runtime не обеспечивает. Хуков владелец не заводит
(решение зафиксировано), значит реальный control — это review-скил, который
владелец вызывает сам. В пробе `P1` скил сработал (позиция 1), в `P2` — нет; но
в `P1` `1skill-architect` мощно триггерится и своим собственным описанием, так что
атрибуция к `AGENTS.md` **не разделена**. Честный статус правила: 1 из 2 при
неразделённой атрибуции.

**Repair:** оставить в корне только `observable trigger → exact route`
(«новый или переписанный skill → `1skill-architect` до принятия; метод и evidence
— его»), метод убрать; сильное слово оставить только если появится
детерминированный слой.

### F6 — «Проверка» конфликтует с глобальным контрактом финального отчёта

**Failure mode:** конфликт precedence, разрешаемый молча и не в пользу репо.

**Evidence:**

- `AGENTS.md`: «Пиши по-русски, **коротко, без справочного шума**».
- `~/.claude/CLAUDE.md`: «Финальный отчёт пиши как привык; в конце отдельным
  блоком перескажи всё сказанное ещё раз простым языком … **Понятность важнее
  краткости**: строка-ярлык, из которой не видно, что произошло, хуже лишнего
  предложения».

Два правила тянут один и тот же момент в разные стороны, и ни одно не называет
победителя.

**Наблюдаемый исход: 3 из 3.** Все три пробы вернули длинный отчёт **с** блоком
пересказа простым языком. Глобальное правило выиграло у локального во всех
случаях; строка `AGENTS.md` про краткость поведение не изменила.

**Repair:** снять конкуренцию — репо владеет **содержанием** приёмки (что
изменено / чем проверено / какие риски), глобальный файл владеет **формой**
отчёта. Формулировка вроде `«В финале назови: что изменено, чем проверено, какие
риски остались. Форму отчёта задаёт глобальная инструкция.»` Слово «коротко»
удалить — оно проиграло замеру.

### F7 — «Цель» дублирует `_ops/GOAL.md`

**Failure mode:** text-level duplicate.

**Evidence:** первое предложение раздела («Делать систему `skills`, hooks, prompts,
инструкций, знаний и рабочих контрактов…») — почти дословный `_ops/GOAL.md`
«Что делаем». Оно не меняет ни одного первого акта: агент, который уже читает
`AGENTS.md`, из этой фразы не получает решения.

**Что удалять нельзя:** вторая часть («Канон не расширяется до model-neutral;
`GPT-5.5` и старее — только историческое evidence») — это **decision rule,
доступный без открытия `GOAL.md`**, и он режет реальную развилку. Это осознанная
свежесть, а не дубль.

**Repair:** срезать первое предложение до указателя (`Контракт проекта —
_ops/GOAL.md`), модельную оговорку оставить дословно.

### F8 — устаревшие имена в `experiments/`

**Failure mode:** stale fact.

**Evidence:** перечислены `gemini-mcp` и `md-tools` — **обеих папок нет**. При этом
`1design-review`, `logical-map-lab`, `prose-audit-lab`, `zbs-dossier`,
`global-agent-surface-viewer` и др. не названы (закрыто словом «и др.», это
нормально). Вред умеренный: агент, посланный за примером в `md-tools`, потратит
ход и может решить, что репо описан неверно целиком.

**Repair:** удалить два мёртвых имени. Список вообще не обязан быть полным —
достаточно 2–3 живых примеров плюс «и др.».

**Проверенная и снятая гипотеза:** я предполагал, что правило «правь субтри от его
инструкции» ломается на 9 папках без `AGENTS.md`. Проба `P3` показала, что не
ломается: правило само называет `README.md` как альтернативу, и агент пошёл
именно туда, первым файлом. Реальный остаток — один `zbs-dossier`, где нет ни
`AGENTS.md`, ни `README.md`. Это не finding уровня инструкции.

### F9 — `science/` не маршрутизирован из корня

**Failure mode:** gap (job `Load`).

**Evidence:** `science/` — живая зона: в scope `_ops/GOAL.md` (решение владельца
2026-08-04), свой `README.md` с явными границами владения, два owner-документа,
три папки `verification/`. Корневой `AGENTS.md` не упоминает её **ни разу**.
`README.md` маршрут даёт (пункт 6), но `README.md` объявлен «входным контекстом»,
не обязательным чтением.

Симптом на себе: адрес `science/verification/2026-08-07/` я получил из задания.

## Часть 3. Что в файле работает — не трогать

Пакет требует не переписывать здоровый слой. Работает, с evidence:

1. **`Load` в целом — pass.** `CLAUDE.md` = `@AGENTS.md`, текст дословно
   присутствует в системном контексте сессии. Механизм shim выбран верно.
2. **Раздел «Что Это За Репо» steer-ит реальные решения.** Проба `P3` на развилке
   «писать бизнес-результаты MAVO или методологические» выбрала методологические
   и **сослалась на корневую строку** «продукт всегда снаружи». Это не
   декоративная идентичность, это работающий тайбрейкер.
3. **Fallback owner-правила («tracked owner отсутствует → live install —
   единственная правда, не выдумывай parity») — сработал.** Проба `P1`:
   у `1md-lint` owner-а в репо нет, агент это проверил и корректно объявил
   установленные копии правдой, второго source tree не изобрёл.
4. **Owner-правило само по себе — сработало.** Проба `P2` процитировала
   `AGENTS.md` и выбрала repo-owner против того файла, из которого скил реально
   грузится. Без этого правила естественный ход — править то, что видишь.
5. **Раздел «GitHub» — самое сильное правило файла.** Он перекрывает дефолт

   branch first»). Такой override обязан лежать громко и в корне; форма
   правильная. (В этом прогоне не сработал только потому, что аудит ничего не
   менял.)
6. **Приоритет 1 («живой `SKILL.md` сильнее старых repo notes») —** корректное
   правило precedence, самопонижающее и потому честное. Замером не проверено:

### Предсказанный bypass моих же repair-ов

Самый вероятный способ выполнить форму, сохранив старое поведение: агент
процитирует поправленное правило в финальном отчёте («сверил owner и install»,
«прочитал wisdom») и не выполнит операцию. Именно поэтому F2 и F3 сформулированы
через **предъявляемый артефакт** (вывод `diff`, процитированная строка), а не
через обязанность. Правило без следа не лечится ещё одним `MUST` — это верно и
для моих собственных предложений.

## Часть 5. Заметка для сравнения пакетов

Что полный пакет сделал наблюдаемо, помимо содержания аудита:
